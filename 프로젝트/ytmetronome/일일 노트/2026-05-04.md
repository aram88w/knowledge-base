### 상태를 부모 컴포넌트로 올릴지, 부모 컴포넌트에서 자식 컴포넌트의 상태를 가져와서 사용할지

리액트의 기본 철학은 "상태는 부모로 올려라"이지만, 그건 부모가 그 상태를 실시간 화면 렌더링에 계속 써먹어야 할 때의 이야기입니다. 지금처럼 **"특정 이벤트(Note 변경)가 터졌을 때 딱 한 번만 상태값이 궁금한 상황"**이라면, 불필요한 전역 렌더링을 막고 컴포넌트를 독립적으로 유지하기 위해 `useImperativeHandle`로 상태를 읽어오기만(Getter) 하는 것이 압도적으로 세련된 설계입니다!


### 왜 `isSyncMode?: boolean` 처럼 `?` (선택적 프로퍼티)를 쓰나요?

`Metronome` 컴포넌트는 굉장히 독립적이고 잘 만들어진 컴포넌트입니다. 지금은 `MetronomeStudio` 안에서 쓰이고 있지만, 나중에 유튜브 기능이 전혀 없는 **"순수 메트로놈 페이지"**를 따로 만들어서 `<Metronome />`을 재사용할 수도 있습니다.

만약 `?`를 빼고 `isSyncMode: boolean`으로 필수값 처리를 해버리면, 유튜브 기능이 없는 일반 페이지에서도 무조건 `<Metronome isSyncMode={false} />`라고 억지로 적어줘야 하는 불편함이 생깁니다. `?`를 붙여두면 부모가 아무 값을 안 넘겨도 에러가 나지 않으며, 컴포넌트 내부에서 알아서 `false`로 취급할 수 있어서 **컴포넌트의 재사용성**이 훨씬 높아집니다.

```tsx
// Metronome.tsx
interface Props {
  isSyncMode?: boolean;
}

export default function Metronome({ isSyncMode = false }) {...}
```


### 하위 컴포넌트의 데이터 초기화 

`bpmOptions`는 부모(`YoutubeSync`)가 아니라 자식 컴포넌트인 `TrackInfoPanel.tsx` 내부의 자체 State(`useState`)로 존재합니다. 부모에서 유튜브 URL을 바꾼다고 해서 자식 컴포넌트의 State가 알아서 지워지지 않습니다.

이를 초기화하는 두 가지 방법이 있는데, **두 번째 방법(꿀팁)**을 강력히 추천합니다!

##### 방법 1. `useEffect` 사용하기 (일반적인 방법)

`TrackInfoPanel.tsx` 내부에 아래 코드를 추가해서, `videoId`가 바뀔 때마다 수동으로 비워주는 방법입니다.

```tsx
useEffect(() => {
    setExtractedBpm(null);
    setBpmOptions([]);
}, [videoId]);
```

##### 방법 2. `key` Prop 활용하기 (🔥가장 추천하는 리액트 꿀팁🔥)

리액트에서는 컴포넌트의 `key` 값이 바뀌면, 기존 컴포넌트를 아예 파괴(Unmount)하고 완전히 새 컴포넌트로 다시 만들어버립니다(Remount). 따라서 `YoutubeSync.tsx`에서 `TrackInfoPanel`을 부를 때 **`key={videoId}`** 하나만 딱 추가해 주면 끝납니다!

```tsx
// YoutubeSync.tsx
<TrackInfoPanel
    key={videoId} // 💡 핵심! 비디오가 바뀌면 컴포넌트가 완전히 초기화됨
    videoId={videoId}
    selectedBpm={selectedBpm}
    // ...
/>
```

이렇게 하면 `useEffect`를 귀찮게 적을 필요도 없이, 새로운 영상을 불러오는 순간 `TrackInfoPanel` 내부에 있던 `bpmOptions`나 분석 로딩 상태 등 모든 State가 백지상태(기본값)로 완벽하게 리셋됩니다. 아주 깔끔하고 강력한 아키텍처 패턴이니 꼭 적용해 보세요!


### 유튜브 플레이어 <-> 메트로놈 배속 설정

A. 유튜브 플레이어에서 배속 설정하면 메트로놈의 배속이 설정되는 과정
1. 가장 상위 컴포넌트인 MetronomeStudio에서 **onVideoPlaybackChange를 유튜브 플레이어 컴포넌트로 내려주고**, 
2. 유튜브 컴포넌트에서 배속이 변경되면 해당 메서드를 호출 
3. 해당 메서드 내에서는 메트로놈 컴포넌트에서 **useImperativeHandle로 올려보낸 메트로놈 배속 설정**이 있음.

B. 메트로놈에서 배속 설정하면 유튜브 플레이어 배속이 설정되는 과정: A와 동일

Tone.Part에서 초(s) 단위를 사용하면 배속을 지정할때 뭔가 이상한 문제가 자꾸 생김. 그래서 '음악적 시간 단위'인 Ticks(i)를 사용함. 


### 프로젝트의 복잡성이 오르는 경우

복잡한 프로젝트일수록 이런 식으로 **데이터를 담는 창고(Zustand)**와 **로직을 처리하는 뇌(Custom Hook)**, 그리고 **화면을 보여주는 얼굴(Component)**을 분리해서 관리하게 됩니다!

커스텀 훅으로 로직과 컴포넌트를 분리한 예시 
- 로직만 모아둔 파일
``` ts
// useMetronomeSync.ts
import { useState, useEffect } from 'react';

export function useMetronomeSync() {
    // 여기에 기존 MetronomeStudio에 있던 지저분한 로직들을 다 몰아넣습니다.
    const [bpm, setBpm] = useState(120);
    const [beatsArray, setBeatsArray] = useState([]);
    // ... useEffect 등 각종 함수들 ...

    // 화면(UI)에서 쓸 것들만 바구니에 담아서 반환해줍니다.
    return { bpm, setBpm, beatsArray, setBeatsArray /* 등등 */ };
}
```

- 화면만 남은 파일
``` tsx
// MetronomeStudio.tsx
import { useMetronomeSync } from './useMetronomeSync';

export default function MetronomeStudio() {
    // 훅을 호출해서 로직과 데이터를 쏙 빼옵니다.
    const { bpm, setBpm, beatsArray, setBeatsArray } = useMetronomeSync();

    // 여기는 온전히 화면(UI) 그리는 데만 집중할 수 있습니다!
    return (
        <main>
            <Metronome bpm={bpm} onBpmChange={setBpm} />
            <YoutubeSync beatsArray={beatsArray} />
        </main>
    );
}
```


### Zustand의 트레이드 오프

##### 1. 컴포넌트의 재사용성 파괴 (가장 큰 이유)

리액트에서 부모가 자식에게 Props를 내려주는 구조가 기본인 이유는 **"컴포넌트의 독립성"** 때문입니다.
- **Props를 받는 방식 (현재 구조)**: `<Metronome bpm={120} />`처럼 만들면, 나중에 다른 페이지나 아예 다른 프로젝트에서도 `bpm` 숫자만 던져주면 똑같이 작동하는 훌륭한 '재사용 가능한 부품'이 됩니다.
- **Zustand를 쓰는 방식**: `Metronome` 컴포넌트 안에서 `useStore(state => state.bpm)` 처럼 전역 상태를 직접 꺼내 쓰게 만들면? 이 컴포넌트는 무조건 Zustand 스토어가 있는 프로젝트에서만 작동하는 '종속적인 컴포넌트'가 되어버립니다.

따라서 팝업 창 열림/닫힘, 검색창 입력값 같은 **특정 컴포넌트 안에서만 쓰이는 상태까지 전부 Zustand에 넣으면 코드가 엉키고 재사용이 불가능해집니다.**

##### 2. Next.js의 서버 컴포넌트 패러다임 (Server vs Client)

현재 사용 중이신 Next.js (특히 App Router 최신 버전)는 **서버 컴포넌트**라는 강력한 기능을 사용합니다. Zustand는 브라우저 위에서만 돌아가는 **클라이언트 상태 관리 도구**입니다. 서버에서 HTML을 미리 그려서 내려보내는 Next.js의 핵심 기능 안에서는 Zustand의 값을 직접 읽거나 수정할 수 없습니다. 결국 서버에서 가져온 데이터는 어쩔 수 없이 최상단 부모에서부터 Props로 자식들에게 내려줘야만(Prop Drilling) 하는 경우가 많습니다.

##### 3. 서버 상태(Server State) vs 클라이언트 상태(Client State)

앱이 다루는 상태는 크게 두 가지로 나뉩니다.
- **클라이언트 상태**: 지금 다루고 계신 현재 BPM, 동기화 오프셋, 다크모드 여부 등 (브라우저 안에서만 의미 있는 데이터) 👉 **Zustand가 최고입니다.**
- **서버 상태**: DB에서 가져온 곡 목록, 유튜브 영상 캐시 데이터 등 👉 이런 데이터는 Zustand에 넣기보다 **React Query, SWR** 같은 '데이터 통신/캐싱 전용 라이브러리'를 쓰는 것이 훨씬 강력합니다. 로딩 상태나 에러 처리를 다 알아서 해주기 때문입니다.


그래서 실무 개발자들은 **"이 데이터가 진짜 여러 컴포넌트에서 공유되어야 하는 앱의 핵심 상태(Global State)인가?"**를 고민한 뒤, 정말 필요한 상태(예: 현재 BPM 설정, 로그인한 유저 정보)만 Zustand에 넣고, 나머지는 기본 `useState`와 Props로 해결하는 식으로 **균형(Trade-off)**을 맞추며 개발합니다!
