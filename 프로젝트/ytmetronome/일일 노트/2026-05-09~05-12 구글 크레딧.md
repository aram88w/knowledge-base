구글 클라우드 무료 크레딧의 사용 기한이 5월 13일까지인데 잔여 크레딧이 많아서 일요일부터 오늘(화요일)까지 이것저것 돌려봤음. 

우선 이미지 생성 AI 모델을 사용해보고 싶어서 테스트로 고화질 이미지를 몇백장 뽑아두려고 했는데, 생각보다 이미지를 알아서 딱 맞게 뽑아주지는 않았다. 프롬프트를 아주 잘 입력해야할 것 같았기에 번거로워서 금방 포기했다. 

다음으로는 메트로놈 서비스에서 사용할 데이터를 미리 준비해두는 것을 했다. 오디오 파일을 받아서 분석 후에 beatsArray를 DB에 저장해두는 것이다. 
사람들이 악기를 연습할때 많이 연주하는 곡의 제목을 많이 받아야했는데 이것부터 쉽지 않았다. 이런 대량의 데이터를 제공하는 곳이 찾기가 힘들었다. API를 제공하는 스포티파이의 재생목록에서 데이터를 받아올까 했는데 '기타 연주곡', '베이스 연습곡' 이런식의 플레이리스트는 이상한 노래만 있었다. 
그래서 생각해낸 것이 유튜브에서 타브를 올리는 채널의 모든 동영상의 videoId를 가져와서 그걸 1차로 사용하고, 2차로 해당 동영상의 제목으로 검색한 원본 음원, 타브 영상 3개 (혹시 누락된 계정의 영상), 백킹트랙 영상 3개를 가져오기로 했다. 

구글 VM 서버는 예전에 extractframe을 할때 삽질을 했던 경험이 있었기에 쉽게 설정했다. yt-dlp을 기반으로 한 오디오 파일 수집 파이프라인을 실행하니까 유튜브의 IP 기반 요청 제한 정책으로 인해 차단당하는 문제가 발생했다. 처음에는 5~6개의 서버에 워커를 병렬로 4개씩 돌렸는데 30분도 안 돼서 차단 당했다. 
이를 해결하기 위해서 서버당 워커 수를 2개로 줄이고 요청 간 간격을 대폭 늘렸으며 세션 쿠키 인증 헤더를 파이프라인에 적용했다. 이렇게 하니까 속도가 느리긴 해도 차단은 당하지 않고 안정적으로 20000개 이상의 데이터를 수집할 수 있었다. 
마지막에는 속도를 높이기 위해 서버 두 개를 추가로 올려서 RapidAPI를 이용해서 오디오 파일 다운로드 워커도 실행했다. 중간에 실수로 풀링 요청 주기를 너무 짧게 설정하여 API 한도가 금방 소진되는 시행착오도 겪었다. 

아 그리고 초반에 타브 채널들의 videoId를 yt-dlp로 조사해서 .csv 파일로 12000개 정도 저장해놨는데 이걸 내 DB로 옮길때 여러가지 문제가 많았다. DBeaver를 사용했는데 대용량 CSV 임포트 시 데이터 타입 매핑 문제로 시행착오가 있었다.

구글 클라우드 에이전트 파트에 여러가지 기능이 많길래 마케팅 에이전트? 이것도 사용해봤는데, 뭐 딱히 획기적이지는 않았다. 그냥 마케팅에 더 특화된 제미나이 3.0 같은 느낌. 

지금은 1차로 타브 채널의 모든 영상들은 이미 완료했고, 그 videoId를 기반으로 아티스트와 제목을 뽑아서 중복은 없애고 그걸로 유튜브 검색을 해서 공식음원, 타브, 백킹트랙의 videoId를 다시 뽑아내고 있다. 마지막으로 이 videoId를 조사해서 beatsArray를 뽑아내면 완료된다. 

나중에 보니까 너무 작업량이 많아져서 공식음원은 제외하는 작업을 또 돌린 후에 다시 video_tasks에 채워서 worker_cookies.py랑 worker_api.py를 돌리고 있다. 힘들다.
