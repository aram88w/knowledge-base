### Next.js 로그 

- **서버:** 개발자가 직접 `Pino`로 필요한 로그(정보, 경고, 에러 등)를 명시적으로 작성함.
- **클라이언트:** 개발자가 직접 로깅 시스템을 구축하지 않고, `console.log`는 디버깅용으로만 쓰며, `Sentry`가 에러를 자동으로 수집함.
- **통합 뷰어:** `Sentry` 대시보드에서 클라이언트의 자동 에러 로그와 서버의 주요 에러/로그를 한눈에 파악함.

##### 1. 서버 세팅 (Pino)

- `pino`를 설치하고 `lib/logger.ts` 같은 유틸리티 파일을 만듭니다.
- 서버 컴포넌트, Route Handler(API), Server Action에서 `console.log` 대신 이 logger를 가져와 사용합니다.
- **주의점:** Pino 로그는 터미널(stdout)로 출력되므로, 서버(예: AWS, Vercel 등) 환경에 따라 이 출력된 로그들을 모아서 저장해 줄 인프라(AWS CloudWatch, Datadog 등)가 나중에는 필요할 수 있습니다. (하지만 Vercel을 쓴다면 Vercel 대시보드의 Logs 탭에서 Pino가 예쁘게 출력한 JSON 로그를 바로 확인할 수 있어서 매우 편리합니다.)

##### 2. 프론트/풀스택 에러 트래킹 세팅 (Sentry)

- `@sentry/nextjs`를 설치하고 `npx @sentry/wizard@latest -i nextjs` 명령어를 실행하면 Sentry가 프로젝트에 필요한 설정 파일들을 자동으로 세팅해 줍니다.
- 이 세팅이 끝나면 **클라이언트 에러와 서버측 에러를 즉시 자동 수집**됩니다.

##### 3. (옵션) 수동 기록

- 만약 Server Action 내부에서 `try-catch` 블록을 사용해 에러를 잡은 뒤, 사용자에게 성공/실패 여부(예: `{ success: false, error: '...' }`)를 객체로 반환하도록 코드를 작성했다면, 이 에러는 **예외로 던져지지 않은 것(handled)**으로 취급되어 Sentry에 자동으로 기록되지 않습니다.
- 이 경우에는 `catch` 블록 내에서 명시적으로 Sentry에 보고해야 합니다.

```ts
import * as Sentry from "@sentry/nextjs";

export async function myServerAction() {
  try {
    // 비즈니스 로직
  } catch (error) {
    // 에러를 수동으로 Sentry에 전송
    Sentry.captureException(error);
    return { success: false, error: "서버 오류가 발생했습니다." };
  }
}

```


### 질문 1. `db/data.ts`에는 로그를 안 찍어도 되나? `actions.ts`에만 찍는 게 낫나?

**네, 가급적 "최상위 진입점"인 `actions.ts` (또는 API Route)에서만 에러 로그를 한 번 찍는 것이 좋습니다.**

이유는 **"로그 중복(Noise) 방지"** 때문입니다.

만약 `db/data.ts` 안의 `dbGetUserByIpAddress` 함수에서도 `logger.error`를 찍고, 그걸 호출한 `actions.ts`의 `getUserByIp`에서도 `logger.error`를 찍는다면 어떻게 될까요? 단 하나의 DB 에러가 발생했을 뿐인데, 똑같은 에러 로그가 두 번, 세 번 연달아 찍히게 됩니다. 이는 로그 시스템을 더럽히고 로그 용량(비용)만 늘리게 됩니다.

**[ 권장하는 패턴 ]**

1. **하위 레이어 (`db/data.ts`):** 에러가 나면 굳이 로그를 찍지 않고 에러를 위로 **그대로 던집니다(`throw`)**.
    
    ```typescript
    // db/data.ts
    export async function dbGetUserByIpAddress(ip: string) {
        // try-catch 없이 바로 던지거나, catch 하더라도 throw error; 만 합니다.
        return await db.select().from(users).where(eq(users.ip, ip));
    }
    ```
    
2. **최상위 레이어 (`lib/actions.ts`):** 클라이언트의 요청을 직접 받는 최전방이므로, 여기서 전체를 `try-catch`로 묶고 **딱 한 번만 상세하게 `logger.error`를 찍습니다**.
    
    ```typescript
    // lib/actions.ts
    export async function getUserByIp() {
        try {
            const ip = getClientIp();
            // 내부 함수 호출 (여기서 터지면 catch로 내려옴)
            const user = await dbGetUserByIpAddress(ip); 
            return user;
        } catch (error) {
            // ⭐ 여기서 한 번만 상세하게 로그를 찍음
            logger.error({ err: error, ip }, "IP 기반 유저 조회 실패");
            throw new Error("유저 정보를 가져오지 못했습니다.");
        }
    }
    ```

### declare global

``` ts
declare global {
    interface Window {
	    // webkitAudioContext의 타입이 AudioContext와 같음을 명시
        webkitAudioContext: typeof AudioContext;
        // webkitOfflineAudioContext의 타입이 OfflineAudioContext와 같음을 명시
        webkitOfflineAudioContext: typeof OfflineAudioContext;
    }
}
```

1. `declare` (선언하다)
"이 코드는 실제 작동하는 자바스크립트 로직이 아니니까 나중에 빌드할 때 다 지워버려! 오직 **TypeScript(문법 검사기)에게 타입 정보만 미리 귀띔해주기 위한 용도**야!"라는 뜻입니다.

2. `global` (전역)
"내가 지금부터 귀띔해 줄 타입 정보는 이 파일 안에서만 쓰이는 게 아니라, **우리 프로젝트 전체(Global) 어디서든 똑같이 적용되는 규칙**이야!"라는 뜻입니다.

3. `interface Window { ... }` (인터페이스 병합)
이 문법이 가능한 가장 큰 이유는 TypeScript의 **'인터페이스 병합(Interface Merging)'**이라는 독특한 특징 때문입니다. 일반적인 변수(`const`, `let`)는 똑같은 이름을 두 번 선언하면 충돌이 나서 에러가 납니다. 하지만 `interface`는 똑같은 이름으로 여러 번 선언하면, 기존 것을 덮어버리는 게 아니라 **기존 내용에 새로운 내용이 찰흙처럼 합쳐집니다(Merge).**

TypeScript는 이미 자체적으로 거대한 `Window` 인터페이스(사전)를 기본으로 내장하고 있습니다. 거기에 우리가 `interface Window`를 한 번 더 적어주었기 때문에, TypeScript는 "아하! 내가 가진 기존 Window 사전에 네가 적어준 `webkitAudioContext`라는 단어를 추가로 끼워 넣어줄게!" 하고 합쳐버리는 것입니다.


**한 줄 요약:** `declare global { interface Window { ... } }` 라는 문법은, **"이 프로젝트 전체에서(global), 실제 코드는 건드리지 말고(declare), 네가 원래 가지고 있던 Window 사전에 이 단어들만 몰래 추가해 줘(interface 병합)!"** 라는 뜻의 완벽하게 짜여진 TypeScript 공식 문법입니다!


### 다국어

1. `next-intl` 패키지를 설치합니다.
2. `messages/` 폴더에 각 언어별 번역 파일(`en.json`, `ko.json` 등)을 생성합니다.
3. `routing.ts`에서 지원하는 언어, 기본 언어 설정
4. 프로젝트 루트에 `i18n/request.ts` 파일을 생성하여 번역 파일을 불러오는 설정을 합니다.
5. `proxy.ts` 파일을 생성하여 사용자의 브라우저 언어를 감지하고 URL에 국가 코드(예: `/ko/about`, `/en/about`)를 붙여주도록 설정합니다.
6. `next.config.mjs`에 `next-intl` 플러그인을 적용합니다.
7. 기존 `app/` 폴더 내의 페이지들을 `app/[locale]/` 폴더 하위로 이동시킵니다.
8. 컴포넌트 내에서 `useTranslations` (클라이언트) 또는 `getTranslations` (서버) 훅을 사용하여 텍스트를 출력합니다.

##### 1단계: `proxy.ts`의 시간 (교통 경찰)

- **언제 실행되나?** 사용자가 URL을 치고 엔터를 친 직후, 화면(HTML)을 그리기 **전**에 가장 먼저 실행됩니다.
- **무엇을 하나?** 오직 **'주소(URL)'**만 건드립니다. "어? 너 한국인이네? `/ko/` 경로로 가!" 하고 주소만 바꿔줍니다.
- **한계:** 얘는 `ko.json` 파일 안에 무슨 글자가 적혀 있는지 전혀 모릅니다. 파일에 접근조차 하지 않습니다. 그저 방(경로) 안내만 해줄 뿐입니다.

##### 2단계: `layout.tsx`와 `getMessages()`의 시간

- 이제 Next.js가 `/ko` 경로의 페이지를 바탕으로 화면(HTML)을 그리기 시작합니다.
- `layout.tsx`에서 `const messages = await getMessages();`를 만납니다.
- "잠깐! 화면을 그리려니까 번역 텍스트가 필요한데? 나 텍스트 좀 줘!" 하고 외칩니다.

##### 3단계: `request.ts`의 시간 (번역본 창고 관리자)

- **언제 실행되나?** `getMessages()`가 호출되는 순간, 즉 **화면을 그리는 도중에 번역 데이터가 필요할 때**마다 백그라운드에서 실행됩니다.
- **`requestLocale`에는 뭐가 들어가나?** `proxy.ts`가 안내해 준 현재 경로의 언어값, 즉 **`"ko"`** 또는 **`"en"`**이라는 문자열이 쏙 들어갑니다. (내부적으로 Next.js의 캐시나 헤더에서 읽어옵니다)
- **무엇을 하나? (가장 중요 ⭐️)**
    - `requestLocale`이 `"ko"`인 것을 확인합니다.
    - **실제로 하드디스크에 있는 `../messages/ko.json` 파일을 열어서 읽어옵니다.** (`import` 구문 실행)
    - 이 JSON 데이터를 덩어리째로 `layout.tsx`에게 넘겨줍니다.


##### 언어 변경

`next-intl` 라이브러리를 사용하면 이를 훨씬 더 스마트하게 처리할 수 있습니다. 구체적인 로직은 다음과 같습니다:

1. **경로 유지 (Pathname Preservation):** 사용자가 현재 어느 페이지(예: `/about`, `/settings`)에 있든, 언어를 바꿨을 때 해당 페이지의 내용을 그대로 다른 언어로 보여줘야 합니다. 그래서 현재의 `pathname` 정보를 가져옵니다.
2. **클라이언트 사이드 네비게이션:** `next-intl`에서 제공하는 `useRouter`를 사용하면 브라우저의 전체 새로고침 없이 URL만 살짝 바꿔주는 '소프트 네비게이션'이 가능합니다.
3. **쿠키 업데이트 (자동 처리):** 이미 `proxy.ts`에 미들웨어 설정을 잘 해두셨기 때문에, 사용자가 `/en` 경로로 이동하면 미들웨어가 이를 감지하고 브라우저의 언어 설정 쿠키(`NEXT_LOCALE`)를 자동으로 업데이트합니다. 이렇게 하면 다음에 사이트에 다시 들어올 때도 사용자가 마지막으로 선택한 언어가 유지됩니다.

**실제 코드 예시 (개념 설명용):** `i18n/routing.ts`에서 이미 `useRouter`와 `usePathname`을 만들어 두셨기 때문에, 다음과 같은 방식으로 작동하게 됩니다.

``` tsx
const router = useRouter();
const pathname = usePathname();

const onLanguageChange = (nextLocale: string) => {
  // 현재 경로(pathname)는 유지하고, locale 옵션만 바꿔서 replace 합니다.
  router.replace(pathname, { locale: nextLocale });
};
```

단순히 `window.location.href`를 바꾸는 게 아니라, 라이브러리가 제공하는 래퍼(wrapper) 함수를 사용함으로써 **현재 주소창의 쿼리 파라미터나 해시 등은 유지하면서 언어만 깔끔하게 전환**하는 것이 핵심입니다.
