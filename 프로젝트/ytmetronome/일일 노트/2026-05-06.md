### 리액트 구조와 리팩토링 타이밍

처음에는 상위 컴포넌트에서 하위 컴포넌트의 videoCurrentTime을 ref로 가져오지 않고 하위 컴포넌트에서 직접 videoCurrentTime을 넣어서 상위 컴포넌트의 메서드를 호출했는데, 코드를 작성하다 보니까 상위 컴포넌트에서 하위 컴포넌트의 ref가 필요해서 ref로 가져왔음. 그러면 굳이 하위 컴포넌트에서 직접 videoCurrentTime을 넣지 않고 상위 컴포넌트에서 ref로 videoCurrentTime을 넣어줘도 됨. 
이렇게 처음에 만들어둔 데이터 구조가 바뀔때 다른 부분은 바로바로 적용을 해야하는것인지 아니면 구조를 유지해도 되는것인지 모르겠음.

##### 리액트의 기본 원칙 관점에서의 답변

리액트는 기본적으로 **"데이터는 위에서 아래로 흐르고 (Props), 이벤트는 아래에서 위로 올라간다 (Callback)"**는 단방향 데이터 흐름(One-way Data Flow)을 매우 권장합니다.

따라서 **기존 방식(하위가 상위의 함수를 호출하면서 값을 넘겨주는 방식)이 리액트의 철학에 더 맞고 자연스러운 방식**입니다.

`ref`를 통해 상위가 하위의 내부 데이터(currentTime)나 메서드에 직접 접근하는 것은 리액트에서 **"제어의 역전(Inversion of Control)"을 깨뜨리는 예외적인 행위(Escape Hatch)** 로 간주합니다. 공식 문서에서도 `ref`는 DOM 노드에 직접 포커스를 주거나 외부 라이브러리(여기서는 YouTube Player API)를 다룰 때처럼 '불가피할 때만' 쓰라고 권장합니다.

`ref`를 사용하면 상위 컴포넌트가 하위 컴포넌트의 내부 구조를 깊이 알아야 해서 결합도가 높아지므로 최대한 자제.


### NextAuth.js 공통 테이블 

NextAuth는 사용자 관리를 위해 크게 **2개의 테이블**을 사용하도록 설계되어 있습니다. 이 2개의 테이블만 있으면 구글이든 카카오든 애플이든 수십 개의 소셜 로그인을 다 붙여도 테이블을 추가할 필요가 없습니다.

**1. `User` 테이블 (유저 정보 - 공통)** 사람 자체를 나타내는 테이블입니다. 소셜에서 받아온 정보 중 가장 공통적인 것만 담습니다.
- `id`
- `name` (이름 또는 닉네임)
- `email` (이메일)
- `image` (프로필 사진)

**2. `Account` 테이블 (소셜 연결 정보 - 공통)** "이 유저가 어떤 소셜 서비스들을 이용해 가입했는지"를 기록하는 테이블입니다.
- `userId` (User 테이블의 id를 가리킴)
- `provider` (예: `"google"`, `"kakao"`, `"apple"`)
- `providerAccountId` (그 소셜 서비스 내에서 발급한 고유 ID 값)
- `access_token`, `refresh_token` (소셜 서비스와 통신할 때 쓰는 인증 토큰)

질문자님은 **단 하나의 공통된 `users` 테이블과 `accounts` 테이블** 구조만 만들어 두시면 됩니다. 나중에 "카카오 로그인도 추가해야지!" 라고 마음먹으셨을 때, DB 테이블 구조는 단 1건의 수정도 필요 없고 NextAuth 설정 코드에 카카오 키 값만 추가하면 끝납니다!
