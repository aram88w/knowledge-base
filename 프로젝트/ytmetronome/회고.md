## 개요 및 총평

ytmetronome은 유튜브 영상의 오디오 파일을 분석하여 추출한 BPM과 박자 정보를 기반으로 사용자가 영상에 맞춰 실시간으로 동기화된 메트로놈을 들으며 악기를 연습할 수 있도록 하는 웹 서비스임.

저작권 및 서비스 지속가능성 측면에서 서버에 오디오 파일을 영구 저장하지 않고 1회성으로 비트 분석 후 즉시 폐기하며 오직 BPM과 박자 타임스탬프 데이터(BeatsArray)만 DB에 저장하는 구조임.

## 내용

처음에는 유튜브 URL로 해당 오디오 파일을 앞에 1분만 받아오고 그걸 기반으로 BPM을 분석해서 메트로놈의 BPM을 설정하고 첫 박자만 맞추려고 했다. BPM을 맞춰두고 첫 박자에 실행하도록 하면 나머지는 자동으로 맞을 거라고 생각했기 때문이다. 그래서 정확한 BPM을 추출하는 것과 첫 박자를 맞추는 것만 해결하면 쉽게 구현할 것이라고 생각했다. 

프로젝트를 진행하는 도중에 특정 곡의 BPM이 계속 유지되는게 아니라는 것을 깨닫고 박자 타임스탬프 데이터(BeatsArray)를 추출하는 방식으로 바꿨다. 그러기 위해서 오디오 파일도 앞에 1분이 아닌 전체를 받도록 수정해야했다.

### 4/24 ~ 4/28: 기본적인 메트로놈 기능

Next.js + 리액트 + TS로 만드는 첫 프로젝트여서 헤맨 부분이 많았다. 
코드를 본격적으로 작성하기 전에 `globals.css`에 사용할 테마들을 지정했다. 폰트도 공통으로 하나만 빠르게 지정하고 넘어갔다. 이런 사소한 디자인이 중요하지 않다는 것을 전 프로젝트에서 배웠기 때문이다. 

기본적인 메트로놈 기능은 Tone.js 라이브러리를 사용하여서 구현했다. 소리 선택, 노트 설정, 박자 설정, 탭탬포, 볼륨 및 배속 기능까지 빠르게 구현했다. 반복적인 코드 작성은 AI를 통해서 개발 속도를 높였고 나는 컴포넌트 간 상태 관리 구조와 데이터 흐름 아키텍처를 설계하는 데 집중했다.  


### 4/29 ~ 5/5: 유튜브 동기화 기능

유튜브 URL로 오디오 파일을 받아올 수 있는 방법이 뭐가 있을까 찾아보다가 대강 4개가 있는 걸 알았다. 
1. RapidAPI를 활용: 무료 횟수가 적고, 유료 전환 시 비용이 발생하고 외부 API 의존해야하지만 관리를 알아서 해줌. 
2. e2-micro 서버에 yt-dlp + po-token 직접 구축: 자체 서버에서 처리할 수 있으나 유튜브 보안 정책이 업데이트될 때마다 지속적으로 유지보수를 해줘야함. 
3. 서버에 Coblat API 사용: 내부적으로 yt-dlp를 사용하는 오픈소스 기반 API. 무거워서 e2에서는 사용하지 못할 가능성이 크다고 했음. 
4. e2-micro 서버에서 주거용 프록시 + yt-dlp: 찾아보니까 대형 클라우드 서버 IP는 이미 유튜브에서 차단을 시켜놨다고 함. 주거용 프록시를 사용하면 해결할 수 있으나 지속적인 트래픽당 비용(GB당 요금) 비효율성과 프록시 망의 보안 및 안정성 불확실성 문제가 있음.

처음에는 Coblat API를 사용하려고 했음. 만약 스트리밍 형태로 받을 수 있으면 어차피 10초만 받을거니까 가볍게 운영할 수 있을 거라고 생각했음. 그런데 제대로 동작하지 않아서 레딧에 찾아보니까 한 8개월부터 정상 동작이 안되는 서비스였음. AI가 이 소식을 업데이트 못한 것임. 
결과적으로는 RapidAPI를 사용하기로 했음. 초기에는 무료 플랜을 사용하고 사용자가 많아지면 유료 플랜을 쓰든 할 생각임. 
어차피 한번 등록한건 DB에 BPM, 첫 박자 시간 데이터를 저장해서 그걸 사용하면 되고 사용자가 많아지면 나중에 RapidAPI 유료 플랜을 사용할 예정임. 사용자가 유튜브 URL을 입력하고 확인을 누르면 RapidAPI로 StreamURL을 받아서 앞에 1분만 오디오 파일을 받고 바로 끊어버린 후 그걸로 Essentia.js를 활용해서 브라우저에서 BPM과 첫 박자를 분석하도록 했다. RapidAPI에서 수많은 서드파티 API를 테스트하며 최적의 StreamURL을 제공하는 API를 찾아냈다. 

현재 동기화 모드인지 아닌지, 선택된 BPM으로 메트로놈의 BPM을 업데이트, 유튜브 영상 실행하면 메트로놈도 실행되도록 하는 등의 기능들도 추가했다. 

여기까지 해두고 여러가지 영상으로 테스트를 해봤는데 박자가 절반은 안 맞는 것이었다. 첫박자의 문제인가 싶었는데 첫박자를 맞춰놔도 시간이 지나면 어긋나는 것이었다. 이유는 모든 곡이 명시된 BPM대로 쭉 따라가지 않는다는 것이었다. 난 이게 납득이 안되었다. 라이브는 몰라도 공식 음원이면 녹음할때 드럼이 메트로놈을 틀고 드럼을 치고 그것에 맞춰서 다른 악기들이 연주하는 것이라고 생각했다. 그렇다면 중간중간에 어느정도 박자는 맞지 않더라도 전체적인 곡의 흐름은 하나의 BPM을 따라가야하는 것이 맞다고 생각했다. 하지만 이게 아니었다. 공식 음원이고 밝혀진 BPM이 있더라도 한 곡 안에서 BPM이 미세하게 바뀔 수 있었다. 그런 곡이 적은 것도 아니었다. 
이런 것을 서비스 개발 전에 알고 구현을 어떻게할지 예상을 했어야 했는데 너무 안일하게 생각했다. 

어쨋든 하나의 BPM으로 실행하면 박자가 맞지 않는다는 것을 알고 Essentia.js에서 박자라고 인식되는 시점을 모아둔 BeatsArray를 추출할 수 있는데 이것을 이용하기로 했다. 오디오파일을 1분만 받지 않고 전부 다 받도록 하고 동기화 모드인 경우에 메트로놈이 BeatsArray에 맞춰서 울리도록 수정했다. 

그런데 이렇게 했는데도 미세하게 박자가 안 맞는 것이다. 유튜브 동영상이 먼저 실행되면 그때의 동영상 시간이 메트로놈에 전해지고 그걸 기반으로 BeatsArray에서 언제 박자를 울릴지 정하는 구조였는데, 동영상 시간이 메트로놈으로 전해지는 사이에 지연이 있었기 때문에 박자가 안 맞는 것이었다. 해결책으로 메트로놈과 유튜브 컴포넌트를 총괄하는 `MetronomeStudio.tsx`를 만들어서 여기서 `MetronomeRef`, `youtubeSyncRef`를 이용해서 관리하도록 했다. 그 이후로도 Tone.js에서 매번 BeatsArray를 이용한 Part를 만들지 않게 하거나 videoId가 입력되면 미리 Part를 만들어두던가 하는 등의 최적화로 지연을 거의 없앴다. 

Note를 변경할때도 동기화가 유지되도록 하거나, videoId가 바뀌면 초기화를 하거나, 특정 상황에서 버튼들의 비활성화/활성화 설정, 동기화 모드일때 BPM 설정 불가, 싱크보정이나 BeatsArray가 변경되면 메트로놈 실행 중인 경우에도 자동 반영, 동기화 모드 활성화/비활성화 시 메트로놈 시작/정지 등의 규칙들을 추가했다. 이게 은근히 데이터 관리 같은 걸 신경써야해서 힘들었다. 


### 5/5 ~ 5/6: 메트로놈 소리 설정, 박자 상태 설정, 유튜브 PIP

메트로놈 소리가 마음에 안들어서 AI를 통해서 여러가지 소리를 테스트했는데 이것도 엄청 마음에 들지는 않는다. Tone.js에서 설정할 수 있는 것들이 너무 많고 값을 0.01 단위로 수정이 가능하다보니 설정을 하나씩 바꿔보면서 해보기도 힘들어서 우선은 연주 연습에 방해되지 않는 정도의 소리를 찾아서 적용하고 후순위 과제로 미뤘다. 
박자를 기본, 강조음, 뮤트음, 고스트노트를 설정할 수 있도록 했고, 메트로놈을 보거나 설정하면서 유튜브를 볼 수 있도록 PIP 모드도 추가했다. 


### 5/7 ~ 5/9: IP 기반 사용자 로직 추가, 에러 공통화, 오디오 파일 다운로드 방식 수정

우선 로그인 기능을 추가하지 않고 IP 기반으로 사용자 정보를 저장하고 사용량과 요청한 동영상이 저장되도록 했다. 이것도 기존이었으면 로그인 기능을 일단 구현했을텐데, 이전 서비스의 경험으로 먼저 거창하게 하지 않았다. 반응이 좋으면 그 다음에 추가해도 되는 것들이다. 

실제로 RapidAPI를 요청해서 테스트 해봤는데 자꾸 오디오 파일을 받는 과정에서 무한대기하다가 타임아웃이 발생하는 에러가 나는 것이었다. 나는 StreamURL을 받으면 그게 유튜브 서버랑 API 서버의 중간 다리를 놔주는 걸로 알아서 바로 StreamURL로 오디오 파일을 받을 수 있는줄 알았는데, API 서버가 먼저 유튜브 서버에서 오디오 파일을 받고 그걸 내가 StreamURL로 받는 것이었다. API 서버가 오디오 파일을 다운로드 하기 전에 내가 다운로드하려고 접근하면 무한대기를 하게되는 것이었다. 그래서 LinkDownloadProgress를 받아서 EventStream에서 진행상황을 받고 API 서버에서 완료된 후에 DownloadUrl을 받아서 처리하도록 바꿨다. 


### 5/10 ~ 5/13: 구글 클라우드 크레딧 사용

구글 클라우드 무료 크레딧 만료일이 5/13까지라서 4일간 크레딧을 최대한 소진하기 위해서 이것저것 했다. 
처음에는 이미지 생성 AI 모델을 사용해보고 싶어서 테스트로 고화질 이미지를 만들어두려고 했는데 결과가 너무 AI가 만든 이미지가 티나서 포기했다. 프롬프트를 잘 넣으면 결과가 다를지는 모르겠지만 실망스러웠다. 

다음으로는 메트로놈 서비스에서 사용할 BeatsArray 데이터를 미리 조사해둬서 API 요청 비용을 아끼도록 했다. 기타 타브를 올리는 채널 리스트를 손수 찾아서, yt-dlp로 해당 채널의 videoId를 전부 추출해서 DB에 올렸다. 
구글 클라우드 서버에 yt-dlp를 기반으로 한 오디오 파일 수집 파이프라인을 파이썬워커로 병렬로 띄워서 해당 DB에서 videoId를 가져와서 오디오 스트림을 Essentia로 분석하고 BeatsArray와 BPM을 저장하도록 했다. yt-dlp을 기반으로 한 오디오 파일 수집 파이프라인을 실행하니까 유튜브의 IP 기반 요청 제한 정책으로 인해 차단당하는 문제가 발생했다. 
이를 해결하기 위해 서버당 워커 수를 2개로 줄이고 요청 간 간격을 대폭 늘렸으며 세션 쿠키 인증 헤더를 파이프라인에 적용했다.
추가로 속도를 높이기 위해 서버 두 개를 추가로 올려서 RapidAPI를 이용해서 오디오 파일 다운로드 워커도 실행했다. 중간에 실수로 풀링 요청 주기를 너무 짧게 설정하여 API 한도가 금방 소진되는 시행착오도 겪었다. 

타브 채널의 영상들의 박자 정보는 다 저장을 한 후에 해당 videoId들의 동영상 이름을 기반으로 일반적인 아티스트명과 곡명만 Gemini API를 통해서 뽑아내고 중복을 없앤 후 해당 곡 이름, 곡 이름 + backing track, 곡 이름 + tab를 검색해서 상위 몇개의 videoId를 추가로 수집했다. 해당 videoId 중에서 조회수가 3만 이상인 것만 Essentia가 분석해서 BeatsArray와 BPM을 추출해서 DB에 저장했다. 이렇게해서 22000개 정도의 데이터를 미리 받아둘 수 있었다. 

이때 무거운 작업을 병렬로 돌리고 순차대로 처리하고 하는게 머리가 아팠다. 자꾸 깔끔하게 안 되고 중간에 뭔가 문제가 생겼다. 이런걸 나중에 AI를 통해서 자동화가 할 수 있는건가? 어쨋든 서버 띄우는 비용과 Gemini API 비용으로 구글 무료 크레딧은 얼마 남기지 않고 알차게 사용하긴 했다. 


### 5/13 ~ 5/18: 다국어 설정, 로그 설정, 전체적인 ui/ux

Pino를 통해서 로그 공통화를 시키고 푸터, 로고 추가 등 전체적인 ui/ux를 했다. 그리고 다국어를 적용했다. 
다국어 적용을 빨리 하면 절대로 안될 것 같다. 나중에 SEO 작업하면서 다국어 때문에 고생을 많이 했다. 다음에는 다국어를 적용하지 않거나 아예 정말 마지막에 적용하는 것을 고려해볼 것이다. 이것도 서비스의 반응이 터지기 전에 하면 비효율적인 작업인 것을 느꼈다. 
개인정보처리방침, 이용약관도 추가하고 모바일 디자인을 AI로 생성했다. 


### 5/20 ~ 5/22: SEO 

이 기간 동안은 SEO의 지옥이었다. 구글 키워드 플래너에서 적당히 검색이 되는데 경쟁률이 낮은 키워드를 찾아서 사이트 설명글을 만들고 그 모든 글을 다국어 적용해야했다. 원래는 모든 언어별로 키워드를 찾아보고 적용해야하지만, 그건 너무 시간이 많이 들어서 영어랑 한국어만 하고 나머지는 AI한테 맡겼다. 
또한, SEO 점수를 높이기 위해서 robots.txt, 사이트맵, 메타데이터, 캐노니컬 주소, JSON-LD를 추가했다. 키워드 검색 유도를 위해서 내부주소로 BPM이나 박자별로 메트로놈 페이지를 만들어서 루트 경로에 연결시켰다. 
SEO 설정은 딱 정해진게 아니라 할 것도 많고 방법도 많아서 AI의 도움을 받으면서 진행했었다.
