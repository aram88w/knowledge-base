## 개요 및 총평

extractframe은 동영상에서 특정 시간 간격 혹은 장면 전환을 감지하여 이미지를 추출할 수 있고 웹 안에서 이미지 편집까지 가능한 웹 서비스임. 

실제로 배포, 운영까지 하는 웹 서비스는 처음이기에 많은 삽질을 하고 배웠다. 크게 4가지가 남는다.

1. 코드를 작성하기 전에 ==전체적인 구조==는 무조건 정하고 가야함.
   - ==디자인 가이드==: 이미 만들어진 `Vue.js` 프로젝트에 내가 원하는 디자인을 입히는 것은 쉽지 않음. 디자인 시안을 `Stitch` 등과 같은 AI 모델을 통해서 확인한 후 디자인 가이드를 지정한 후, 더미데이터를 넣은 뼈대를 작성한 후에 기능을 개발하는게 편함.
   - ==아키텍처==: 요금이나 지역에 따른 지연, 성능 등을 고려해서 확실한 아키텍처를 정하고 가야지 코드를 작성할때도 편하고 나중에 갈아엎을 일이 없음.
2. 처음 사용하는 기술은 막 사용하면 안됨. AI로 코드를 작성하더라도 3가지는 알고 시켜야함. 이게 결국은 시간을 절약하는 길임.
	   1. 기본 개념
	   2. 디자인 패턴, 실행 흐름
	   3. 트레이드 오프, 단점
3. ==수익 구조==를 생각해야함. 수익 구조가 광고 수익밖에 없다면 서버 비용이 거의 0에 가까워야함. 그게 아니라면 흑자가 나는지를 생각해봐야함.
4. 처음 런칭을 너무 완벽하게 하려고 하지 말고 적정선에서 런칭을 해야함.

이번 프로젝트는 아키텍처만 4번을 바뀌면서 코드 수정에 시간을 너무 많이 들였고 마지막에는 서버없이 브라우저에서 처리가 가능한 것을 알고 현타가 왔음. 약 3달 간 작성한 서버와 파이썬워커가 필요없고 수많은 시행착오를 겪으며 구축했던 클라우드 서버 설정, `Cloud Run` 설정, `Spring Native` 빌드 등이 필요없다니.
지금은 어차피 나중에 경험하고 배워야할 것들을 먼저 했다고 생각하고 있다. 이렇게 된 이유는 내가 하나에 꽂히면 그걸 중심으로 질문을 하고 AI도 그걸 기준으로 대답을 하기 때문인 것 같다. 처음에 `FFmpeg`를 염두에 뒀기 때문에 `FFmpeg`를 돌릴 수 있는 Hetzner의 `CAX31`, `CAX41`, `Cloud Run`과 같은 대답을 들었고 그것만을 고려했다. 다른 시각에서 바라보지를 못했던 것이다.
AI는 이 세상에서 가장 좋은 방안을 바로 던져주지 않는다. 내가 계속 질문을 통해서 찾아야한다. 좋은 방안이라고 생각한 것도 더 좋은 방안이 있는지 이건 안되는지 저건 되는지 등을 계속 물어야한다. 그러다보면 대답에서 다른 방법을 언급할때 있는데 그것에 대해서 캐물어서 장단점을 따져봐야한다. 모델도 바꿔서 교차 검증하는 방법도 괜찮다.
정말 다행인 것은 동영상 검증 코드를 강화하다가 AI한테 `FFmpeg wasm`에 대해 대답을 들었기에 지금처럼 서버 없이 유지비 0원 구조를 만들 수 있었다. 만약 이 일이 없었으면 속도는 더 느리고 아키텍처와 코드는 더 복잡한데 사용자가 많아질수록 Egress 비용이 늘어나는 이상한 구조를 사용중이었을 것이다.


## 내용

처음에는 `FFmpeg`를 사용한다는 생각에 맞춰져 있어서 그걸 기반으로 구조를 설계함. 클라우드 서비스에 대한 개념이 부족해서 파이썬워커를 내장 디스크에서 사용한다는 것을 기준으로 생각했음.

처음 구조
- 프론트에서 동영상을 업로드: 백엔드에서 DB 저장
- 작업 요청: Redis 큐에 작업 내용을 JSON으로 저장, 파이썬워커는 while로 계속 돌아가면서 Redis를 확인함. 작업이 들어오면 작업을 받아서 `FFmpeg`를 실행해서 내장 디스크에 결과 저장, 백엔드에 API 요청을 보내서 DB에 작업 상태 업로드
- 프론트에서는 작업 요청 후 계속 풀링 요청을 보내서 DB를 조회, 완료 상태인 경우에 추출 이미지의 URL을 받아서 화면에 뿌려줌. 그걸 편집해서 다운로드 받을 수 있도록 함.

최종 구조
- 프론트에서 동영상을 업로드하면 브라우저에서 돌아가는 `FFmpeg wasm`를 실행해서 결과 반환 

### 1/5 ~ 1/14: 백엔드 코드 작성 및 `FFmpeg` 명령어 지정

우선 백엔드 코드부터 작성했음. 기반 코드를 작성하는데 2주 정도 걸렸었음. 스프링에서 Redis를 처음 써봤고 응답 구조, DTO 규칙, 공통 예외 처리 같은 틀을 잡는데 시간이 많이 걸렸고 이때까지만 해도 직접 코딩을 해야한다는 생각이 있어서 더 오래 걸렸던 것 같다. 지금은 구조만 내가 짜고 코드 작성은 AI한테 맡긴 후에 AI와 의논하면서 코드를 수정하는 편이다.
아 그리고 FFmpeg 명령어가 이상한 프레임을 추출하는 경우가 많아서 정확한 프레임을 추출하는 명령어를 찾는데 엄청 오래 걸렸다. FFmpeg에 대한 데이터가 부족한 것인지 이때 AI가 이상한 대답을 많이 했다. 이때도 꽤 고생을 했었다.

### 1/14 ~ 1/30: 프론트엔드 프로토타입 작성 후 디자인 적용 

이때 웹 디자인 및 퍼블리싱을 하기 위해서 피그마 강좌와 'Do it! 웹 사이트 기획 입문'을 보고 시작했음. 3일 정도에 끝냈지만 시간 낭비였음. 어차피 피그마를 써서 내가 웹 디자인을 할 일도 없고 '웹 사이트 기획 입문'은 가독성도 떨어지고 현재 내 상황에 거의 도움이 되지 않는 책이었음.

프론트엔드에서 이미지들을 편집하기 위해서 `Canvas API`를 사용하면 된다고 하는데 `Canvas API`를 한번도 사용해본 적이 없어서 어떤식으로 되는건지 머리속에 그려지지 않았음. 그래서 프로토타입으로 기능만 돌아가도록 `Konva API`(내부적으로 `Canvas API`를 사용하는 라이브러리)를 통해서 이미지 편집 기능을 만들었음. 이때, 처음으로 학습하지 않은 외부 라이브러리를 제대로 사용해본 거라서 삽질을 많이 했음. AI한테 코드를 다 만들게 시키고 '이거 왜 안돼', '이게 아니잖아', '해결해줘.' 이렇게 진행했어서 시간이 오래 걸렸음. 그러다가 결국 AI가 끝까지 해결 못하는 문제가 있어서 내가 `Konva API`의 기본 개념을 배우고 코드를 이해해서 해결했음. 이때, AI 시대에 개발자는 어느정도까지 학습을 해야하는지에 대한 궁금증이 생겼음.

프로토타입을 만든 후에는 웹 디자인을 했음. 여러가지 찾아보다가 도저히 피그마로 내가 할 엄두가 안나서 구글에서 제공하는 AI 웹 디자인 툴인 `Stitch`를 사용함. 디자인에 대한 개념이 없다보니 기준도 없이 만들어줘 -> 이거 바꿔줘 -> 이거 바꿔줘. 이런 식으로 시간 낭비를 많이 함. 디자인 가이드(색 조합 3가지, 폰트 사이즈, 테두리 등)을 지정하고 그거에서 벗어나지 않도록 통일감을 주면서 하면 훨씬 보고 좋고 시간도 절약된다는 것을 나중에 알았음. 이것에 대해서는 다음 프로젝트를 하기 전에 어느 정도 기준을 잡고 시작할 예정임.

제일 문제였던 건 프로토타입(`Vue.js`)을 만든 후 웹 디자인(`HTML`, `CSS`, `JS` 파일)을 만들었더니 기능만 있는 프로토타입에 웹 디자인을 넣어야하는데 기존의 디자인을 유지 못하거나 기능이 갑자기 작동을 하지 않거나 하는 이슈가 많았음. 특히 결과 화면을 담당하는 `CaptureResultView` 컴포넌트의 경우, 전체 코드가 `Konva.js`로 되어있었기 때문에 더 적용하기 힘들었음. 두 달이 지난 아직도 그 때 골머리를 썩이던 기억이 남아있음. 다음에는 디자인을 이런 식으로 할 예정임.

>[!info] 디자인 적용 순서 
> 1. 디자인 가이드 정의: 마음에 드는 웹사이트를 캡처하든 검증된 디자인 키트(`shadcn` 등)를 사용하든 `Stitch` 사용하든 해서 웹디자인에 사용할 컬러 3개, 폰트 사이즈 3단계(제목, 본문, 소제목), 테두리 등의 값들을 미리 지정함.
> 2. 레이아웃 구현: Vue에서 전체적인 화면 구조를 디자인 가이드에 맞춰서 작성. 필요하면 가짜 데이터를 채워넣음.
> 3. 기능 주입: 클릭 이벤트, 백엔드 API, 실제 데이터 등 실제 기능을 넣음.
>    - 복잡한 기능을 사용해야하는데 기능이 검증이 필요한 경우에는 프로토타입을 따로 만들어서 검증 후에 옮기는 방식을 써도 됨

### 1/30 ~ 2/6: 사전조사 기능 추가

화면 변화율을 이용해서 추출하는 기능을 이때쯤 추가했음. 원래 타브 동영상에서 타브를 편하게 추출하는 것을 감안하고 만든 것인데 타브가 바뀌는 시간이 일정하지 않은 영상이 많아서 어떻게 할지 생각해보다가 중간에 기능을 넣었던 것이다. 서비스를 만들기 전에 충분한 조사와 구상을 하지 않음. 이번 프로젝트를 하면서 코드를 작성하기 전에 충분한 정보로 최대한 변하지 않게 구상을 해두고 구조를 짜놔야 한다는 것을 여러번 느낌.
scene(화면 변화율)의 값을 받아서 사용자에게 보여줘야하는데 기존 워커로는 처리를 할 수 없어서 `Fast API`를 도입해서 사전조사 명령어를 실행해서 응답을 하도록 했음. `Fast API`를 호출하고 응답을 받을 때 동안 스프링 메인 스레드를 블락 시켜놓을 수 없어서 `Mono`를 사용해서 비동기로 처리했음. `Mono`를 사용할때 JPA 관련 로직은 `.subscribeOn(Schedulers.boundedElastic())`의 스레드를 사용해서 처리하고 외부 API 호출은 `Mono` Netty 스레드가 처리하도록 해야한다는 것을 알게 됨. JPA는 블로킹 I/O 작업이라서 Netty 스레드를 점유하지 않도록 하기 위함임. 

응답으로 받은 데이터는 프론트엔드에서 `Chart.js`를 사용해서 그래프를 표현하도록 했는데 이때도 처음보는 외부 라이브러리에 대해서 어떻게 다뤄야할지 몰라서 그냥 이거 안돼, 왜 안돼, 이거 바꿔줘. 이런 식으로 하느라 시간이 오래걸렸음.
이렇게 나는 기술에 대한 이해가 없이 AI한테 시키고 고치고 할 때 현타가 엄청 옴. 내가 지금 무엇을 하고 있는 것인지, 이런 식의 개발이 과연 내 실력 향상에 도움이 되는지에 대한 생각이 계속 듦. 

### 2/6 ~ 2/10: 로그 공통화, `record` 적용, 예외 공통화

백엔드, 파이썬워커에서 로그 공통화 작업을 했음. 요청이 들어오면 필터에서 `requestId`를 만들어서 `MDC`에 추가해서 로그 앞에 붙이고 `videoId`, `jobId`도 생기면 로그 앞에 붙이도록 해서 백엔드, 파이썬워커 사이에서 데이터의 이동을 쉽게 추적이 가능하게 됐음. 이때 `@MdcLog` 애노테이션을 만들어서 호출되는 메서드에서 `videoId`, `jobId`를 파라미터로 갖고 있으면 자동으로 `MDC`에 추가되도록 AOP를 만들어서 요청을 받는 Controller에 추가했음. MDC에 추가한 값들은 스레드 반환 전에 깨끗하게 비우는 로직을 실행하도록 해야했는데 이것과 `Mono` 로직이 겹치면서 골치 아픈 일이 있었음. `Mono`를 사용하면 설계도만 만든 후 바로 반환한 후에 Netty 스레드에서 해당 설계도로 작업을 처리하는 비동기 작업을 한다. 이때 메인스레드는 설계도를 만든 후 바로 반환하기 때문에 당연히 `MDC`도 비워지고 Netty 스레드부터는 로그에 `requestId`, `videoId`, `jobId` 찍히지 않는다. 그래서 Netty 스레드로 바뀔때 전파가 되도록 하는 설정을 해야하는데 이것도 어떤 상황은 작동하는데 어떤 상황에서는 작동하지 않아서 수동으로 추가해줘야할 때가 있다.

DTO를 `record`로 바꾸는 작업을 했음. `record`가 간편한 것 같아서 앞으로 DTO는 처음부터 `record`를 사용할 것 같음.

백엔드, 파이썬워커에서 검증, 오류 공통화 작업을 했음. 백엔드에서는 에러 응답 객체(HTTP 상태코드, 에러코드 + 에러 메세지)을 정의하고 커스텀 예외가 에러 코드를 담아서 던지도록 해서 공통예외처리 핸들러에서 공통된 에러 응답을 반환하도록 했음. 이때는 그냥 만드는데 급급하느라 천천히 생각을 못 했는데 나중에 다국어를 적용하려니 이 2가지 방식이 고민이 됐음. 

- 백엔드 완성형: 백엔드가 에러코드와 에러메세지(`Accept-Language` 헤더를 통해서 다국어 적용)로 에러 응답을 만들고 프론트엔드로 반환하는 방식
- 프론트엔드 매핑형: 백엔드에서는 에러코드만 갖고 반환하고 프론트엔드에서 에러코드를 기반으로 에러메세지를 매핑해서 (다국어 적용) 보여주는 방식

유지보수 편의성 측면에서 백엔드 완성형 방식(전자)이 더 적합하다고 판단했다.
이를 위해 `ErrorCode`에 에러메세지를 직접 하드코딩으로 넣지 말고 공통예외처리 핸들러(`GlobalExceptionHandler`)에서 에러코드를 기반으로 다국어가 적용된 에러메세지를 응답하도록 설계함. 
커스텀 예외를 던질때 넣는 메세지는 서버 디버깅용으로 로그에 남기도록 하는게 권장된다고 함.

```java
public enum ErrorCode { 
    USER_NOT_FOUND(HttpStatus.NOT_FOUND, "U001", "error.user.not_found"), 
    INVALID_INPUT(HttpStatus.BAD_REQUEST, "C001", "error.common.invalid_input"); 

    private final HttpStatus status; 
    private final String code;        // 프론트엔드가 식별할 고유 에러코드 (예: U001)
    private final String messageKey;  // messages.properties의 다국어 키값 
}
```

이때부터 파이썬워커 코드를 조금씩 개선했는데 파이썬워커가 기본적으로 위와 같은 단계를 밟음.
1. 작업을 `Redis` 큐에서 가져오기
2. 작업 선점 API 요청, 작업 상태를 PROCESSING으로 변환
3. `FFmpeg` 작업 실행
4. 성공 시 성공 API 요청, 작업 상태를 COMPLETEDED로 변환
5. 실패 시 실패 API 요청, 작업 상태를 FAILED로 변환 + 에러코드 저장

여기서 다음과 같은 모든 예외 케이스에 대해서 생각하느라 머리 터질 듯이 고민했다. 
- 네트워크 에러로 API 호출 실패시 재시도 로직
- 실패 시 작업 상태에 대한 처리 (작업 상태를 COMPLETEDED, FAILED로 변환하지 못하면 프론트에서 계속 풀링 요청을 보냄.)

### 2/26 ~ 3/9: 아키텍처 

이제 어느정도 코드가 완성이 되어서 도커에 올려서 클라우드 서비스에 배포하기 위해서 도커 복습을 했음.
`Nginx`(프론트엔드), 백엔드 서버, DB, `Redis`, 파이썬워커(사전조사 `Fast API` 서버 포함)의 아키텍처를 어떤식으로 구성해야 속도를 챙기고 요금을 절약할 수 있을지에 대해서 많이 고민했음.

**_1번 아키텍처 (2/26 ~ 2/27)_**

- ``Oracle A1`` 4코어: 프론트엔드, 백엔드, DB, Redis, scout
- `Cloudflare R2` : 업로드된 동영상, 작업이 완료된 결과 이미지들 저장 (Nginx에서 바로 서빙)
- `Hetzner CAX31` 8코어 : worker

1. 동영상 업로드: 브라우저에서 서버로 업로드 -> 서버에서 R2로 업로드
2. 추출 작업 요청: 작업 DB 저장, `Redis` 큐에 작업 추가, 파이썬워커가 `Redis`에 작업이 들어오면 `R2`에서 동영상을 가져와서 `FFmpeg` 실행, 추출된 이미지는 `/tmp`에 저장했다가 R2로 업로드, 작업 상태 변경
3. 프론트엔드 작업 요청 후 풀링 요청을 보내다가 작업 상태가 COMPLETED면 서버에서 `R2`에 저장된 이미 지 경로를 반환해서 프론트엔드에서 `R2`에서 이미지를 받아서 사용

처음에는 이렇게 하기로 결정함. 기존 코드는 아무생각 없이 동영상 파일을 로컬디스크에서 꺼내고 추출되 이미지는 로컬디스크에 저장하도록 했기 때문에 위의 아키텍처대로 하려면 코드를 수정해야했음. 동영상 파일 위치와 이미지 파일에 대해서 상대경로로 처리하도록 바꿨고 도커 컨테이너로 `MiniO`를 띄워서 백엔드, 파이썬워커가 R2로 연동되도록 수정했음.

그러나 이 아키텍처는 문제가 많았음. 무시할만한 문제가 아니었기에 폐기했음

1. 가격 문제: 처음에 클라우드 비용만 내면 된다고 생각했음. `R2`가 업로드, 다운로드가 무료라길래 그냥 그런줄 알았음. 그런데 서버에서 다운로드 (Ingress) 할때는 비용이 들지 않지만 업로드(Egress) 할때는 추가적인 비용이 든다는 것을 코드 수정 후에 알았음.
   - `Oracle A1`: 서버 비용 무료 + 동영상 Egress 비용
   - `R2`: 서버 비용 거의 무료(하루 지난 파일은 다 삭제함) + Egress, Ingress 비용 무료
   - `Hetzner CAX31`: 서버 비용 2~3만원 + 이미지 파일 Egress 비용
     서버마다 월간 Egress 무료 제공이 있지만 이 구조는 사용자가 늘면 늘수록 적자인 구조였음.
1. 성능 문제: `CAX31`(8코어) 하나가 모든 사용자의 파이썬워커를 책임져야 했음. 동시 사용자가 3명만 되도 3번째 사용자는 20~30초를 기다려야하고 10명만 되어도 병목 현상으로 처리가 불가능할 정도로 지연이 심해졌음. 그리고 `A1` <-> `R2`, `CAX31` <-> `R2` 간에 데이터 이동 때문에 지연 시간도 무시를 할 수 없었음.

**_2번 아키텍처 (3/2 ~ 3/6)_**

- `Hetzner CAX41` 16코어: 프론트엔드, 백엔드, DB, Redis, scout, worker, 파일저장

기존에 로컬디스크를 사용하던 것처럼 그냥 16코어짜리 클라우드 서비스를 사용해서 Egress 비용이 발생하지 않도록 하는 아키텍처 전략이었음. R2를 적용했던 코드를 따로 브랜치로 빼서 저장시키고 main 브랜치에서는 `CAX41`에 모든 걸 올리도록 다시 수정했음. 다 수정을 한 후에 도커파일, Nginx, 도커 컴포즈 파일까지 다 작성하고 도커 데스크탑에 올려서 테스트까지 한 후에 이 아키텍처의 가장 큰 문제를 발견했음. 

- `Hetzner CAX41` 요금제: 월 5만원 정도
- Egress 비용: 추출된 이미지들을 `R2`로 보내서 브라우저에서 `R2`에 접근하든 직접 보내든 결국은 서버에서 업로드하는 Egress 비용이 듦

문제는 수익모델이 없는 이 웹서비스는 광고수익만으로는 사람이 엄청 들어와도 5만원 + @의 수익을 넘어설 수 없었음. 이미 두번이나 아키텍처를 바꿨는데 또 바꿔야해서 허탈했지만 다른 방법을 찾아봤음.

**_3번 아키텍처 (3/9 ~ 3/24)_**

- ``Oracle A1`` 4코어 / `e2-micro` CPU2코어 메모리 1기가: nginx(프론트엔드), 백엔드, DB, Redis
- ``Cloud Run``: 파이썬워커 (min-instances=1에 대해서도 상당한 무료 할당량을 주기도 하니, 한 달 내내 1대를 상시 대기시켜도 0원인 경우가 많음)
- `R2`: 업로드된 동영상, 추출된 이미지 (동영상은 프라이빗 접근, 이미지는 속도를 생각해서 퍼블릭 접근)

1. 동영상 업로드: 사용자가 동영상 업로드 -> 서버(`A1` or `e2`)에서 R2에 업로드 가능한 URL 제공 -> 브라우저에서 `R2`로 업로드
   => 브라우저에서 `R2`로 업로드하는 것이므로 비용 x
2. 작업 요청 (worker):  서버에서 DB 저장 및 ``Cloud Run``으로 작업 요청 (R2 동영상 URL을 넘겨줘야함.) 
   -> ``Cloud Run``에서 worker 실행 (`R2` 동영상 URL로 `FFmpeg` 실행) 및 결과 이미지를 `R2`로 업로드 (비용 발생) 
   -> 서버에서 결과 이미지에 접근 가능한 R2 URL을 반환 
   -> 브라우저에서 R2 URL로 접근해서 이미지 편집 및 다운
3. 사전조사 요청 (scout): 서버에서 ``Cloud Run``으로 작업 요청 (R2 동영상 URL을 넘겨줘야함.) -> ``Cloud Run``에서 scout 실행 및 결과 응답

### 3/9 ~ 3/18: 파이썬워커 Fast API로 통합, 작업을 Mono 비동기 호출로 변경

처음에는 ``Oracle A1``, ``Cloud Run``, `R2`를 사용하기로 결정함. 이 방식은 어차피 요청때만 10초 정도(8코어 기준) 작동하는 파이썬워커를 계속 서버 비용이 들게 하지 않고 요청때마다 구동이 되는 `Cloud Run (GCP)`를 사용했음. 심지어 각 요청마다 `Cloud Run`을 구동 시키므로 8코어를 온전히 사용해서 다른 사람의 작업을 기다릴 필요도 없음.
``Oracle A1``, `e2-micro`는 서버 1대를 무료로 제공 했고 ``Cloud Run``도 us-central1, us-east1, us-west1에서는 Always Free를 제공해서 꽤 넉넉한 사용량을 달마다 줬음. 여기서 발생하는 비용은 ``Cloud Run``에서 `R2`로 이미지를 업로드하는 Egress 비용이었음. 달에 1GB 업로드가 무료였는데 20번을 업로드하면 (50메가 기준) 무료가 끝나고 추가요금은 1GB당 160원, 100GB = 2000번 업로드 = 16000원 이었음.
AI를 통해 웹사이트 통계를 찾아본 결과, 달에 2000명이 이용하는 웹사이트는 아주 잘 되는 경우라고 했고 기존에 서버 비용으로 3만원, 5만원 나가던 것을 생각하면 가격이 괜찮아보였기에 이 아키텍처로 결정을 하고 코드를 다시 수정하기 시작했음.

우선 worker를 워커가 아닌 `Fast API` 서버 형식으로 바꿔서 scout랑 통합을 했고 기존에 작업 요청을 하면 `Redis` 큐로 작업을 추가하고 프론트에서는 풀링, 서버에서는 작업 상태를 확인하던 로직에서 프론트에서 작업을 요청하면 백엔드에서 `Mono`로 ``Cloud Run``을 실행하도록 하고 결과를 바로 받을 수 있도록 했음. 작업 취소는 프론트에서 abort로 HTTP 연결을 끊으면 백엔드에서 신호를 받아서 `Cloud Run`을 중단하도록 하려고 했음.

Redis 큐 관련 코드나 작업 상태를 변경하는 API를 삭제하고 `Cloud Run`을 호출했던 백엔드에서 작업이 응답을 받으면 그때 DB에 작업 상태를 업데이트 하면 됐음. 사용자가 접근 가능한 R2 PresignedURL나 이미지 같은 경우에는 성능을 위해서 R2 PublicURL로 제공하는 등의 R2 관련 로직이 추가됐음.
Mono 문법에 익숙하지 않아서 좀 헤맸고 추출된 이미지를 업로드할 R2 Presigned URL을 몇개나 만들어서 넘길지, 만약 성공했는데 몇개의 이미지가 R2에 업로드 실패한 경우에는 어떻게 할지 등 예외 케이스를 고려해서 코드를 작성했다. 이때 워커에서 발생하는 에러를 처리하는 커스텀 예외를 만들어서 백엔드에서 에러코드에 다국어를 적용해서 넘기도록 바꿈. 워커를 Mono로 바꾸면서 MDC에서 xxxId가 전파가 안 돼서 수동으로 주입해서 헤더에 넣어서 Fast API로 넘기도록 했음.
기존에 `/scout`는 Fast API로 돌리고 `/worker`는 워커로 돌리다가, `/scout`, `/worker`를 Fast API로 통합하니까 파이썬워커 코드는 엄청 간단해졌음.

그런데 문제가 발생함. Mono를 사용했기에 프론트에서 abort 신호를 줘도 백엔드에서 받지를 못했음. 여기서 또다시 코드를 작성하기 전에 확실히 찾아보고 생각해보고 적용해야한다는 것을 느꼈음. 이번 프로젝트에서 한두번 느끼는게 아님.
어쩔 수 없이 다시 취소 API를 만들고 Redis를 만들어서 워커가 작업 중에 Redis에서 상태를 계속 조회해서 취소된 경우에 프로세스를 종료하도록 만듬.
그 후에는 프론트에서 창을 닫았을때 취소 API를 보내거나 작업 중에 페이지 이동이 불가하게 하거나 폰트를 다운로드 해둔다거나 이미지 확대 중에 이동 기능을 추가한다거나 등의 자잘한 코드 개선을 함.

### 3/18 ~ 3/24: 클라우드 서비스, GCP, R2 설정 및 서버 최적화, CI/CD

연동하는 것 빼고는 코드 작성이 완료되어서 `Oracle A1`, `Cloud Run`, `R2`에 실제로 도커를 올리기 시작했음.
먼저 클라우드 서비스 `Oracle A1`을 회원가입하고 무료 서버를 받으려고 했음. 서버, `Cloud Run`, `R2` 간의 지연을 최소화 하기 위해서 리전 선택을 신중히 했음. `Cloud Run`의 Always Free를 사용할 수 있는 지역을 기준으로 잡고 `Oracle A1`의 지역은 기타 사용자가 많은 지역에서 가까운 리전인 chicago-1로 결정, `R2`는 전역에 퍼져있어서 auto로 하면 첫 요청을 기준으로 자동으로 가까운 지역을 선택해준다고 해서 힌트만 설정해둠.
그런데 `Oracle A1`의 가장 큰 문제가 무료 서버가 성능이 너무 좋아서 자리가 없었음. 찾아보니까 현실적으로 상시 할당받기가 매우 어렵다는 것을 확인해서 다른 방안을 찾아보다가 구글의 `e2-micro` 무료 서버를 사용하는게 낫겠다는 생각을 했음.

이때쯤 구글 클라우드에서 무료 크레딧을 받은 것을 사용하기 위해서 구글 콘솔에서 구글 AI Studio와 Vertex API를 연동해서 VSCode + Roo Code에서 호출하는 형태로 AI를 사용하도록 바꿨었다. 이 과정에서도 안되는게 많아서 많이 골치아팠던 기억이 있지만 구글 콘솔에 익숙해져서 `e2-micro`를 설정하는 것은 무난하게 진행되었음. `A1`, `e2-micro`를 설정하면서 느꼈던 것은 내가 클라우드 서비스나 네트워크 관련 지식이 부족하는 것이었음. 군대에서 CS 서적을 읽었기에 네트워크 기본 개념은 있었지만 오래되기도 했고 갑자기 DNS 레코딩, 공용 IPv4, 공용 서블릿 같은 개념이 나왔을때 이게 클라우드 개념에서 어떻게 작용하는 것인지 이해를 하기 힘들었음. 아마 클라우드 서비스에서 사용되는 네트워크 개념이 부족한 것 같다.
아무튼 `e2-micro`를 설정했는데 문제는 `e2-micro`는 CPU 2코어, 메모리 1기가의 스펙이었음. 메모리 1기가에 우분투, Nginx, 스프링 서버, DB, Redis를 그냥 올려서 운영하기에는 리소스가 너무 빠듯했음. 그래서 메모리 최적화를 진행함.

- `e2-micro`의 swap 메모리 설정으로 메모리가 부족한 경우 디스크에서 2GB를 메모리처럼 사용하도록 함
- 백엔드 서버를 `Spring Native`로 빌드해서 올리기. (메모리 100MB 정도로 줄어듬)
- MySQL 최적화 (150~200MB로 줄어듬)
  1.  performance_schema = off
  2.  innodb_buffer_pool_size = 64M
  3.  max_connections = 50
- 기본 OS 우분투 (150MB)
- Nginx (20MB)
- Redis (20MB)
- Dozzle (30MB), `Cloudflared` (40MB)

GitHub Actions를 통해서 git push를 하면 깃허브 서버에서 빌드가 되고 `e2-micro`에서 빌드된 이미지가 저장된 GHCR에 접근해서 docker pull 해당 이미지, docker compose up -d 해당 이미지를 실행해서 프론트엔드와 백엔드가 자동 배포가 되도록 했음. (CI/CD)
`Spring Native`로 빌드를 하기 위해서 몇가지를 수정하고 힌트를 줘야했는데 직접 빌드를 하다가 발생하는 에러메세지를 확인하고 코드를 수정해야해서 엄청 귀찮았음. 처음에는 git push를 하고 빌드를 기다리고 에러가 발생하면 그걸 확인했는데 GitHub Actions를 통해서 하는 빌드가 거의 15분 정도로 오래 걸려서 나중에서는 로컬에서 Native 빌드 하는 방법으로 해서 빌드까지 5분 정도로 단축시켰음.
그래도 오래 걸렸고 특히 `Spring Native`의 컴파일 과정에서 발생하는 에러를 직관적으로 파악하기 어려워서 에러 로그를 읽고 수정하고 다시 돌려보는 과정의 연속이었음. 
Native 빌드 중에 가장 크게 문제가 됐던 것은 `Mono`와 관련된 설정들이었음. 수많은 시도 끝에 겨우 빌드를 성공시키긴 했지만, `Spring Native`가 제공하는 메모리 절감 이점과 빌드 복잡도와 높은 디버깅 비용이 트레이드오프라는 것을 느낌.

`e2-micro`에서 도커로 올린 Nginx, Spring Native, MySQL, Redis가 동작하는 걸 확인한 후에는 `Cloud Run`에 파이썬워커 Fast API를 올리는 작업을 했음. 깃허브 리포지토리를 연동해놓기만 하면 구글 클라우드가 push를 감지해서 자동으로 빌드하고 `Cloud Run`에 올리기 때문에 너무 간단했음.

`Cloudflare R2`도 버킷을 동영상, 이미지 두 개로 만들고 동영상은 Private, 이미지는 Public로 설정해둠.
`Cloudflare`에서 도메인을 구매하고 `Cloudflare Tunnel`을 설정해서 도메인을 연결, `docker-compose.yml`에 `cloudflared` 컨테이너를 둬서 모든 요청이 `Cloudflare Tunnel`을 거쳐서 오도록 설정을 함. 기본 extractframe.org 도메인은 Nginx 컨테이너(http://capture-frontend:80)로 연결하고 dozzle.extractframe.org는 Dozzle 컨테이너(http://dozzle:8080)으로 연결했음. Dozzle 경로에는 이메일 인증을 받도록 엑세스 제어 프로그램에 등록함. `Cloudflare`을 사용하니 HTTPS, 도메인 설정을 자동을 해줘서 아주 편했다.

브라우저에서 R2 PresignedURL로 직접 업로드하는 방식을 해봤는데 너무 느렸음. `e2`, `Cloud Run`, `R2`를 us-central1 지역에 몰아뒀기 때문에 한국에서 R2로 업로드하는 지연시간이 컸음. 그래서 멀티파트 업로드 방식을 적용함.
R2에서 제공하는 멀티파트 업로드 방식을 이용해서 R2 PresignedURL을 필요한 개수만큼 발급 받아서 브라우저에서 동시에 업로드하고 완료 API 보내서 업로드된 동영상을 R2에서 합치도록 했음.

원래 단일 업로드 방식일때는 이런 방식으로 악의적인 파일 업로드를 방지했으나 멀티파트 방식에서는 악의적인 사용자가 PresignedURL을 가로채서 다른 파일을 업로드할 수 있기 때문에 로직이 복잡해짐.

- 기존 로직
  1.  프론트에서 동영상 파일 1차 검증 (확장자, 크기, 파일의 앞부분만 읽어서 동영상인지 판단 등)
  2.  백엔드에서 동영상 파일 2차 검증
  3.  R2 PresignedURL을 발급 받을때 contentLength 설정을 해서 업로드 요청한 파일의 크기와 정확히 일치하도록 강제함

- 멀티파트 방식에서 파일 검증
  1.  프론트에서 동영상 파일 1차 검증
  2.  백엔드에서 동영상 파일 2차 검증
  3.  각각의 PresignedURL은 contentLength로 10MB로 강제(마지막 청크면 계산해서 지정)
  4.  업로드 완료 API에서 합쳐진 파일 크기가 처음에 요청한 동영상 크기와 같은지 확인

### 3/24 ~ 3/31: 브라우저에서 추출 처리하는 아키텍처로 변경

모든 설정을 하고 이제 마지막으로 악의적인 파일을 업로드하지 못하도록 검증을 강화하고 있었음. 완벽한 검증을 위해서는 백엔드에서 `FFmpeg`를 실행하든지 프론트에서 브라우저용 `FFmpeg`인 `FFmpeg wasm`을 사용해야한다고 했음.
이걸 듣고 나니까 문득 추출 작업도 `FFmpeg wasm`를 사용하면 `Cloud Run`에서 `FFmpeg를` 실행해서 R2에 업로드하고 그걸 브라우저에서 접근하는 구조가 아니라 브라우저에서 처리하고 브라우저에서 바로 접근하면 돈도 안들고 속도도 빠를 것이라는 생각이 들었음.

**_4번 아키텍처 (3/24 ~ 3/31)_**

- 브라우저에서 추출 작업 처리 (서버리스)

프론트엔드에서 API 요청 로직을 전부 없애고 `extractor.js`에서 `Web Codecs` (디코더), `web-demuxer`(디먹서), `Konva.js`(이미지 그리기)를 사용해서 처리하도록 했음. (처음에는 프레임 추출 작업은 `video.currentTime`을 이용한 Seek 방식을 사용했는데 너무 렉이 걸려서 `WebCodecs`로 처리)

크롬에서는 빠릿빠릿하게 돌아갔는데 사파리에서 해보니까 너무 느리고 버벅였음. 문제는 `extractor.js`에서 디먹서, 디코더, 캔버스 작업을 브라우저 메인스레드가 하면서 느려지는 거였음. `worker.js`를 만들어서 작업을 메인스레드가 아닌 브라우저의 워커들이 처리하도록 해서 메인스레드에 영향이 받지 않도록 했음. 크롬은 역시나 잘 돌아갔는데 사파리는 자꾸 이상한 버그가 터짐. 또 외부 라이브러리를 사용하는 `extractor.js`, `worker.js`의 코드를 이해하지않고 코드를 작성하다가 버그가 해결이 안되어서 코드 흐름을 이해한 다음에 해결했음.
기본적으로 사파리는 워커가 다른 워커를 호출하려고 할때 보안상 문제로 막는 구조였음. 내 코드에서는 메인스레드에서 워커로 작업을 넘겼는데 디먹서가 자체적으로 내부워커를 호출하려고 하니 발생하는 문제였음. 그래서 디먹서는 메인스레드(`extractor.js`)에서 처리하고 디코더랑 캔버스 작업만 워커(`worker.js`)로 넘겨서 처리함.
작업 취소 로직은 처음에는 onProgress를 넘겨서 abort 되면 워커에서 onProgress를 반복 확인하다가 `new Error('CANCELED')`를 던지도록 했고 이후에는 signal을 넘겨서 signal을 체크해서 `new Error('CANCELED')`를 던지도록 함.

구글 검색을 할때 나오는 title, content도 추가하고 다른 언어로 검색해도 내 웹사이트가 나오도록 다국어 URL 라우팅 설정을 했음. 예외 케이스가 좀 있어서 은근 생각할 것들이 많았음.

사파리에서는 초반 이미지가 보이지 않다거나 세로 영상이 회전이 적용이 안되어서 추출된다거나 crop 지정을 하면 비율이 이상해진다거나하는 버그가 있어서 시간을 좀 썼음. 나중에 처음 배포 할때는 크롬을 기준으로 완성 시키고 이후에 반응을 보고 확장하는게 나은 것 같음.

모바일일때 디자인도 수정을 한 후에 사소한 버그나 기능 추가를 한 후에 `Cloudflare Pages`에 배포를 마쳤다.
