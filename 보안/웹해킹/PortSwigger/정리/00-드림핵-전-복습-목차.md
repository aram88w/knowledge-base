# 드림핵 시작 전 PortSwigger 복습

3주간의 공백 뒤에 개념과 문제 풀이 흐름을 다시 떠올리기 위한 정리본. 원본의 서버 측 15개, 클라이언트 측 6개 노트를 바탕으로 재구성했다. 원본의 모든 페이로드를 옮기는 대신 **원리 → 성립 조건 → 공격 흐름 → 대표 예시 → 혼동 지점**을 연결했다.

> [!info] 읽는 기준
> 예시는 학습용 취약 환경을 전제로 한다. 코드 조각은 삽입 위치의 문법, 데이터 형식, 인코딩에 맞춰 사용해야 한다. 원본만으로 확정할 수 없는 내용은 각 장의 **확인 필요**와 [[03-원본-확인-필요-목록]]에 표시했다. 외부 문서나 실제 실행으로 검증한 정오표는 아니다.

## 읽는 순서

1. 아래 공통 개념을 읽고 HTTP 요청이 어디서 어떻게 처리되는지 떠올린다.
2. [[01-서버-측-복습]]을 읽으며 각 공격이 서버의 어떤 처리 과정에 개입하는지 설명해 본다.
3. [[02-클라이언트-측-복습]]을 읽으며 요청 전송·쿠키 전송·응답 읽기를 구별한다.
4. 예시를 가리고 원리와 다음 확인 단계를 말해 본다. 막히는 부분만 원본으로 돌아간다.

## 공통 개념부터 복구하기

### 데이터가 명령이 되는 경계

```text
사용자 입력
  → 브라우저/프록시의 인코딩·디코딩
  → 애플리케이션의 검증·문자열 조립
  → SQL / 셸 / XML / 내부 URL / HTML / JavaScript 해석
  → 결과·오류·시간·외부 통신·상태 변화
```

대부분의 주입 취약점은 **데이터로만 취급해야 할 입력이 다른 해석기의 문법이 되는 순간** 발생한다. 페이로드를 외우기 전에 다음을 묻는다.

- 입력이 어디에서 들어오는가? 쿼리, 본문, 쿠키, 헤더, 업로드 파일, 웹소켓 메시지인가?
- 누가 해석하는가? DB, 셸, XML 파서, 내부 HTTP 클라이언트, 브라우저인가?
- 어느 문맥에 들어가는가? 문자열, 객체, URL, 속성, 스크립트인가?
- 어떤 신호로 성공을 판단하는가? 응답 내용, 오류, 지연, OAST, 실제 저장 상태인가?

### 인증·세션·접근 제어

| 개념      | 질문                         | 실패 예시                   |
| ------- | -------------------------- | ----------------------- |
| 인증      | 누구인가?                      | 비밀번호·MFA 검증 우회          |
| 세션 관리   | 이후 요청을 누구의 요청으로 연결하는가?     | 예측 가능한 로그인 유지 토큰        |
| 접근 제어   | 이 사용자가 이 대상에 이 작업을 해도 되는가? | 다른 사람의 계정 조회, 관리자 기능 실행 |
| 비즈니스 로직 | 현재 상태에서 이 작업과 값이 타당한가?     | 결제 생략, 음수 수량, 쿠폰 중복 적용  |

로그인 여부만 확인해도 다른 사람의 데이터에 접근하는 문제가 남을 수 있다. 반대로 화면에 메뉴가 없어도 서버가 요청을 허용할 수 있다.

### 인코딩·해시·암호화

| 개념 | 목적 | 복습 포인트 |
|---|---|---|
| URL 인코딩 | URL 구성 요소를 전송 가능한 형태로 표현 | `%26`이 어느 단계에서 `&`로 바뀌는지 추적 |
| HTML/XML 엔티티 | 마크업 안에서 문자를 표현 | 해당 파서와 문맥에서만 디코딩됨 |
| Base64 | 바이트를 텍스트로 표현 | 암호화가 아니며 디코딩 가능 |
| 해시 | 입력의 요약값 계산 | 복호화 대신 후보를 해시해 비교 |
| 암호화 | 키로 기밀성을 제공 | 암호문 보유만으로 위조 가능하다고 단정하지 않기 |

**인코딩은 보안 검증을 대신하지 않는다.** 한 단계에서는 단순 문자열이던 `%2523`이 여러 디코딩 단계를 거치며 `%23`, `#`으로 바뀔 수 있다. 반대로 수신 측에서 디코딩하지 않으면 끝까지 일반 문자열이다.

### 브라우저의 세 가지 질문

1. **요청을 보낼 수 있는가?** HTML 폼·리소스 로드·fetch는 전송 제약이 서로 다르다.
2. **인증 쿠키가 붙는가?** 쿠키의 Domain, Path, Secure, SameSite, 브라우저 정책과 fetch의 credentials 등을 확인한다.
3. **JavaScript가 응답을 읽을 수 있는가?** SOP와 CORS를 확인한다.

CSRF는 주로 1·2번, CORS 설정 취약점은 주로 3번의 문제가 핵심이다. XSS는 대상 출처 안에서 코드를 실행시켜 피해자가 접근할 수 있는 데이터와 기능을 악용한다.

| 비교 | 기준 | 예시 |
|---|---|---|
| Origin | 스킴 + 호스트 + 유효 포트 | `https://app.example.com`과 `https://api.example.com`은 다름 |
| Site | 스킴 + 등록 가능 도메인(eTLD+1) | 위 두 주소는 같은 사이트일 수 있음 |

같은 사이트의 다른 출처를 이용하면 SameSite와 SOP/CORS가 서로 다른 판단을 한다는 점을 기억한다.

## 막혔을 때 돌아갈 질문

- 입력이 반사된다는 것과 코드로 실행된다는 것은 어떻게 다른가?
- 결과가 안 보이면 참·거짓 응답, 오류, 지연, OAST 중 무엇을 관찰할 수 있는가?
- 요청이 성공한 것처럼 보여도 실제 데이터가 바뀌었는가?
- 서버가 내부 API를 호출하는가, 브라우저가 다른 출처로 요청하는가?
- 우회가 되는 이유가 검증 누락인가, 파서 차이인가, 처리 순서인가, 타이밍인가?

드림핵 문제 풀이 방식은 기존 [[보안/가이드라인|문제풀이 마인드셋]]과 연결하면 된다. 먼저 스스로 탐색하고, 막힌 개념을 복습본에서 찾고, 상세 구문이 필요할 때 원본으로 돌아간다.
