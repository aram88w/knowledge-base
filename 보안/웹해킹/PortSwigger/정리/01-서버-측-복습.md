[[00-드림핵-전-복습-목차|목차]] · [[02-클라이언트-측-복습|클라이언트 측]] 

## 01 SQL 인젝션

원본: [[보안/웹해킹/PortSwigger/Server-side/01-SQL-인젝션]]

### 발생 원리와 조건

사용자 입력을 SQL 문자열에 이어 붙이면 입력이 값의 경계를 넘어 SQL 문법으로 해석될 수 있다. URL뿐 아니라 쿠키의 TrackingId, XML 본문의 값 등 **DB 조회에 사용되는 모든 입력**이 후보이다.

```sql
-- 취약한 쿼리의 예
SELECT * FROM users WHERE username = '입력' AND password = '입력';
-- username에 administrator'-- 를 넣는 환경의 예
SELECT * FROM users WHERE username = 'administrator'--' AND password = '...';
```

주석으로 비밀번호 조건을 제거하는 예이다. 실제 성립 여부는 문자열 경계, DBMS 주석 문법, 로그인 처리 방식에 달려 있다.

### 공격 흐름과 방법

1. 정상 요청을 기록하고 `'`, `''` 등을 넣어 오류·응답 변화를 비교한다. 차이만으로 SQLi를 확정하지 않는다.
2. 참/거짓 조건을 짝으로 넣어 SQL 표현식이 실제 동작에 영향을 주는지 본다.
3. 결과가 화면에 나오면 UNION, 나오지 않으면 블라인드·오류·시간·OAST 경로를 검토한다.
4. DBMS와 쿼리 문맥을 구분하고 필요한 테이블·컬럼을 찾는다.
5. 최종적으로 원하는 값이나 조건을 실제로 관찰했는지 확인한다.

| 기법 | 대표 구문/관찰 | 성립 조건 |
|---|---|---|
| UNION | `' UNION SELECT NULL,NULL--` | 원래 SELECT와 컬럼 수 및 자료형이 호환됨 |
| 컬럼 수 확인 | `' ORDER BY 1--`, `2`, `3`… | 번호 초과 시 관찰 가능한 차이가 생김 |
| 문자열 출력 위치 | `' UNION SELECT 'a',NULL--` | 해당 위치가 문자열을 수용하고 응답에 노출됨 |
| 조건부 응답 | `' AND '1'='1` / `' AND '1'='2` | 참/거짓에 따라 내용이 다름 |
| 조건부 오류 | `CASE WHEN 조건 THEN 오류 ELSE 정상값 END` | 조건별 오류가 응답으로 구분됨 |
| 오류 기반 추출 | `CAST((SELECT …) AS int)` | 오류 메시지에 변환 대상 값이 노출됨 |
| 시간 기반 | 조건이 참일 때 `pg_sleep(5)` 등 | DB 지연이 HTTP 응답 시간에 반영됨 |
| OAST | DB 기능으로 고유한 외부 도메인 조회 | 해당 기능·권한·외부 통신 경로가 있음 |

### 대표 예시: 블라인드로 비밀번호 추론

`LENGTH((SELECT password FROM users WHERE username='administrator')) > 10` 같은 조건으로 길이를 좁힌다. 이후 `SUBSTR`/`SUBSTRING`으로 각 문자를 검사한다. 핵심은 **비밀번호 자체를 반환받지 않고 질문의 참/거짓을 반복 관찰한다**는 것이다. 함수명·인덱스·문자 비교 규칙은 DBMS별로 확인한다.

### DBMS 차이와 우회

- 버전 조회: MySQL `@@version`, PostgreSQL `version()`, Oracle `v$version`.
- 메타데이터: 다수 DB는 `information_schema.tables`와 `columns`, Oracle은 `all_tables`, `all_tab_columns`.
- 문자열 연결: Oracle/PostgreSQL `||`, SQL Server `+`, MySQL `CONCAT()`.
- Oracle UNION 예제는 `FROM dual`을 사용하는 형태로 원본에 정리되어 있다.
- MySQL의 `--` 주석에는 뒤 공백 등이 필요하다. URL의 `#`는 그대로 보내면 fragment가 되므로 전달 방식도 고려한다.
- XML 입력의 `&#x53;ELECT`는 XML 파서가 `SELECT`로 복원하지만 앞단 필터는 다르게 보는 환경의 우회 예이다. XML을 사용한다고 자동으로 SQLi가 되는 것은 아니다.

### 헷갈리기 쉬운 개념과 확인 필요

- **블라인드 = 공격 불가가 아니다.** 직접 결과가 없다는 뜻이다. 응답 차이·오류·지연·외부 통신이 단서가 된다.
- OAST 도메인의 DNS 조회 확인과 데이터 추출 성공은 다르다. DB별 외부 통신 기능은 권한·OS·패치에 의존한다.
- 원본의 일부 `CASE … ELSE 'a' AND FROM …` 예시는 문법이 불완전하다. 그대로 재사용하지 말고 같은 절의 Oracle 예시와 실제 쿼리 문맥을 확인한다.
- 문자 대소 비교 순서와 세미콜론 다중 쿼리 지원은 DB 정렬 규칙·드라이버 설정에 따라 달라진다.

## 02 인증 취약점

원본: [[보안/웹해킹/PortSwigger/Server-side/02-인증취약점]]

### 발생 원리와 조건

사용자 존재 여부가 새어 나오거나, 반복 시도를 제한하지 않거나, 인증 단계와 사용자를 올바르게 연결하지 않을 때 발생한다. 로그인뿐 아니라 MFA, 로그인 유지 쿠키, 비밀번호 재설정도 인증 표면이다.

### 공격 흐름과 방법

1. 로그인 실패 시 상태 코드·메시지·시간을 비교하여 사용자 열거 가능성을 본다.
2. 차단 기준이 IP, 계정, 세션 중 무엇인지 살핀다. 성공 시 실패 횟수가 초기화되는지도 비교한다.
3. MFA 전후에 동일한 보호 자원을 요청해 중간 상태가 차단되는지 확인한다.
4. 로그인 유지 토큰의 인코딩·해시·서명 여부와 사용자 결합 방식을 분석한다.
5. 재설정 URL을 만들 때 Host 계열 입력을 신뢰하는지 확인한다.

| 공격 방법 | 원본의 예 | 필요한 결함 |
|---|---|---|
| 사용자 열거 | 존재하는 계정만 다른 오류 또는 긴 처리 시간 | 응답 차이의 반복 재현 |
| 브루트포스 제한 우회 | 내 계정 로그인 성공을 실패 시도 사이에 삽입 | 성공하면 공통 차단 카운터를 초기화 |
| IP 헤더 조작 | `X-Forwarded-For` 변경 | 신뢰하지 않아야 할 헤더를 차단 기준으로 사용 |
| 패스워드 스프레이 | 여러 계정에 소수의 흔한 비밀번호 | 계정별 제한만으로 충분히 막지 못함 |
| MFA 대상 변경 | 1차 인증 후 사용자 식별 쿠키 변경 | MFA 대상과 1차 인증 사용자 결합 누락 |
| MFA 시도 체인 | 로그인→MFA 페이지→코드 제출 반복 | 재인증 이후에도 코드 추측 가능 |
| 재설정 링크 오염 | `X-Forwarded-Host`에 학습용 수신 서버 지정 | 링크의 도메인을 외부 헤더로 조립 |

### 대표 예시: MFA 요청 체인

`GET /login`으로 세션·CSRF를 받고 → `POST /login` → 새 세션으로 `GET /login2` → 그 단계의 CSRF와 코드로 `POST /login2`를 보낸다. 매크로나 Turbo Intruder는 이 상태 연결을 자동화한다. **이전 단계의 토큰을 그대로 쓰면 실패한 코드 때문인지 만료된 세션 때문인지 구분하지 못한다.**

### 헷갈리기 쉬운 개념과 확인 필요

- 비밀번호+PIN처럼 지식 요소 두 개를 확인하는 것과 서로 다른 요소의 MFA는 다르다.
- Basic 인증은 일반적으로 클라이언트가 `username:password`를 Base64로 표현해 Authorization 헤더에 보낸다. Base64는 비밀번호를 보호하는 암호화가 아니다.
- 해시를 알아도 복호화할 수 있는 것은 아니다. 후보 비밀번호를 해시해 비교하는 과정과 구별한다.
- 배열 비밀번호 처리, 세션·CSRF의 일회성, 자동 로그인 토큰 형식은 랩별 구현이다. 모든 PHP·ORM에 적용된다고 외우지 않는다.
- 원본 Turbo Intruder 코드는 생략된 헤더와 랩 주소가 있는 학습 기록이다. 완성된 범용 매크로로 취급하지 않는다.

## 03 경로 탐색

원본: [[보안/웹해킹/PortSwigger/Server-side/03-경로탐색]]

### 발생 원리와 조건

파일 경로를 사용자 입력으로 만들 때 허용 디렉토리 밖으로 이탈할 수 있는 문제이다. 다운로드, 이미지 조회, 템플릿·언어팩 로딩, 업로드 파일명 등을 살핀다. 읽기 취약점이 곧 코드 실행을 뜻하지는 않는다.

### 공격 흐름과 방법

1. `filename=photo.png` 같은 입력이 실제 파일 선택에 쓰이는지 확인한다.
2. `../`로 상위 디렉토리 이동을 시도한다.
3. 막히면 검증·디코딩·경로 결합 순서를 추론해 변형을 비교한다.
4. 응답에 나온 내용이 요청한 파일인지 확인한다.

| 방법 | 예시 | 필요한 조건 |
|---|---|---|
| 상대 경로 이탈 | `../../../etc/passwd` | 상위 이동이 제한되지 않음 |
| 절대 경로 | `/etc/passwd` | 사용 중인 결합 API가 절대 입력을 허용하거나 기준 경로를 무시함 |
| 일회성 제거 우회 | `....//` → `../` | `../`를 한 번만 제거 |
| 접두사 검사 우회 | `/var/www/images/../../../etc/passwd` | 정규화 전 문자열 접두사만 검사 |
| 디코딩 차이 | `%2e%2e%2f`, `%252e%252e%252f` | 필터와 파일 접근 시 해석이 다름 |
| 오래된 확장자 검사 우회 | `../../../etc/passwd%00.png` | 널 바이트에서 잘리는 취약한 구형 처리 경로 |

### 헷갈리기 쉬운 개념과 확인 필요

URL 경로 이탈과 서버 파일시스템 경로 이탈은 서로 다른 층위이다. `%00`, 과거 비표준 UTF-8, 절대 경로 결합 동작은 언어·API·버전마다 다르다. **정규화된 최종 경로가 허용 디렉토리 내부인지 안전하게 검사하는 경우**와 단순 문자열 startsWith 검사를 구별한다. 원본의 “정규화하면 공격 불가”는 구현 전체를 보지 않고 단정할 수 없다.

## 04 OS 명령어 주입

원본: [[보안/웹해킹/PortSwigger/Server-side/04-OS-명령어주입]]

### 발생 원리와 조건

사용자 입력으로 셸 명령 문자열을 조립하면 셸 메타문자가 명령 경계를 바꿀 수 있다. 재고 확인처럼 외부 스크립트를 호출하는 기능이 원본 예시다. 레거시에만 한정되는 취약점은 아니다.

```text
정상: stockreport.pl 381 29
취약한 조립 예: productID = & echo hello &
결과: stockreport.pl & echo hello & 29
```

### 공격 흐름과 방법

1. 외부 프로그램 호출이 의심되는 입력을 찾고 정상 출력을 기록한다.
2. 셸·OS 문맥에 맞는 구분자로 `echo`나 `whoami` 같은 결과를 관찰한다.
3. 출력이 없으면 지연, 파일 리다이렉션, OAST 등 관찰 경로를 선택한다.

- **직접 출력:** 주입 명령의 stdout이 응답에 포함되는지 본다.
- **시간 지연:** Unix 계열의 `sleep 5`처럼 해당 OS에 맞는 명령을 사용하고 반복 비교한다.
- **출력 파일:** 쓸 수 있고 웹으로 읽을 수 있는 경로가 있다면 `whoami > …` 결과를 조회한다.
- **OAST:** 외부 도메인 조회를 유도한다. 명령 결과를 도메인에 넣는 예시는 문자열이 DNS 이름에 적합한지도 고려한다.

| 셸 구문 | Unix 계열에서의 의미 |
|---|---|
| `;` | 앞 명령 종료 후 다음 명령 |
| `&` | 앞 명령을 백그라운드에서 실행 |
| `|` | 앞 출력을 다음 입력으로 전달 |
| `&&` / `||` | 앞 명령 성공 / 실패 시 다음 실행 |
| `$()` / 백틱 | 명령 치환 |

### 헷갈리기 쉬운 개념과 확인 필요

SQLi는 DB 해석기, OS 주입은 셸 해석기에 개입한다. 한쪽 문법이 다른 쪽에 그대로 통하지 않는다. `ping -c`는 모든 OS에서 같은 옵션이 아니며 `nslookup`도 설치·권한·네트워크 정책에 따라 사용 불가할 수 있다. **외부 조회가 안 보인다고 명령 주입이 없다고 확정하지 않는다.**

## 05 비즈니스 로직 취약점

원본: [[보안/웹해킹/PortSwigger/Server-side/05-비즈니스-로직-취약점]]

### 발생 원리와 조건

서비스가 “사용자는 UI 순서와 정상 범위의 값만 사용한다”고 가정하면 서버의 업무 규칙을 우회할 수 있다. 특별한 주입 문법 없이 정상 엔드포인트와 값의 조합만으로도 발생한다.

### 공격 흐름과 방법

1. 정상 업무 흐름을 요청 단위로 적는다. 각 단계의 가격·수량·계정·권한·상태를 추적한다.
2. **값 변경:** 음수·0·큰 수·긴 문자열·다른 사용자명을 하나씩 시험한다.
3. **파라미터 제거:** 빈 값과 키 자체 삭제를 구분해 비교한다.
4. **순서 변경:** 건너뛰기, 반복, 역순으로 실행한다.
5. 실제 잔액·주문·계정 상태가 의도한 규칙을 어겼는지 확인한다.

### 대표 예시와 공격 방법

- `current_password`가 있을 때만 검증하는 구현이라면 키를 제거해 검증 없는 경로로 들어갈 수 있다. 실제 그런 코드인지 요청 비교로 확인해야 한다.
- 결제 검증 다음에 나오는 완료 URL이 직접 주문을 확정한다면 완료 단계만 호출해 본다.
- 쿠폰 A/B 교차 적용, 할인된 기프트카드의 재충전 등으로 이익이 순환하는지 본다.
- 이메일 검증기가 `@company.com` 포함 여부만 보고 발송기는 실제 도메인을 다르게 해석하면 소속 확인이 어긋날 수 있다. 원본의 `"admin@company.com"@hacker.com`이 개념 예시다.
- 암호화 오라클에서는 공격자가 정한 평문을 암호화해 주는 기능과 인증 토큰 처리 기능이 결합될 수 있다. 재사용 가능성은 모드·형식·무결성 검증에 달려 있다.

### 헷갈리기 쉬운 개념과 확인 필요

업무 규칙 위반은 응답 200만으로 입증되지 않는다. 저장 결과를 확인한다. 정수 오버플로우·문자열 잘림·이메일 특수 형식 허용은 기술 스택에 의존한다. 원본의 **암호화 오라클에서 더미 없이 32개를 잘랐을 때 실패한 이유**는 해결되지 않은 질문이다. 암호문·IV·모드·패딩·절단 단위를 확인하기 전 원인을 단정하지 않는다.

## 06 정보 노출

원본: [[보안/웹해킹/PortSwigger/Server-side/06-정보-노출-취약점]]

### 발생 원리와 조건

민감한 사용자 데이터, 내부 경로·버전, 소스·설정·인증 정보 등이 의도하지 않은 사용자에게 노출된다. 노출 자체의 영향과 다른 공격을 가능하게 하는 단서를 함께 평가한다.

### 공격 흐름과 방법

1. HTML/JS·주석·응답 헤더·오류·공개 파일을 살핀다.
2. 발견한 경로·파일명·파라미터를 따라 연관된 노출을 찾는다.
3. 노출된 정보가 실제 비밀인지, 권한 없는 데이터인지 확인한다.

| 표면 | 대표 확인 내용 |
|---|---|
| `robots.txt`, `sitemap.xml` | 숨겨진 경로의 단서. 접근 제어 기능은 아님 |
| 디렉토리 리스팅 | 목록 제공이 켜진 디렉토리의 파일·백업 |
| HTML 주석·JS | 내부 API 경로, 개발 메모 |
| 오류·디버그 페이지 | DBMS·프레임워크·내부 경로·키·세션 상태 |
| 백업 파일 | `.bak`, `~` 등으로 남은 서버 소스 |
| 사용자별 API | 다른 ID로 요청했을 때 민감 데이터 반환 |
| TRACE | 프록시가 추가한 정보를 반사하는 구성인지 |
| 노출된 `.git` | 버전 기록에 남은 과거 소스·비밀 |

### 헷갈리기 쉬운 개념과 확인 필요

`index.html`이 없다고 자동으로 목록이 보이는 것은 아니다. 리스팅 설정이 필요하다. `.git`의 한 경로가 보인다고 전체 저장소를 복구할 수 있다고 단정하지 않는다. 디버그 화면에 `is_admin`이 보여도 **서버가 그 필드를 외부 입력으로 받아 신뢰하는 별도 결함**이 있어야 권한 조작으로 이어진다.

## 07 접근 제어

원본: [[보안/웹해킹/PortSwigger/Server-side/07-접근제어]]

### 발생 원리와 조건

서버가 요청마다 사용자·작업·대상·현재 상태의 권한을 검증하지 않는다. UI 숨김이나 예측하기 어려운 URL은 권한 검사를 대신하지 않는다.

| 유형 | 대표 예시 |
|---|---|
| 수직 | 일반 회원이 관리자 삭제 기능 실행 |
| 수평 | 내 ID를 다른 회원 ID로 바꿔 다른 계정 조회 |
| 컨텍스트 종속 | 승인·검증 단계를 생략하고 최종 단계 호출 |

### 공격 흐름과 방법

1. 비로그인·일반 사용자·다른 일반 사용자·관리자 등 역할별 정상 요청을 비교한다.
2. 같은 엔드포인트에 다른 세션이나 대상 ID를 적용한다.
3. 화면에 없는 관리 경로, 쿠키의 역할 값, 숨겨진 필드를 확인한다.
4. 경로·메서드·프록시 헤더별로 권한 검사가 일관되는지 본다.
5. 리다이렉트 응답 본문 및 실제 변경 결과까지 확인한다.

### 대표 예시와 공격 방법

- IDOR: `/customer_account?customer_number=132355`나 `/static/12144.txt`의 식별자를 변경한다. **직접 참조 + 권한 검증 누락**이 문제이다.
- 역할 입력: `Admin=false`, `roleid=2` 등을 서버가 그대로 신뢰하는 구현인지 확인한다.
- 프록시 불일치: 외부 경로는 허용되지만 `X-Original-URL`/`X-Rewrite-URL`을 백엔드가 다른 경로로 해석하는 경우를 비교한다.
- 메서드·경로 불일치: POST만 막고 GET도 처리하는지, 대소문자·후행 슬래시 변형에서 필터와 라우터가 다른 결정을 하는지 본다.
- 다단계 기능: 앞 단계가 막혀도 최종 승인 요청에 직접 접근할 수 있는지 확인한다.
- Referer 검사: 단순히 `/admin`에서 온 것처럼 보이면 허용하는 구현인지 본다.

### 헷갈리기 쉬운 개념과 확인 필요

GUID는 추측을 어렵게 할 뿐 권한 검사가 아니다. 다른 사람의 프로필 응답을 얻었다고 그 계정으로 로그인한 것은 아니다. Referer·역할 쿠키·위치 입력은 그 자체로 신뢰 가능한 권한 근거가 아니다. 다만 헤더·경로 변경만으로 모든 환경에서 우회되는 것은 아니다.

## 08 웹 서버 보안과 파일 업로드

원본: [[08-파일-업로드-취약점]]

### 발생 원리와 조건

원본은 WAF → 웹 서버/리버스 프록시 → 애플리케이션의 여러 검증 층을 설명하고, 파일 업로드를 중심으로 다룬다. 검사 시 파일명·확장자·MIME·내용을 보는 방식과 **저장·조회·실행 때의 해석**이 어긋나면 취약점이 생긴다.

업로드 성공과 코드 실행은 별개다. 서버가 저장 파일을 PHP/JSP 등으로 해석하고 실행하는 경로가 있어야 웹 셸이 작동한다.

### 공격 흐름과 방법

1. 정상 파일의 multipart 요청, 저장 이름, 조회 URL을 기록한다.
2. `filename`, 파트별 `Content-Type`, 파일 내용 중 무엇으로 검사하는지 하나씩 바꾼다.
3. 저장 위치와 조회 시 Content-Type·실행 동작을 구별한다.
4. 검증기와 실제 처리기의 차이를 노려 조건에 맞는 우회를 시험한다.
5. 실행, 파일 읽기, 덮어쓰기, 저장형 XSS 등 실제 영향을 확인한다.

| 방법 | 원본 예시 | 필요한 조건 |
|---|---|---|
| MIME 위조 | 스크립트 파트의 `Content-Type: image/jpeg` | 클라이언트 제공 MIME만 신뢰 |
| 파일명 우회 | `.pHp`, 이중 확장자, 끝의 점·공백 | 검사기와 저장/실행기의 해석 차이 |
| 일회성 제거 우회 | `.p.phphp` → `.php` | 위험 확장자를 한 번만 제거 |
| 경로 조작 | filename의 `../` 등 | 저장 경로 이탈 가능 |
| 설정 파일 업로드 | `.htaccess`로 `.l33t`를 PHP 처리 | 설정 파일 저장·적용 및 해당 지시어 허용 |
| 폴리글랏 | JPEG 메타데이터에 PHP 삽입 | 이미지 검사 통과와 별도로 코드 실행 경로 존재 |
| 업로드 레이스 | 저장 직후 검증·삭제 전 조회 | 검증 전 웹 접근/실행 가능 |
| URL 업로드 레이스 | 내려받은 파일을 웹 루트 임시 경로에 보관 | 위치 추측·접근 가능한 시간 구간 |
| 다른 쓰기 경로 | PUT 지원 여부 확인 | 서버가 해당 요청을 실제 파일 쓰기로 처리 |

### 대표 예시: 폴리글랏과 실행 조건

이미지 메타데이터에 `<?php echo 'test'; ?>`를 넣으면 이미지로도 해석 가능한 파일이 될 수 있다. 그러나 `.jpg`를 올리고 조회하는 것만으로 PHP 실행이 보장되지는 않는다. PHP 확장자 처리, LFI의 include 경로, 설정 변조 등 **별도 실행 경로**를 확인해야 한다.

업로드된 SVG/HTML은 브라우저에서 XSS로, XML 기반 문서는 서버 파서에서 XXE로 연결될 수도 있다. 서버 코드 실행과 공격 대상이 다르다.

### 헷갈리기 쉬운 개념과 확인 필요

- 매직 바이트 검사는 완전한 파일 검증이 아니다. 모든 형식이 동일한 고유 헤더를 갖는 것도 아니다.
- `.htaccess`는 업로드만 되면 항상 적용되는 것이 아니다. Apache 설정과 허용 지시어를 확인한다.
- 널 바이트·다중 확장자·유니코드 변환은 버전·파일시스템·핸들러 의존이다.
- OPTIONS의 Allow는 탐색 단서이다. PUT 파일 쓰기나 권한 검증 누락을 입증하지 않는다.
- 업로드 레이스의 Turbo Intruder 예제는 HTTP/2 엔진 설정을 별도로 확인해야 한다. [[#09 경쟁 상태]]와 연결한다.

## 09 경쟁 상태

원본: [[보안/웹해킹/PortSwigger/Server-side/09-경쟁-상태]]

### 발생 원리와 조건

같은 상태를 다루는 요청들이 겹치며 **검사와 갱신 사이**, 또는 **객체가 부분적으로 생성된 순간**의 가정을 깨뜨린다. 순차 요청은 정상이어도 병렬 실행 때 쿠폰·잔액·토큰·인증 상태가 꼬일 수 있다.

### 공격 흐름과 방법

1. 결제·쿠폰·이메일 변경·MFA·비밀번호 재설정처럼 공유 상태가 있는 기능을 고른다.
2. 순차 요청으로 기준 동작을 확인한다.
3. 같은 요청 또는 관련된 여러 엔드포인트를 병렬 실행한다.
4. 응답 차이 외에 잔액·주문·메일의 대상과 링크 등 실제 상태를 비교한다.
5. 차이가 반복되면 요청 수·순서·연결 준비를 조절해 충돌 조건을 좁힌다.

| 종류 | 대표 예시 |
|---|---|
| 제한 초과 | 사용 여부 확인과 표시 사이에 쿠폰 여러 번 적용 |
| 단일 엔드포인트 | 서로 다른 이메일 변경 요청의 수신자와 확인 링크가 뒤섞임 |
| 다중 엔드포인트 | 결제 검증 중 장바구니에 상품 추가 |
| 숨은 중간 상태 | 세션 userid 설정 후 MFA 강제 플래그 설정 전 자원 접근 |
| 부분 생성 | 사용자 객체는 존재하지만 API 키/확인 토큰이 아직 null |
| 약한 토큰 생성 | 동시 발급에서 시간 기반 토큰 충돌 가능성 조사 |

### 대표 예시: 이메일 변경

순차로 A→B 주소 변경을 요청했더니 A 링크가 무효가 된다면 “대기 중인 변경 상태를 덮어쓸 수 있다”는 가설을 세울 수 있다. 여러 변경을 병렬로 보내 **A 수신 메일에 B용 링크가 들어가는지** 관찰한다. 단, 내부 DB 컬럼이 정확히 하나라는 것은 응답만으로 확정할 수 없다.

### 동기화 도구와 한계

- HTTP/1 계열 마지막 바이트 동기화: 연결별 요청 완성을 지연했다가 해제해 도착 시차를 줄인다.
- HTTP/2 단일 패킷 기법: 하나의 연결에서 여러 요청 완성을 묶어 네트워크 지터 영향을 줄인다.
- Burp Repeater 그룹 병렬 전송으로 탐지하고, 원본의 Turbo Intruder `Engine.BURP2`, `concurrentConnections=1`, `gate` 예제를 참고한다.
- 서버 내부 큐·프록시→백엔드 연결·DB 처리·세션 잠금은 여전히 타이밍에 영향을 준다. 필요하면 연결을 미리 준비하고 다른 세션에서도 비교한다.

### 헷갈리기 쉬운 개념과 확인 필요

단일 패킷이라고 모든 서버 로직이 0초 오차로 실행되거나 탭 순서대로 완료되는 것은 아니다. 클라이언트 토큰을 쓴다고 모든 경쟁 상태가 사라지는 것도 아니다. JWT는 암호화와 동일하지 않다. 원본의 PHP `strcmp(null, [])` 우회는 버전별 오류 처리·타입 비교 확인이 필요하다. 토큰 충돌만으로 시간 기반 생성이라고 확정할 수 없다.

## 10 SSRF

원본: [[보안/웹해킹/PortSwigger/Server-side/10-SSRF]]

### 발생 원리와 조건

URL 가져오기·재고 API·웹훅·미리보기 등의 목적지를 공격자가 조작해 **서버가 의도하지 않은 곳으로 요청**하게 한다. 공격자의 브라우저가 아닌 서버가 발신하므로 내부망·루프백에 닿을 수 있다.

### 공격 흐름과 방법

1. `stockApi`, 이미지 URL, 웹훅 등 서버 측 요청 입력을 찾는다.
2. 통제 가능한 주소로 요청이 나오는지 확인한다.
3. 응답 반환 여부와 허용 스킴·호스트·포트·리다이렉트 정책을 살핀다.
4. 랩 내부의 루프백·백엔드 목적지로 요청을 바꾸고 결과를 관찰한다.

```text
stockApi=http://127.0.0.1/admin
stockApi=http://192.168.0.68/admin
```

첫 예시는 서버 자기 자신, 둘째는 서버에서 접근 가능한 내부 시스템을 겨냥한다. 내부 요청을 신뢰하는 대상이라는 추가 조건이 있어야 권한 우회로 이어진다.

### 필터별 공격 방법

| 방법 | 핵심 |
|---|---|
| IP 표기 변형 | `127.1`, 정수 표현 등을 연결 라이브러리가 같은 주소로 해석하는지 |
| DNS 이름 | 문자열 호스트 검사를 통과한 이름이 차단 IP로 해석되는지 |
| 인코딩·대소문자 | 검증 시와 실제 요청 시 다른 표현으로 처리되는지 |
| userinfo `@` | `https://expected-host@evil-host/`의 실제 호스트는 뒤쪽 |
| fragment `#` | `https://evil-host/#expected-host`는 포함 문자열 검사만 속일 수 있음 |
| 하위 도메인 | `expected-host.evil.example`은 expected-host 자체가 아님 |
| 리다이렉트 | 허용 URL에서 내부 주소로 이동할 때 목적지를 재검사하는지 |

### 블라인드와 추가 연결

응답이 보이지 않는 블라인드 SSRF는 고유 OAST 도메인의 DNS/HTTP 로그로 통신을 관찰한다. DNS만 보이면 HTTP 완료나 내부 데이터 유출까지 입증한 것은 아니다. 원본의 CGI/Shellshock 및 HTTP 클라이언트·이미지 파서 공격은 **해당 구성요소에 별도 취약점이 있어야 하는 공격 체인**이다.

### 헷갈리기 쉬운 개념과 확인 필요

`@`, `#` 예시는 URL 파서에 전달하는 문자열의 규칙이다. HTTP Host 헤더를 같은 형태로 바꾸면 동일하게 라우팅된다고 볼 수 없다. 이중 디코딩·IP 별칭·경로 대소문자 처리는 구현에 의존한다. DNS 통신도 차단될 수 있으며 항상 허용되는 것은 아니다.

## 11 XXE

원본: [[보안/웹해킹/PortSwigger/Server-side/11-XXE]]

### 발생 원리와 조건

신뢰할 수 없는 XML을 처리하는 파서가 DTD의 외부 엔티티를 해석해 파일이나 URL을 읽을 수 있을 때 발생한다. XML 본문뿐 아니라 SVG, 오피스 문서 내부 XML, SOAP/SAML 처리 경로도 후보이다. **XML을 받는다는 사실만으로 XXE는 성립하지 않는다.**

### 공격 흐름과 방법

1. 요청이나 업로드 파일이 실제 XML 파서로 처리되는지 확인한다.
2. DTD·외부 엔티티 허용 여부를 조사한다.
3. 값이 응답에 반영되면 파일 내용을 치환하고, 안 보이면 OAST·오류 경로를 검토한다.
4. 문서 전체를 바꿀 수 없는 경우에는 XInclude 같은 별도 처리 기능을 확인한다.

### 대표 예시: 파일 읽기

```xml
<?xml version="1.0"?>
<!DOCTYPE stockCheck [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<stockCheck><productId>&xxe;</productId></stockCheck>
```

외부 엔티티가 파일 내용으로 치환되고 `productId`를 오류 메시지에 반사하는 환경이면 파일이 노출된다. `SYSTEM`을 HTTP URL로 바꾸면 서버 측 요청, 즉 SSRF로 연결될 수 있다.

### 응답이 보이지 않을 때

- **일반 외부 엔티티:** 본문에서 `&xxe;`를 참조해 외부 요청을 관찰한다.
- **파라미터 엔티티:** DTD 안에서 `%xxe;`로 외부 DTD를 로드할 수 있는지 본다.
- **외부 DTD로 유출:** 파일 엔티티를 읽고 그 값을 포함한 외부 요청용 엔티티를 구성한다. 문자·줄바꿈·URL 제약으로 실패할 수 있다.
- **오류 기반:** 존재하지 않는 파일 경로에 읽은 값을 포함하여 노출된 파싱 오류에서 값을 관찰한다.
- **로컬 DTD 재사용:** 외부 통신이 불가능하면 실제 설치된 로컬 DTD의 엔티티 재정의 가능성을 살핀다. 파일과 엔티티 이름이 맞아야 한다.

### XInclude와 업로드

일반 폼 값을 서버가 내부 XML에 넣는 경우, 문서 시작의 DOCTYPE은 제어하지 못해도 삽입 지점에서 XInclude가 처리될 수 있다.

```xml
<foo xmlns:xi="http://www.w3.org/2001/XInclude">
  <xi:include parse="text" href="file:///etc/passwd"/>
</foo>
```

서버가 이 마크업을 이스케이프 없이 넣고 XInclude 처리를 활성화해야 성립한다. SVG의 `<text>&xxe;</text>`를 서버가 렌더링하는 경로, Content-Type 변경으로 XML 파서가 선택되는 경로도 원본의 공격 예시이다.

### 헷갈리기 쉬운 개념과 확인 필요

일반 엔티티는 본문에서 `&이름;`, 파라미터 엔티티는 DTD에서 `%이름;`으로 참조한다. XML 숫자 엔티티로 SQL 키워드를 복원하는 공격은 SQLi 우회이며 XXE와 다르다. 클라우드 메타데이터 접근은 서비스 설정·인증 요구·네트워크에 따라 달라진다. “특정 DTD가 거의 항상 존재”, “모든 XML 파서에서 자동으로 처리”, “임의 파일을 Base64로 변환 가능”은 원본만으로 보장할 수 없다.

## 12 NoSQL 인젝션

원본: [[보안/웹해킹/PortSwigger/Server-side/12-NoSQL-인젝션]]

### 발생 원리와 조건

NoSQL은 여러 DB 계열의 총칭이다. 원본의 주입 예시는 주로 MongoDB이며 두 경계를 구별해야 한다.

| 유형 | 취약한 처리 | 공격자가 제어하는 것 |
|---|---|---|
| 구문 주입 | `$where`의 JavaScript 문자열에 입력 결합 | 문자열 경계를 벗어난 JS 표현식 |
| 연산자 주입 | 쿼리 값으로 외부 객체를 그대로 수용 | `$ne`, `$regex` 등의 조건 객체 |

### 구문 주입 흐름과 예시

```js
// 취약한 조립
db.products.find({ $where: "this.category == '" + category + "'" });
```

1. 따옴표 등으로 구문 오류·이스케이프 처리 차이를 관찰한다.
2. `fizzy' && 0 && 'x`와 `fizzy' && 1 && 'x`를 비교한다.
3. `'||'1'=='1`처럼 원래 조건을 바꾸는 표현식을 구성한다.
4. 현재 문서의 필드를 조건으로 조회할 수 있다면 문자·길이 조건으로 데이터를 추론한다.

원본의 `this.password[0] == 'a'`는 현재 검사 중인 문서의 첫 글자를 질문하는 예이다. `$where`에서 임의의 다른 컬렉션을 자유롭게 조회할 수 있다고 확장해 해석하지 않는다.

### 연산자 주입 흐름과 예시

```json
{"username":"admin","password":{"$ne":""}}
```

비밀번호 문자열 대신 조건 객체를 수용해 쿼리에 넣는 구현이라면 원래의 일치 검사를 바꿀 수 있다. 이후 `$regex: "^a"` 등으로 접두사를 추론할 수 있지만, 실제 저장 필드가 해시라면 평문 비밀번호 추출과는 다르다.

- JSON 객체와 `username[$ne]=…` 같은 폼 표기를 비교한다. 후자가 중첩 객체로 변환되는지는 파서 설정에 달려 있다.
- `$where`를 쿼리 최상위에 추가할 수 있다면 `Object.keys(this)`로 필드 이름 조건을 만들 수 있다.
- 시간 기반 예시는 서버 측 JS 실행과 해당 함수/기능 지원이 전제이다. 지연만으로 바로 확정하지 않는다.

### 헷갈리기 쉬운 개념과 확인 필요

객체형 쿼리를 쓴다고 무조건 안전하지는 않다. `category`가 문자열로 제한되면 구문 주입을 막을 수 있지만 **공격자 객체를 받아 그대로 넣으면 연산자 주입**이 남는다. `$in`은 후보 중 하나와 일치하는 조건이다. `this.field != ''`만으로 필드 존재를 확정하면 안 된다. 원본의 중괄호가 중첩된 `$where` JSON 일부는 문법이 불완전하며, `%00`과 `sleep()` 동작도 환경 확인이 필요하다.

## 13 API 테스트

원본: [[보안/웹해킹/PortSwigger/Server-side/13-API-테스트]]

### 발생 원리와 범위

API 테스트는 하나의 취약점명이 아니라 **숨겨진 엔드포인트·입력·메서드·버전을 찾아 인증과 데이터 처리의 결함을 조사하는 방법**이다. 화면에서 보이지 않는다고 서버에도 기능이 없는 것은 아니다.

### 공격 흐름과 방법

1. 정상 트래픽·JS 번들·공개 API 문서에서 경로와 요청 형식을 모은다.
2. 필수/선택 파라미터, 지원 메서드, Content-Type, 인증, 속도 제한을 목록화한다.
3. `/api`, `/api-docs`, `/openapi.json`, Swagger 관련 경로 및 상위 경로를 조사한다.
4. 발견한 URL 패턴을 확장하고, 숨겨진 파라미터·구버전을 확인한다.
5. 인증·객체 권한·필드 권한·입력 검증을 실제 요청으로 구별한다.

### 대표 예시: 대량 할당

```js
// 위험 여부를 확인할 후보
user.update(req.body);
```

서버가 수정 가능한 필드를 제한하지 않으면 `{"email":"me@example.com","isAdmin":true}`가 관리자 필드까지 갱신할 수 있다. 응답에 보이는 `isAdmin`은 후보 이름의 단서이지 쓰기 가능성의 증거는 아니다. 요청 후 별도 조회나 기능 접근으로 실제 변경을 확인한다.

### 공격 방법 연결

- GET→DELETE/PATCH 변경: 메서드별 접근 제어 차이 조사.
- JSON→XML 변경: XML 파서가 실제 선택되면 XXE 표면 조사.
- 다른 리소스 ID: IDOR 조사.
- 토큰 제거: 서버 측 인증 검증 조사.
- 숨겨진 필드 추가: 대량 할당/권한 필드 조작 조사.

### 헷갈리기 쉬운 개념과 확인 필요

공개 문서나 다른 HTTP 메서드 지원 자체가 취약점은 아니다. 서버가 허용하지 않는 방식으로 상태나 데이터에 영향을 주어야 한다. “Param Minor”는 원본 표기이며 도구 이름은 Param Miner로 확인할 대상이다. 자동 추측 개수나 도구 UI는 고정 규칙으로 외우지 않는다.

## 14 서버 측 파라미터 오염

원본: [[보안/웹해킹/PortSwigger/Server-side/14-서버-측-파라미터-오염]]

### 발생 원리와 조건

외부 입력을 내부 API의 URL·경로·JSON 등에 **문자열로 조립하면서 값의 경계를 보존하지 못하면**, 공격자가 내부 요청의 구조까지 바꿀 수 있다. 특정 MSA 구성에서만 생기는 문제는 아니다.

### 공격 흐름과 대표 예시

```text
외부: /userSearch?name=peter
내부: /users/search?name=peter&publicProfile=true

외부 입력: peter%23foo
디코딩 후 내부 조립: /users/search?name=peter#foo&publicProfile=true
```

내부 URL 파서가 `#` 뒤를 fragment로 처리하면 보안 관련 후행 파라미터가 전송되지 않을 수 있다.

1. `%26x=y`로 별도 파라미터를 추가하고 오류 차이를 관찰한다.
2. `%23`으로 뒤를 잘라 필수 필드가 사라지는지 본다.
3. 중복 이름을 넣어 어떤 값이 채택되는지 비교한다.
4. 관찰한 필드·경로만 바꾸고 실제 내부 동작의 변화를 확인한다.

### 공격 방법

| 위치 | 방법 | 예시 |
|---|---|---|
| 쿼리 | 파라미터 추가 | `peter%26email=foo` |
| 쿼리 | 중복 값 주입 | `peter%26name=carlos` |
| 쿼리 | 후행 내용 제거 | `administrator%23` |
| 경로 | 내부 API 경로 이탈 | `peter%2f..%2fadmin` |
| 경로 | 문서·구버전 탐색 | 이탈 후 내부 `openapi.json`과 버전 경로 조사 |
| JSON | 따옴표 탈출·필드 추가 | `peter","access_level":"administrator` |

원본의 재설정 예시는 오류를 통해 `field`라는 내부 파라미터를 발견하고 `reset_token`을 요청해 토큰 노출로 연결하는 흐름이다. 에러와 응답은 내부 구조의 단서이며, 원본에 그린 서비스 분할도가 실제 구현이라고 확정할 수는 없다.

### 헷갈리기 쉬운 개념과 확인 필요

SSRF는 주로 목적지를 바꾸고, 이 공격은 내부 요청의 **파라미터·경로·구조**를 바꾼다. 파일시스템의 `../`와 내부 URL의 `../`도 구별한다. 중복 파라미터가 첫 값·마지막 값·배열·결합값 중 무엇이 되는지는 프레임워크 이름만으로 확정하지 않는다. JSON serializer로 안전하게 문자열 값을 넣는 경우라면 위의 JSON 문자열 탈출이 그대로 성립하지 않는다.

## 15 웹 캐시 기만

원본: [[보안/웹해킹/PortSwigger/Server-side/15-웹-캐시-기만]]

### 발생 원리와 조건

캐시는 정적 리소스로 판단하지만 원본 서버는 개인화된 동적 페이지로 처리하는 URL을 만들어 **피해자의 민감 응답을 공유 캐시에 저장**하게 한다. 이후 공격자가 같은 캐시 항목을 받을 수 있어야 데이터 유출이 성립한다.

```text
피해자 로그인 상태로 /profile;test.js 방문
  → 원본: /profile로 해석해 피해자 정보 반환
  → 캐시: .js 규칙으로 저장
  → 공격자: 같은 캐시 키로 요청하여 저장된 정보 수신
```

### 공격 흐름과 방법

1. 민감 정보가 나오는 GET 페이지와 정상 캐시 응답을 찾는다.
2. 임의 경로 추가, 구분 기호, 인코딩된 이동 경로를 사용해 원본 해석을 비교한다.
3. 같은 URL의 반복 요청에서 캐시 저장·재사용을 관찰한다.
4. 자신의 테스트 세션과 별도 비인증 요청 등으로 **다른 사용자에게 응답이 공유되는지** 확인한다.
5. 새 시험마다 캐시 키에 반영되는 새 경로/파라미터로 기존 캐시 영향을 구별한다.

| 불일치 | 대표 URL | 확인할 양쪽 해석 |
|---|---|---|
| 경로 매핑 | `/my-account/foo.js` | 원본은 접미 경로를 무시, 캐시는 확장자로 저장 |
| 구분 기호 | `/profile;foo.css` | 원본만 `;` 뒤를 무시 |
| 구분 기호 디코딩 | `/profile%23foo.css` | 원본만 디코딩 후 경로 절단 |
| 원본만 정규화 | `/assets/..%2fprofile` | 캐시는 assets 규칙, 원본은 profile |
| 캐시만 정규화 + 원본 구분자 | `/profile;%2f%2e%2e%2fstatic` | 캐시는 static, 원본은 profile |
| 파일명 규칙 | 위 구조의 끝을 `index.html` 등으로 구성 | 캐시가 특정 파일명에 규칙 적용 |

### 관찰 방법

`X-Cache: hit/miss`, Age, 응답 내용·시간 등을 함께 비교한다. 캐시 키는 경로뿐 아니라 쿼리·헤더 등도 포함할 수 있다. Cache-Control은 단서지만 실제 캐시 설정·사용자별 분리·재사용 여부를 따로 확인한다.

### 헷갈리기 쉬운 개념과 확인 필요

- 캐시 **기만**은 민감한 정상 응답이 잘못 공유되는 문제이다. 공격자 콘텐츠를 캐시에 넣는 캐시 오염과 구별한다.
- URL이 다르지만 응답이 같다고 리다이렉트라고 확정하지 않는다. 상태 코드·Location·최종 요청을 본다.
- `.js`가 붙었다고 항상 캐시되지 않으며, hit라고 피해자 데이터가 공격자에게 공유되는 것도 아니다.
- 피해자의 로그인 쿠키가 실제 요청에 붙어야 한다. `<img>`만으로 유도하는 예시는 SameSite·제3자 쿠키 정책에 막힐 수 있다.
- 프레임워크·CDN별 구분 기호 처리와 POST로 캐시를 피한다는 방법은 대상 설정에 따라 확인해야 한다.
