## 인증 취약점

- 무차별 대입 공격(브루트포스)에 대한 적절한 방어 기능을 제공하지 못한 경우
- 구현상의 논리적 오류나 부실한 코딩으로 인한 인증 메커니즘의 우회가 가능한 경우

### 브루트포스 

Burp Suite의 Intruder 등을 활용하여 반복적인 시도를 통해서 사용자의 아이디와 비밀번호를 추측하는 방식 

- 아무렇게나 때려박지 말고 해당 웹사이트가 사용자 이름이나 닉네임 등을 노출하고 있는지 확인해야 함. 프로필에 사용된 이름이 로그인 시 사용되는 사용자의 이름과 동일할 확률이 있음. 
- 비밀번호의 경우에 사용자가 많이 사용하는 패턴이 있으므로 그걸 이용함. 예: Mypassword1!, Mypassword1?, Mypassword2! 등
- 같은 사용자인지 모르도록 쿠키를 삭제하거나 조작해야할 수도 있음.

#### 사용자 아이디를 알아내는 방법

1. 상태 코드: 다른 상태 코드가 반환된다면 해당 아이디는 존재할 확률이 높음.
2. 오류 메세지: 다른 오류 메시지가 반환된다면 해당 아이디는 존재할 확률이 높음. 
3. 응답 시간: 맞는 아이디인 경우에 비밀번호가 맞는지 확인하기 위해서 암호화 알고리즘(해싱)이 작동하기 때문에 응답시간이 길어짐.

#### 응답시간 

- `concurrentConnections`(동시 연결 수), `requestsPerConnection`(연결당 요청 수)를 1로 설정 (지연시간을 정확히 체크하기 위함.)
- 비밀번호를 아주 길게해서 아이디가 맞은 경우 비밀번호가 맞는지 확인하기 위해 암호화 알고리즘(해싱)을 돌릴때 시간 지연이 크도록 해야함.
- 여러번 돌려서 응답시간이 꾸준히 길게 나오는 것을 찾아내야함. 


#### IP 차단

- IP 차단을 피하기 위해서 HTTP 헤더 `X-Forwarded-For`를 설정해주는 등의 작업이 필요할 수 있음. 
	- **HTTP 헤더:** 조작 가능
	- **TCP/IP 패킷(OS가 처리하는 곳):** 해당 웹 서비스가 TCP 연결 IP를 기준으로 차단하도록 코드를 짠 경우 조작 불가능 => 프록시, VPN을 사용해야함. 
- 로그인에 성공하면 로그인 시도 횟수가 초기화되는 구조일 수도 있음. 이런 경우 로그인 시도 사이에 내 계정으로 로그인 성공을 넣어서 브루트포스가 가능함. 
- `concurrentConnections`(동시 연결 수) 등을 1개로 설정해야함. 안그러면 동시에 여러 요청이 날아가서 차단당함. 


#### 계정 잠금

- 실제로 존재하는 사용자 아이디인 경우에 여러번 시도하면 계정이 잠길 수 있음. (계정이 잠기지 않는 아이디는 존재하지 않는 것이라고 판단 가능.)
- 계정이 잠겼어도 아이디, 비밀번호가 일치하면 다른 응답을 반환하는 경우에는 이게 정답임. 
- 우회 방법 
	1. **패스워드 스프레이**: 유효할 가능성이 높은 아이디 리스트에 흔한 비밀번호 1~3개를 다 넣어보는 방법
	2. **크리덴셜 스터핑**: 이미 다른 곳(예: 다크웹)에서 털린 아이디랑 비밀번호를 넣어보는 방법


#### 한번의 요청에 여러개의 로그인

- 비밀번호를 배열(`["a", "b", "c"]` 등)으로 요청하면 특정 언어(예: PHP)나 특정 SQL ORM 라이브러리들은 배열의 내용과 비밀번호를 전부 비교함. 


### HTTP 기본 인증

서버로부터 사용자명과 비밀번호를 합쳐서 Base64로 인코딩한 인증 토큰을 받고 이걸 인증에 사용하는 아주 오래된 방식
- `Authorization: Basic base64(username:password)`

### 다중 인증 취약점 (MFA 취약점)

서로 다른 요소의 방식을 두 가지 이상 확인하는 것이 진정한 다중 인증임.
- **지식:** 머릿속에 기억하고 있는 것 (예: 비밀번호, PIN 번호)
- **소유:** 물리적으로 가지고 있는 것 (예: 내 명의의 스마트폰, OTP 기기, 보안카드)
- **존재:** 내 몸에 붙어있는 것 (예: 지문, 홍채, 안면 인식)

**쿠키를 조작해서 첫번째 인증을 우회할 수 있음.** 
- 아이디, 비밀번호 입력 (1차 인증) -> 쿠키에서 다른 계정명으로 요청: 2차인증 코드가 조작한 쿠키의 계정으로 보내짐. -> 2차 인증 브루트포스로 뚫기 


**브루트포스 + 매크로 사용**

일정 횟수 이상 잘못된 인증 코드를 입력하면 자동으로 로그아웃 되는 상황
각 session, csrf 토큰은 연결되어있고 한번 사용되면 만료됨. 
매크로를 통해서 브루트포스 공격마다 새로운 session, csrf를 발급 받아야함.
로그인할때마다 이메일로 새로운 코드가 전송되는 방식은 아님. (특정 시간마다 코드가 새로 발급되는 상황을 가정한 문제)

요청 과정
1. GET /login에서 session과 csrf 토큰을 발급 받음. 
2. 해당 session과 csrf 토큰으로 POST /login 요청을 보냄. 
3. 응답으로 session과 /login2 리다이렉트를 줌. 
4. GET /login2를 하면 csrf 토큰을 발급 받음. 
5. 해당 session과 csrf 토큰으로 POST /login2 요청을 보냄. 

매크로 설정
1.  Settings > Sessions > Macros, Session handling rules를 통해서 매크로 설정을 하면 매 요청 전에 (Intruder, Repeater 등) 설정된 매크로를 실행함. 따라서 session 값이나 csrf 토큰 값 등을 요청마다 새로운 값으로 넣을 수 있음. 
2. Trubo Intruder를 사용하는 경우에는 매크로를 직접 스크립트를 작성해야함.

### 로그인 상태 유지

**바이트 변환(UTF-8 인코딩/디코딩)**
- 사람의 글자를 컴퓨터가 계산하고 전송할 수 있는 0과 1의 숫자(바이트)로 바꾸거나, 반대로 되돌림. 
- 기본적으로 네트워크에서 패킷을 주고받을 때 자동으로 일어남. 

**Base64**
- 해시값이나 이미지 같은 '날것의 바이트 데이터'를 HTTP 같은 텍스트 기반 시스템에 넣었을 때 에러가 나거나 깨지지 않도록, **가장 평범하고 안전한 64개 종류의 문자(알파벳+숫자)로만 이루어진 텍스트로 위장**시키는 것
- 암호화가 아닌 안전한게 데이터를 주고받는 용도
- 3글자를 4글자로 바꾸고, 끝에 붙는 `=` 기호는 빈칸을 의미함. (4글자를 맞추기 위해서 `=` 사용)

**해싱**: 단방향 
- MD5: 결과물이 항상 32자리의 영문+숫자(Hex)로 나옴. (예: `900150983cd24fb0d6963f7d28e17f72`)
- SHA-1: 결과물이 항상 40자리로 나옴.
- SHA-256: 결과물이 항상 64자리로 나옴.
- **문자열을 바이트로 변환한 후에 해싱해야함.**

**암호화**: 양방향
- 보통 16바이트를 기준으로 블럭을 만들어서 글자를 1대1로 암호화. 


로그인 상태를 유지하기 위해서 서버에서 발급된 토큰을 쿠키에 저장시켜서 로그인 과정을 생략하기도 함. 
이 쿠키가 어떤 구조로 만들어지는지를 분석할 수 있다면 다른 계정에 접근할 수 있음. 
- 유효한 비밀번호 리스트가 있다면, 해당 비밀번호로 토큰을 만들어서 브루트포스 공격 가능
- XSS가 가능하다면, 사용자의 쿠키를 획득해서 역복호화를 해서 비밀번호를 알아낼 수 있음. 


### 비밀번호 재설정

이메일로 가는 비밀번호 변경 URL을 조작해서 토큰을 얻어내고 사용자의 비밀번호를 바꾸는 방법
1. 비밀번호 변경 POST 요청에서 X-Forwarded-Host를 내 서버 주소로 넣음.
2. 서버에서 X-Forwared-Host에 명시된 내 서버 주소 + forgot-password-token으로 비밀번호 재설정 URL을 만들어서 사용자 메일로 보냄. (취약점)
3. 사용자가 이걸 클릭하면 내 서버에 로그가 생기고 난 이걸로 사용자의 비밀번호를 바꿈.


**X-Forwarded-Host**: 현대의 웹 서비스는 사용자와 실제 웹 서버(백엔드) 사이에 로드밸런서, 리버스 프록시, CDN(Cloudflare 등) 같은 '중간자'를 둠. 
사용자가 `Host: example.com`으로 요청을 보내면, 중간자는 이 요청을 받아서 내부망에 있는 진짜 서버(예: `10.0.0.5`)로 전달. 이때 백엔드 서버 입장에서는 요청의 `Host`가 내부 IP(`10.0.0.5`)로 보임. 백엔드 서버가 "원래 사용자가 접속했던 찐 도메인이 뭐였지?"를 알 수 있도록 중간자가 친절하게 붙여서 넘겨주는 헤더가 바로 `X-Forwarded-Host`임.

사실 `Host`를 바꾸지 않고 유지하는 방식이 더 보안적으로 좋음. 이걸 Host Header Preservation (호스트 헤더 보존)라고 함. 
하지만 과거의 서비스, 복잡한 내부망, 관성적인 개발로 그냥 `X-Forwared-Host`를 사용하는 경우가 많음.

사실 이건 Host header attacks 파트임.
