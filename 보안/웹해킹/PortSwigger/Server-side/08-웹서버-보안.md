## 웹 서버 보안

#### 1단계: 웹 방화벽 (WAF, Web Application Firewall)

- 정체: 클라우드플레어(Cloudflare), AWS WAF, ModSecurity 같은 전문 보안 장비나 소프트웨어
- 역할: Nginx에 도달하기도 전에, 인터넷의 맨 앞단에서 패킷을 뜯어보고 방어함. 
- 예시: 파일 이름에 `../`나 `%00` 같은 해킹 기호가 있는 경우 차단

WAF(AWS WAF, Cloudflare 등)는 백지상태로 제공되지 않음. 보통 보안 업체가 미리 만들어둔 '기본 방어 규칙 세트'가 들어있고, 관리자가 이를 켜고 끌 수 있으며, 필요하면 직접 '사용자 정의 규칙(정규표현식)'을 추가할 수 있음.


#### 2단계: 웹 서버 / 리버스 프록시

- 정체: Nginx나 Apache 등
- 역할: 방화벽을 통과한 요청을 받아보고, 주소와 확장자를 검사
- 예시
	- 사용자가 `/uploads/.htaccess` 파일을 올리려고 하는 경우, 내 설정에 `.htaccess`는 접근 금지니까 차단 
	- 이미지는 1번 서버로 보내고, 코드는 2번 서버로 보내는 등

Nginx, Apache 같은 프로그램들은 공식 명칭이 웹 서버임. 원래 웹 서버의 본질적인 역할은 클라이언트(브라우저)가 HTTP 요청을 보내면, 그에 맞는 정적 파일(HTML, CSS, 이미지 등)을 찾아서 던져주는 것이었지만, 현대 아키텍처에서는 이 웹 서버들이 수많은 TCP 연결을 가볍고 빠르게 잘 처리하므로 **직접 파일을 던져주는 대신 요청을 받아서 뒤에 있는 진짜 애플리케이션 로직을 처리하는 서버(WAS)로 토스해주는 역할(리버스 프록시)** 로 주로 사용됨. 

Nginx나 Apache는 WAF와 달리 '보안 전문'이 아니기 때문에 처음 설치하면 해킹 방어 규칙이 **거의 백지상태**임. 개발자나 인프라 엔지니어가 `nginx.conf` 같은 설정 파일을 작성해야함. 

``` nginx
# 개발자가 직접 설정하는 Nginx 규칙의 예
location ~ /\.ht {
    deny all;  # .htaccess 파일에는 아무도 접근 못 하게 막아라!
}

location /uploads/ {
    # 업로드 폴더에서는 PHP 실행을 막아라!
    location ~ \.php$ {
        deny all; 
    }
}
```


#### 3단계: 웹 애플리케이션 서버의 개발자 검증 코드

- 정체: Spring(Java), Node.js(JS), PHP 등으로 개발자가 직접 작성한 파일 업로드 처리 소스 코드
- 역할: 사용자가 올린 파일의 확장자, Content-Type, 파일 크기 등을 검사
- 예시: `if (file.extension == ".php") { 업로드 차단 } else { 저장 }`

 Spring, Node.js, Django 같은 프로그램으로 만든게 '웹 애플리케이션 서버(WAS)'임. 
 웹 서버(Nginx)가 단순한 파일 전달이나 트래픽 분산(문지기)만 한다면, WAS(스프링)는 진짜 비즈니스 로직(DB에서 회원 정보 조회, 결제 처리, 알고리즘 계산 등)을 수행하는 두뇌 역할. 
 엄밀히 따지면 WAS도 밖에서 오는 HTTP TCP 연결을 받아야하니까 내장 웹 서버(Tomcat 등)가 있음.

보안상 개발자가 개발 언어로 무에서 유를 창조하는 공간이므로 **가장 많은 취약점이 발견됨.** 



## 파일 업로드 취약점

웹 서버가 사용자가 업로드하는 파일의 이름, 유형, 내용, 크기 등을 제대로 검증하지 않고 그대로 파일을 시스템에 저장하면서 발생하는 취약점. 

**원인**
1. 어설픈 차단 목록(블랙리스트) 사용: 미처 파악하지 못한 위험한 파일이 차단 목록에서 누락됨.
2. 조작하기 쉬운 속성에 의존: 해킹 도구로 쉽게 위조할 수 있는 파일의 겉모습(속성)만 보고 안전한 파일이라고 착각함. 
3. 일관성 없는 보안 규칙 적용: 웹사이트 내의 서버나 폴더마다 방어 수준이 다르게 적용되어, 방어막이 약한 곳이 뚫림.  

**영향**
1. 파일의 유형이 제대로 검증되지 않는다면, 서버 설정상 특정 유형의 파일들 (`.php`, `.jsp` 등)이 코드로서 실행될 수 있음. 
2. 파일명이 제대로 검증되지 않는다면, 동일한 이름의 파일을 업로드해 중요한 파일(서버 설정 파일 등)들을 덮어쓸 수 있음. 
3. 파일 크기가 제대로 검증되지 않는다면, 서비스 거부(DoS) 공격이 가능해질 수 있음. 


#### 웹 서버(Nginx, Apache)에서 파일 요청을 처리하는 방식

1. 서버는 요청에 포함된 경로를 분석하여 **파일 확장자**를 파악 
2. 미리 저장된 확장자와 MIME 타입 규칙표에서 파일의 유형 결정
3. 그 후 파일 처리
	- 이미지나 정적 HTML 페이지: 서버는 HTTP 응답을 통해 해당 파일의 내용을 클라이언트에게 **그대로 전송**
	- 실행 가능한 파일 (PHP 등): **서버가 이러한 형식의 파일을 실행하도록 설정되어 있다면**, HTTP 요청에 포함된 헤더 정보와 매개변수들을 넣어서 스크립트 실행. 그 후 **생성된 결과를 HTTP 응답을 통해 클라이언트에게 전송**
	- 파일의 형식은 실행 가능한 형태지만, **서버가 해당 형식의 파일을 실행하도록 되어있지 않은 경우**에는 파일의 내용이 텍스트 형태로 클라이언트에 전송돼 정보가 유출될 수 있음. 


#### 파일을 파악하는 요소

1. 파일 확장자: `.jpg`,`.php`
2. Content-Type 헤더: 인터넷 통신(HTTP) 규칙인 MIME 타입(`image/jpeg` 등)을 적어서 보냄. 
	- **GET 요청의 응답 헤더**: 확장자와 MIME 타입 규칙표에 따라 지정됨. 
	- **POST 파일을 업로드 요청**: 브라우저에서 자동으로 정해주거나 사용자가 조작 가능
3. 매직 넘버: 파일의 내용물 자체를 뜻함. 모든 파일은 컴퓨터가 어떤 파일인지 읽을 수 있도록 고유한 암호(바이트 배열)를 가지고 있음.


### 파일 업로드로 웹 셸 배포

파일 업로드에 별도의 제한이나 보안 설정이 되어있지 않은 경우에 웹 셸을 업로드해서 서버의 대한 제어권을 가질 수 있음. 

**웹 셸**: 공격자가 특정 엔드포인트에 HTTP 요청을 보내는 것만으로도 원격 웹 서버에서 임의의 명령을 실행할 수 있도록 해주는 악성 스크립트

``` php
// 예: 원하는 파일을 읽는 웹 셸
<?php echo file_get_contents('/path/to/target/file'); ?>

// 예: 쿼리 파라미터를 통해 임의의 시스템 명령을 전달하는 웹 셸
<?php echo system($_GET['command']); ?>
```

1. 파일 업로드할때 웹 셸 파일을 업로드
2. 해당 경로로 요청을 보내면 웹 셸 파일이 실행된 결과를 응답으로 받을 수 있음. 


### 결함이 있는 파일 형식 검증

- `application/x-www-form-urlencoded` : POST 요청을 통해서 텍스트 데이터를 전송할때 사용하는 콘텐츠 유형
- `multipart/form-data`: POST 요청을 통해서 **이미지, 동영상, PDF 같은 파일(바이너리 데이터)을 전송해야 할 때** 사용

``` http
POST /images HTTP/1.1
    Host: normal-website.com
    Content-Length: 12345
    Content-Type: multipart/form-data; boundary=---------------------------012345678901234567890123456

    ---------------------------012345678901234567890123456
    Content-Disposition: form-data; name="image"; filename="example.jpg"
    Content-Type: image/jpeg

    [...binary content of example.jpg...]

    ---------------------------012345678901234567890123456
    Content-Disposition: form-data; name="description"

    This is an interesting description of my image.

    ---------------------------012345678901234567890123456
    Content-Disposition: form-data; name="username"

    wiener
    ---------------------------012345678901234567890123456--
```
- `Content-Disposition`: 해당 입력 필드에 대한 기본 정보를 제공
- `Content-Type`: 이 헤더는 서버에 해당 입력을 통해 전송된 데이터의 MIME 유형을 알려줌. (선택)
- `filename`: 파일이 저장되는 이름과 위치를 결정

만약 웹사이트에서 `Content-Type` 정보만으로 MIME 타입을 확인하는 경우, Burp Repeater와 같은 도구를 사용해 쉽게 우회가 가능함. 


### 사용자 접근 디렉토리의 파일 실행 방지

위험한 파일이 아예 업로드되지 않도록 미리 방지하는 것이 가장 좋지만, 서버로 유입된 스크립트를 실행하지 못하도록 하는 것이 두 번째 방어 수단이 됨. 
사용자가 파일을 업로드/불러오기 등으로 접근할 수 있는 디렉토리에서는 **아예 파일이 실행되는 것을 막거나 특정 MIME 타입만 허용**해두는 경우, 웹 셸의 실행을 막을 수 있음. 

이러한 보안이 적용되어 있는 웹사이트에서 만약 사용자가 업로드할 수 없는 디렉토리에 스크립트를 업로드할 수 있다면, 서버는 그 스크립트를 실행할 수도 있음. 
**경로 탐색** 공격을 통해서 접근할 수 없는 디렉토리에 접근함. 

동일한 도메인으로 요청을 보낸다고 해도, 로드 밸런서와 같은 리버스 프록시 서버를 거치면서 다른 서버들에 의해 처리가 되는 구조일 가능성이 높음. **웹사이트 방어벽이 너무 단단해보여도 모든 서버들의 보안 설정이 다 똑같이 완벽할 수는 없기 때문에, 설정이 허술한 다른 서버 쪽으로 요청이 넘어가도록 하면 공격이 성공할 수 있음.** 


### 서버 설정 무시

**아파치 설정 파일** 

1. `httpd.conf`: 아파치 전역 설정 파일

``` conf
LoadModule php_module /usr/lib/apache2/modules/libphp.so AddType application/x-httpd-php .php
```
- PHP 파일을 실행 가능하도록 하는 등의 설정 가능

2. `.htaccess`: 디렉토리별 설정 파일
	- 아파치 서버는 기본적으로 전역(Global) 설정 파일을 따르지만, **특정 폴더(`/uploads/`) 안에 `.htaccess` 파일이 있으면 기존 규칙을 무시하고 이 `.htaccess`에 적힌 특별 규칙을 최우선으로 따름.** 
	- `LoadModule` 같은 위험한 명령어는 `.htaccess`에서 아예 쓸 수 없도록 막혀 있음.


일반적으로 HTTP 요청으로 설정 파일을 읽는 것(GET)은 불가능함. 서버에서 403 Forbidden 접근 금지 에러를 터뜨림. 
**만약 블랙리스트에 `.htaccess` 파일을 막지 않았다면**, `.htaccess` 파일을 업로드(POST) 해서 해당 폴더의 규칙을 바꿀 수 있음.

**예시**
1. `filename` 매개변수 값을 `.htaccess`로 변경
2. `Content-Type` 헤더 값을 `text/plain`로 변경
3. 파일 내용 변경
	```
	AddType application/x-httpd-php .l33t
	```
	- `.l33t` 파일 확장자를 PHP로 실행하라는 `.htaccess` 설정 파일 내용임. 
4. 공격 스크립트가 작성된 `.php` 파일을 확장자만 `.l33t`로 바꿔서 업로드 및 조회로 실행


**윈도우**

`web.config`: 윈도우 IIS 서버 버전의 `.htaccess`. 아파치는 `.htaccess`라는 텍스트 파일을 설정 파일로 쓰고, 윈도우 IIS 서버는 `web.config`라는 XML 형식의 파일을 설정 파일 사용

``` xml
<staticContent> <mimeMap fileExtension=".json" mimeType="application/json" /> </staticContent>
```


### 블랙리스트 우회

1. **대소문자 구분**: 검증 코드가 대소문자를 구분한다면, `exploit.pHp` 이 사실은 `.php` 파일이라는 사실을 인식하지 못함.

2. **다중 확장자 지원**: 검사기는 보통 파일의 맨 마지막 확장자만 봄. 하지만 구형 아파치 서버 같은 경우, 파일 확장자가 여러 개 있으면 뒤에서부터 하나씩 읽다가 자기가 실행할 줄 아는 확장자를 바로 실행하는 성질이 있음.
	- 해커의 파일: `shell.php.png`
	- 보안 검사기: `.png`니까 정삭적인 이미지로 통과시킴.
	- 아파치 서버: `.php`를 보고 실행시킴.

3. **끝에 공백이나 점 추가하기**: 윈도우 운영체제는 파일 이름 끝에 의미 없는 마침표(`.`)나 띄어쓰기가 있으면 저장할 때 알아서 지워버림. 
	- 해커의 파일: `shell.php.` 또는 `shell.php `
	- 보안 검사기: `.php.`는 블랙리스트에 없으니 통과시킴.
	- 윈도우 서버: `.php.`를 `.php`로 저장

4. **URL 인코딩 악용: 마침표(`.`)를 URL 인코딩 값 `%2E`으로 바꿔서 보안 검사기를 우회**

5. **널 바이트(`%00`) 또는 세미콜론(`;`) 삽입**: 운영체제의 뼈대를 이루는 C언어는 널바이트(`%00`)를 만나면 문장이 끝난걸로 간주하고 뒤의 글자를 무시함. (`;`은 구형 IIS 웹 서버에서 작동)
	- 해커의 파일: `shell.php%00.jpg`
	- 보안 검사기 (C가 아닌 다른 언어라고 가정): 맨 끝이 `.jpg`니까 통과시킴.
	- 운영체제 (C 언어): 파일을 저장하려고 이름을 읽다가 `%00`을 만나고 파일 이름을 `shell.php`로 저장.

6. **멀티바이트 유니코드**: 전 세계의 언어(유니코드)에는 **마침표와 비슷하게 생긴 특수문자**들이 많음. 검사기는 진짜 아스키코드 마침표(`.`)만 차단함. 하지만 서버 내부 파일시스템이 텍스트를 깔끔하게 다듬는 과정(정규화)을 거치면서, 이 특수문자를 마침표(`.`)로 자동 변환할 수 있음.
	- 해커의 파일: `shell ．php` (가운데 있는 건 일반 마침표가 아니라, 모양만 비슷한 '전각 문자 마침표(U+FF0E)')
	- 보안 검사기: 일반적인 마침표(`.`)가 없으니 확장자가 없는 파일이므로 통과시킴. 
	- 운영체제: 이 특수문자 마침표는 시스템에서 다루기 힘드니까 일반 마침표(`.`)로 치환(정규화)해서 저장. 

7. **확장자 제거 우회**: 서버에서 확장자를 제거하거나 대체하는 방어 작업이 재귀적으로 일어나지 않는다면 우회할 수 있음. 
	- 해커의 파일: `shell.p.phphp`
	- 서버: `.php`를 제거하는 로직이 있어서 `shell.php`로 저장됨.


### 폴리글랏 웹 셸 

이미지 파일 (jpg, png)은 파일의 앞부분(Header), 끝부분(Footer), 메타데이터, 이미지 픽셀 데이터(바이너리 데이터)로 구성되어 있는데 이미지 뷰어나 보안 검사기에서는 이미지의 헤더 부분 `FF D8 FF`(JPEG) 같은 매직 넘버을 확인하고 이미지로 인식함. 
**따라서 메타데이터에 PHP 소스 코드를 넣으면 이미지 파일로 위장을 하고 공격이 가능함.** 이러한 파일을 폴리글랏(Ployglot, 두 가지 언어를 구사하는 자)이라고 부름. 

이렇게 위조된 파일은 `.jpg`, `.png` 등의 이미지 확장자로 바로 실행되는게 아니라 우회 기법을 사용해 실행시킬 수 있음. 
1. LFI(Local File Inclusion, 로컬 파일 포함) 취약점
	- 웹 애플리케이션 소스 코드 중에 다른 파일을 강제로 불러와 실행하는 코드(예: `include('/uploads/dog.jpg');`)가 존재한다면, 확장자가 `.jpg`이더라도 PHP 엔진이 이 파일을 강제로 열어서 내부의 PHP 코드를 실행해 버림.
2. 서버 설정 파일(`.htaccess`)을 변조
	- `.htaccess`를 올려서 이 디렉토리에서는 `.jpg` 파일도 PHP로 실행하라는 규칙을 덮어씌웠다면, `dog.jpg` 그대로 실행 가능
3. 다중 확장자나 파일명 우회 기법
	- `dog.jpg.php` 또는 `dog.php.jpg` (아파치 다중 확장자 취약점) 같은 형태로 이름을 바꿔서 올리면 서버가 확장자를 착각하고 PHP 엔진으로 던져주어 실행 가능


**ExifTool**
ExifTool을 사용하면 폴리글랏 파일을 쉽게 만들 수 있음. 

1. 메타데이터 Comment에 PHP 코드 추가
``` sh
exiftool -Comment="<?php echo 'START ' . file_get_contents('/home/carlos/secret') . ' END'; ?>" <YOUR-INPUT-IMAGE>.jpg
```

2. 파일 확인
``` sh
exiftool <YOUR-INPUT-IMAGE>.jpg
```

3. 확장자 변경 (선택)
``` sh
mv <YOUR-INPUT-IMAGE>.jpg <YOUR-INPUT-IMAGE>.php
```


### 파일 업로드 경쟁 상황 악용

최신 웹 프레임워크들은 일반적으로 파일을 바로 목적지에 직접 업로드하지 않음. **먼저 임시 디렉토리에 업로드**하고, 기존 파일을 덮어쓰는 것을 방지하기 위해 파일명을 무작위로 변경하고 임시 파일에 대한 검증을 수행하며, 안전하다고 판단될 때에만 최종 목적지로 전송됨. 
- 임시 파일을 외부에서 절대 접근이 불가능한 시스템 내부 폴더(예: 영구 격리된 `/tmp` 나 `/var/tmp`)에 저장
- 파일명이 무작위 난수로 변경되므로 예측 불가
- 임시 폴더에서 실행 권한 비활성화

만약 파일을 바로 메인 파일 시스템에 업로드한 후, 검증에 실패하면 해당 파일을 삭제하는 로직을 가진 웹사이트의 경우에는 **파일이 서버에 존재하는 짧은 시간 동안에 공격자가 해당 파일을 실행**시킬 수 있음.


**Trubo Intruder의 경쟁 상황(Race Condition) 공격**

**단일 패킷 공격**: 여러 개의 HTTP 요청을 보낼 때, 각 요청의 마지막 1바이트만 남겨두고 전송을 일시 정지(Block)시킨 후, 방아쇠를 당겨 남은 1바이트들을 **단 하나의 네트워크 패킷(TCP 패킷)에 담아 동시에 전송**하는 기법 (최신 웹 표준인 HTTP/2 환경에서는 단일 네트워크 패킷 안에 여러개의 HTTP 패킷을 넣어서 보낼 수 있음.)
네트워크 상태에 따라 패킷 도착 시간이 미세하게 달라지는 **네트워크 지연 현상을 완벽하게 극복**하고, 서버가 여러 요청을 완전히 같은 밀리초(ms)에 처리하도록 강제함. 

``` python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint, concurrentConnections=1,)
    request1 = '''<YOUR-POST-REQUEST>''' # shell.php를 업로드하는 요청
    request2 = '''<YOUR-GET-REQUEST>''' # 업로드된 shell.php를 실행하는 요청

    # gate 옵션을 추가하면, 요청 데이터의 마지막 1바이트를 남겨두고 전송을 일시 정지함. 
    engine.queue(request1, gate='race1')
    for x in range(5):
	    # GET 요청 5개도 대기시킴
        engine.queue(request2, gate='race1')

	# 게이트를 오픈해서 대기 중이던 6개(POST 1개 + GET 5개) 요청의 마지막 1바이트가 동시에 서버로 전송됨.
    engine.openGate('race1')

	# 응답이 돌아올 때까지 최대 60초 동안 기다리며 결과 수집
    engine.complete(timeout=60)


def handleResponse(req, interesting):
    table.add(req)
```
- `engine.queue(요청, gate='게이트이름')`: 요청을 큐에 넣고 전송을 시작하지만, **마지막 1바이트 전송을 게이트 앞에서 대기**시킴. 
- `engine.openGate('게이트이름')`: 지정된 게이트를 열어, **대기 중이던 모든 요청의 마지막 1바이트를 동시에 발사**시킴. 


**URL 기반 파일 업로드**
웹상에 있는 이미지 주소(URL)를 입력해서 파일을 업로드 하는 기능이 있는 웹사이트의 경우, 최신 웹 프레임워크들이 제공하는 '임시 디렉토리 저장 -> 검사 -> 메인 디렉토리 전송' 과정을 사용할 수 없으므로 개발자가 직접 구현을 해야함. 여기서 실수가 발생하기 쉬움. 

개발자들은 URL로 가져온 파일을 검사할때 무작위 이름의 임시 폴더를 만들어 저장하지만, 취약한 난수 함수를 사용하거나 개발 편의성을 위해 웹 루트 내에 (외부에서 접근 가능) 저장 한다거나 하는 등의 실수가 있는 경우 공격 당할 수 있음. 

해커는 **악성코드 파일 뒤에 엄청나게 큰 쓰레기 데이터를 이어 붙여서 거대한 파일을 생성**해 서버가 파일을 검사하는 시간을 강제로 늘리고 자신이 폴더 이름을 찍어 맞추고 (브루트포스) 파일을 실행할 시간을 벌 수 있음. 


### 원격 코드 실행 외 공격

서버 측에 스크립트를 업로드하여 원격 코드를 실행하는 공격 외에도 다른 방식으로 공격이 가능함. 

1. 클라이언트 타겟: 서버에서 스크립트를 실행할 수는 없더라도, 클라이언트 측에서 악용될 수 있는 스크립트를 업로드
	- 예: HTML 파일이나 SVG 이미지를 업로드할 수 있다면, `<script>` 태그를 사용하여 XSS 공격을 수행할 수 있음.

2. 서버 파서 타겟: 파일 형식을 파싱하거나 처리하는 과정에서 발생하는 취약점을 악용
	- 예: 서버가 마이크로소프트 `.doc`나 `.xls`와 같은 XML 기반 파일을 파싱한다면, 이는 XXE 주입 공격이 가능할 수 있음.


### PUT 사용

보통 웹사이트에서 사용자가 업로드 버튼을 눌러 파일을 올릴 때는 POST를 사용함. 
POST가 개발자가 직접 정성스럽게 작성한 보안 로직으로 향한다면, **PUT은 종종 웹 서버(Apache, Nginx 등)나 프레임워크가 기본적으로 가지고 있는 파일 쓰기 기능으로 바로 연결**됨. 

**HTTP OPTIONS 요청**
OPTIONS 요청을 보내면 해당 경로로 어떤 HTTP 요청을 보낼 수 있는지 알 수 있음.
- 요청: `OPTIONS /images/ HTTP/1.1`
- 응답: `Allow: GET, POST, OPTIONS, PUT`
