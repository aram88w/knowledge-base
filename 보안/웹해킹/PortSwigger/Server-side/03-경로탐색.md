## 경로 탐색

서버로 파일 요청할때 경로를 조작하여 서버의 임의의 파일을 읽거나 제어권을 확보하는 공격
- 파일 다운로드 및 내보내기
- 페이지 및 템플릿 로딩
- 언어팩(다국어) 및 설정 파일 로딩
- 파일 업로드

### 예시

1. 애플리케이션에서 상대경로로 처리하는 경우: `../../../etc/passwd `
2. 애플리케이션에서 BaseURL + 사용자 입력값을 합칠때 Java, Python, PHP 등에서 제공하는 내장 함수(예: `os.path.join` 또는 `Paths.get`)를 사용하는 경우: `/etc/passwd`
	- 해당 내장 함수들에는 **합치려는 두 번째 값(사용자 입력값)이 `/`로 시작하는 '절대 경로'일 경우, 첫 번째 값(베이스캠프)을 완전히 무시하고 절대 경로만 반환**하는 규칙이 있어서 BaseURL이 무시됨.
3. `../`를 없애는 코드가 있는 경우(재귀적 X): `....//`를 사용, `....//` => `../`로 바뀜.
4. 전체 경로를 서버로 넘기고 경로 시작 부분의 유효성 검사를 하는 애플리케이션인 경우: 필요한 디렉토리 뒤에 경로를 붙임 
	- `filename=/var/www/images/../../../etc/passwd` 
5. 파일명이 특정 확장자로 끝나는지 검사하는 애플리케이션인 경우: **널 바이트**(`\0`)을 사용 
	- `filename=../../../etc/passwd%00.png` (`%00`은 `\0`을 인코딩한 것임.)
6. 경로를 정규 경로로 만들고 (정규화) 경로 시작 부분의 유효성을 검사하는 애플리케이션인 경우: **공격 불가**, Nginx의 취약점이나 URL 인코딩 등을 활용해서 우회해야함.


## URL 인코딩

인터넷 주소(URL)에서 **사용할 수 없는 문자(한글, 공백, 특수문자 `+`, `/`, `=`, `;` 등)** 를 웹 서버가 이해할 수 있는 표준 ASCII 문자열로 변환하는 과정
- 크롬 같은 브라우저는 자동으로 URL 인코딩 처리
- 해커 및 개발자(Burp Suite, 파이썬 코드)는 수동 처리
- HTTP 헤더에서도 사용
- 쿠키에서도 사용

웹 서버나 프레임워크(Tomcat, Apache, Nginx, Node.js 등)는 클라이언트(브라우저 등)로부터 HTTP 요청을 받으면, 애플리케이션 로직(사용자가 작성한 코드)으로 데이터를 넘기기 전에 **URL에 포함된 경로와 파라미터를 자동으로 1회 디코딩**함.
하지만 **실제 서비스 환경이나 보안 랩에서는 프록시(Proxy), 로드 밸런서, 웹 방화벽(WAF) 등 여러 단계의 서버를 거치는 경우가 많음.** 
이중 인코딩은 바로 이 **여러 단계를 거칠 때 발생하는 디코딩 횟수의 차이**를 노리는 우회 기법

### URL 인코딩을 이용한 경로 탐색 공격

- URL 인코딩: 애플리케이션에서 보안 필터에서 `../` 등이 보이면 무조건 차단하는 규칙이 있는 경우, `../` 대신 인코딩된 `%2e%2e%2f`를 보냄. 
- 이중 인코딩: 보안 필터(AWS WAF, Cloudflare WAF, ModSecurity, 리버스 프록시 등)에서 `%2e%2e%2f`도 차단하는 규칙이 있는 경우, `../`을 이중 인코딩해 `%252e%252e%252f`로 공격을 할 수 있음. 
- 비표준 인코딩: 컴퓨터가 글자를 인식하는 '유니코드(Unicode)'의 취약점을 찌르는 것. 슬래시(`/`)를 표현하는 정상적인 방법은 `%2f` 하나지만, 컴퓨터 언어의 버그나 복잡한 체계를 악용하면 비정상적으로 뚱뚱하게 만들어진 슬래시(`%c0%af` 등)를 만들어낼 수 있음.
