## 경쟁 상태 

- **경쟁 상태(Race Conditions)**: 두 개 이상의 프로그램이나 명령이 동시에 실행되면서, 미세한 타이밍이나 순서에 따라 결과가 비정상적으로 달라지는 불안정한 상태
- **경쟁 구간(Race Window)**: 충돌이 발생할 수 있는 시간 간격

경쟁 상태를 이용하면 타이밍을 잘 조절한 요청으로 의도적으로 충돌을 일으켜 공격을 할 수 있음. 경쟁 상태가 일어나는 상황인지 예측 및 생각을 해봐야함. 

1. HTTP/1: **마지막 바이트 동기화** 
	- 준비: 서로 다른 통신로(TCP 연결)를 열고, 각각의 통신로에 마지막 1바이트를 제외한 채 데이터를 미리 보내둔 채 대기 (Block)
	- 요청: 신호가 떨어지면, **각각의 개별 네트워크(TCP) 패킷에 마지막 1바이트를 담아서 동시에 전송**
	- 한계: 출발은 동시에 하지만 네트워크 사정에 따라 서버 도착 시간에 미세한 오차(Jitter)가 생김. 

2. HTTP/2: **단일 패킷 공격**
	- 준비: 1개의 통신로(TCP) 안에 여러 요청을 보낼 수 있음. 각각의 요청의 마지막 1바이트를 제외한 데이터를 미리 쪼개서 1개의 통신로에 보내둔 채 대기 (Block)
	- 요청: 신호가 떨어지면, **나머지 1바이트들을 단 하나의 네트워크 패킷(TCP 패킷)에 담아 동시에 전송**
	- 결과: 네트워크상으로 날아가는 패킷이 오직 1개뿐이므로, 한 치의 오차도 없이 동시에 도착
	- 네트워크의 관점: 1개의 패킷이 날아가므로, 안에 담긴 모든 요청은 서버의 랜카드에 **0.000초의 오차도 없이 완벽하게 동시에 도착**
	- 서버 어플리케이션의 관점: 서버가 이 패킷을 뜯어서 읽을 때는 **위에서부터 아래로(순차적으로)** 읽어들이므로, **패킷을 넣어서 보내는 순서도 중요함.** 


**예시**
장바구니 상태가 서버측에서 저장되야 경쟁 상태를 노려서 할인을 여러번 먹일 수 있음. 
장바구니 상태가 클라이언트측에서 저장되는 경우에는 암호화된 토큰 (보통 JWT 사용) 안에 장바구니 정보가 있고 서버에서 그 토큰을 복호화해서 처리하므로 쿠폰을 여러번 먹이는 로직 자체가 불가능함. 
경쟁 상태를 이용한 공격이 통하는 구조인지 확인이 필요함. 

#### Burp Repeater 그룹 기능

Burp Repeater에서 그룹을 만들고 Send group in parallel 설정을 하면 병렬로 패킷을 보낼 수 있음. 어떤 HTTP 버전을 지원하느냐에 따라 알아서 공격 방식을 바꿔줌. 
서버 앞단에서 패킷을 읽을때 Burp 그룹에 정렬된 탭 순서대로(아주 미세한 차이로) 읽어 들임. 따라서 순서도 중요함. 
보통 **취약점 탐지 및 검증**에서 많이 사용함. 

#### Trubo Intruder 단일 패킷 공격

Turbo Intruder의 gate 옵션을 사용해서 단일 패킷 공격이 가능함. 
실제 공격에서 많이 사용

- 대상 서버가 HTTP/2를 지원하는지 반드시 확인. (단일 패킷 공격은 HTTP/1 호환 X)
- 요청 엔진에 대한 `engine=Engine.BURP2` 및 `concurrentConnections=1` 설정 옵션을 지정
- 요청을 순서대로 처리할 때는, `engine.queue()` 메서드의 `gate` 인수를 사용하여 각 요청을 특정 게이트에 할당함으로써 그룹화 가능
- 특정 그룹에 속한 모든 요청을 보내려면, `engine.openGate()` 방법을 사용하여 해당 게이트를 열면 됨. 


**단일 엔드포인트**
``` python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                            concurrentConnections=1,
                            engine=Engine.BURP2
                            )
    
    # queue 20 requests in gate '1'
    for i in range(20):
        engine.queue(target.req, gate='1')
    
    # send all requests in gate '1' in parallel
    engine.openGate('1')
```

**멀티 엔드포인트**

### 방법론

모든 엔드포인트를 무작위로 찌르는 것은 비효율적임. 시스템의 내부 구조를 추론하고, **정상적인 순차 요청**과 **비정상적인 병렬 요청**의 결과를 비교하여 숨겨진 '다단계 처리 과정'의 결함을 찾아내는 3단계 과학적 접근법.

1. 잠재적 충돌 예측하기 (타겟 선정): 무작정 툴을 돌리기 전에, 개발자의 관점에서 시스템 구조를 상상하고 타겟을 좁히는 단계
	- 보안 중요성 검토: 결제, 비밀번호 재설정, 2차 인증, 권한 부여 등 보안상 중요한 기능(엔드포인트)만 집중적으로 노리기
	- **충돌 가능성 판단 (핵심):** 여러 요청이 **동일한 데이터**를 동시에 수정, 접근하려고 할 때 충돌이 발생할 수 있는 구조인지 예측

2. 단서 찾기 (정찰 및 벤치마킹): 예측한 타겟에 대해 정상적인 상황과 공격 상황을 비교하여 미세한 변화(단서)를 찾아내는 단계
	- 기준점(Benchmark) 확보: Burp Repeater의 '순차 전송(Sequential)'을 이용해 하나씩 정상적으로 요청을 보내고, 서버의 기본 응답 패턴을 기록
	- **단일 패킷 공격(Single-Packet Attack) 실행:** 네트워크 지연을 없애기 위해 '병렬 전송(Parallel)'으로 여러 요청을 완벽하게 동시에 서버로 요청
	- **미세한 변화(단서) 포착:**
	    - 응답 코드(상태 값)의 변화
	    - 응답 데이터의 길이(바이트 수) 차이
	    - 처리 시간의 지연
	    - 내 메일함에 도착하는 이메일 내용의 꼬임 현상 등 평소와 다른 '모든 이상 징후'를 예민하게 관찰

3. 개념 증명 (실제 공격): 실제 치명적인 해킹(계정 탈취, 무한 결제 등)으로 연결하여 취약점을 입증하는 단계
	- 로직 이해 및 최적화: 서버 내부에서 정확히 어떤 하위 상태가 발생했는지 원리를 파악하고, 공격에 필요 없는 불필요한 요청은 덜어냄.
	- 구조적 결함으로의 접근: 이 버그를 단순한 에러 창 띄우기가 아닌, 시스템 전체의 논리를 무너뜨리는 '구조적 약점'으로 활용해 최종 공격 시나리오를 완성


#### 예시

이메일 변경 기능에서 경쟁 상태를 찾아 공격하는 과정

1. 잠재적 충돌 예측하기
	1. `A@email.com`으로 변경 요청 (A 링크를 메일로 받음.)
	2. 이어서 순차적으로 `B@email.com`으로 변경 요청 (B 링크를 메일로 받음.)
	3. 처음 받았던 A 링크를 클릭해 봄. 
	4. 결과: A 링크가 더 이상 유효하지 않음. 
	
	- 예측: 이 서버는 사용자가 이메일 변경 요청을 할 때마다 새로운 요청을 리스트로 계속 쌓아두는 게 아님. **데이터베이스에 '대기 중인 이메일'이라는 칸을 딱 하나만 만들어 두고, 새 요청이 올 때마다 기존 값을 덮어씌워 버림(수정)** 그렇다면 이 덮어쓰는 과정에 동시에 여러 개를 밀어 넣으면 충돌이 날 수도 있음.

2. 단서 획득 (정찰 및 벤치마킹): 20개의 다른 이메일로 변경 요청을 동시(병렬)에 보냄. 
	- 정상적인 경우: `test1@email.com` 주소로 도착한 이메일의 본문 링크는 `test1@email.com`로 변경되어야함. 
	- 발견된 이상 현상: `test1@email.com` 주소로 도착한 본문 링크가 `test15@email.com` 등으로 되어있음. 
	- 추론: `test1@email.com`으로 이메일을 보내려고 준비할때 DB 등에 저장된 '대기 중인 이메일' 값이 `test15@email.com`으로 **덮어씌워졌기 때문**에 본문 내용이 바뀐 것



### 다단계 처리 과정

하나의 요청이 있으면 백그라운드에서 여러 단계에 걸쳐 처리가 됨. 애플리케이션은 여러가지 **중간 상태(하위 상태)** 를 거치며, 요청 처리가 완료될 때까지 그 상태들을 반복적으로 오감. 

동일한 데이터를 접근하는 HTTP 요청이 하나 이상 있다면, 미완성된 **중간 상태**를 노려 원래는 불가능해야 할 시스템의 논리 허점을 노릴 수 있음. 

#### 예시

다단계 인증 (MFA) 로직에서 세션에 2차 인증 관련 값이 정해지기 전, 찰나의 순간에 요청이 들어가면 2차 인증을 받지 않고 다른 곳에 접근을 할 수 있음. 

``` python
# [1단계] 서버: "오, 비밀번호 맞네. 일단 이 세션은 'carlos' 거라고 도장 찍어줌!" 
session['userid'] = user.userid  

# 🚨 [치명적인 틈새 (Race Window 발생)] 🚨
# 이 찰나의 순간, 사용자는 '로그인은 되었지만 2차 인증 자물쇠는 아직 안 채워진' 중간 상태가 됩니다!

# [2단계] 서버: "잠깐, 이 유저 2차 인증 켜져 있나?"
if user.mfa_enabled:
    
    # [3단계] 서버: "켜져 있네! 지금부터 2차 인증(MFA) 자물쇠 채운다! 다 막아!"
    session['enforce_mfa'] = True
```



### 다중 엔드포인트

동시에 여러 엔드포인트에 요청을 보내는 경우
예: 온라인 쇼핑몰에서 '장바구니 주문 요청'이 도착해 결제 확인 및 주문 승인 절차가 수행될때 '장바구니 추가 요청'이 도착하도록 한다면 결제를 하지 않아도 새로운 물건을 구매할 수 있음. 

단일 패킷 기술을 사용하여 요청을 동시에 보낸다 하더라도 각 요청의 처리 순서를 일치시켜 경쟁 상태를 만드는 것이 어려울 수 있음. 
1. **네트워크 아키텍처로 인한 지연**: 처음 TCP 연결을 할때 생기는 지연 
	- 브라우저 <-> 프론트엔드: 웹서버 Nginx, 아파치 (리버스 프록시) 등 <-> 백엔드: WAS
2. **엔드포인트별 처리 과정에서 발생하는 지연**: 각기 다른 엔드포인트들은 수행하는 작업에 따라 서버의 처리 시간에 차이가 있음. 
	- 참고: 장바구니가 비어있을때랑 물건을 넣었을때 주문 요청을 처리하는 지연시간이 달라짐.

**네트워크 아키텍처로 인한 지연인지 엔드포인트별 처리 과정에서 발생하는 지연인지 구분하는 방법**
Brup Repeater 그룹 요청에서 Send group in sequence (single connection) 옵션으로 아무 요청을 첫 요청을 보내면 다음 요청들은 TCP 연결 파이프가 생성되는 지연 시간이 없으므로 정확한 서버의 처리 시간(지연 시간)을 알 수 있음. 



#### 네트워크 아키텍처로 인한 지연에 대한 해결책

1. 클라이언트: 단일 패킷 1개에 여러 HTTP 요청을 담아서 요청 (오차 0초, 이때도 TCP 연결을 하는 시간은 있음.) 
2. 프론트엔드 (Nginx / Cloudflare 등): 패킷을 받아서 깐 후 HTTP 요청을 각각의 백엔드 서버로 보냄. (리버스 프록시)
3. _여기서 TCP 파이프를 20개 새로 뚫으면서 미세한 시간 차이 발생_
4. 백엔드 (Spring Boot, Node.js, Django, Tomcat 등) Nginx가 넘겨준 20개의 요청을 제각각 받아서 비즈니스 로직(결제, 장바구니 등)을 실행함. 
5. 데이터베이스 (MySQL, Oracle 등): 최종 데이터 기록

단일 패킷 공격에서 네트워크 패킷에 HTTP 패킷들을 담아서 동시에 도착하게 하는 것은 프론트엔드(웹 서버)에 도착하게 하는 것임. 여기서 각각의 패킷들을 적절한 백엔드 서버로 보내는데 이때 TCP 연결(파이프)이 필요함. 
이 TCP 연결은 상황에 따라 시간이 달라질 수 있으므로 사전에 파이프를 뚫어놓는 작업(**주요 공격을 수행하기 전에 먼저 Turbo Intruder를 사용하여 연결을 미리 준비하는 요청들을 보내는 방법**)을 해두면 정확도가 올라감. 파이프는 일정 시간 유지가 되고 재사용됨. (보통 5초 ~ 60초)



#### 엔드포인트별 처리 과정에서 발생하는 지연에 대한 해결책

엔드포인트별로 처리 시간이 다르다면, 특정 요청만 Trubo Intruder를 사용해서 클라이언트 측에서 약간의 지연을 유발할 수 있음. 그러나 이런 방식을 사용할 경우에 하나의 네트워크 패킷에 담아서 보내는 단일패킷 공격이 불가하므로, 네트워크 상태에 따라서 결과가 예측할 수 없음. 

**웹 서버는 너무 많은 요청들을 너무 빠르게 전송할 경우, 해당 요청들의 처리를 지연시키는 경향**이 있음. (지연시키는 시간은 그때그때 서버의 상태마다 다를 수 있음.)
따라서 단일패킷 공격은 유지하되, 의도적으로 많은 수의 가짜 요청들을 보내서 원하는 만큼의 서버 측 지연 효과를 얻을 수 있음. (시간을 맞출 수 있음.)

**예시**
1. 영점 조절: 가짜 요청을 5개 넣어서 쏴봄. 확인해 보니 'fast(장바구니)'가 여전히 'slow(결제)'보다 먼저 끝남. (지연 부족) 이번엔 가짜 요청을 20개 넣어서 쏴봄. 'fast'가 너무 늦게 시작해서 결제가 먼저 끝남. (지연 초과)
2. 범위 좁히기: 대충 타이밍이 겹치는 가짜 요청의 개수(약 10~12개쯤)의 평균 범위를 찾음. 
3. 반복 공격: 가짜 요청 10~12개를 세팅한 단일 패킷 공격을 여러 번 반복해서 쏨. 서버의 처리 시간이 40ms~80ms 사이에서 요동치다가, 어느 순간 오차가 딱 맞아떨어지면서 'slow'와 'fast'가 정확히 겹치는 찰나(레이스 윈도우)가 발생하고 공격이 성공함.



### 단일 엔드포인트

서로 다른 값을 가진 요청들을 동시에 같은 엔드포인트에 보내는 경우, 경쟁 상황이 발생할 수 있음. 
예: 비밀번호 재설정, 이메일 재설정


### 윈도우 레이스 정렬

1. Repeater 탭의 순서
	- Burp Repeater의 'Send group in parallel'을 이용해서 단일 패킷 공격을 하는 경우에도, 그룹 내의 **탭 순서**가 매우 중요함.
	- 단일 패킷 공격이라 하더라도, 네트워크 소켓에 데이터를 기록할 때는 탭이 배치된 순서대로 바이트(Byte)가 쌓이고, 서버 역시 그 순서대로 파싱을 함. 

2. 서버 웜업
	- 처음 TCP 연결(파이프)을 하는 지연 시간이 있음.
	- 대부분의 웹 서버 프레임워크나 데이터베이스는 일정 시간 요청이 없으면 리소스를 아끼기 위해 절전(휴면) 상태에 들어가는데 이 시기와 맞물리면 요청이 DB 연결을 맺고 클래스를 로딩하느라 지연 시간이 생김.
	- 해결책: 공격을 하기 전에 **의미 없는 정상 요청(예: `GET /` 메인 페이지 호출)을 몇번 보내서 연결을 활성화** 시킨 후 공격 패킷 전송

3. 요청 패킷 수를 늘려서 서버 지연을 노리기
	- **웹 서버는 너무 많은 요청들을 너무 빠르게 전송할 경우, 해당 요청들의 처리를 지연시키는 경향**이 있음. (지연시키는 시간은 그때그때 서버의 상태마다 다를 수 있음.)
	- 따라서 단일패킷 공격은 유지하되, 의도적으로 많은 수의 가짜 요청들을 보내서 원하는 만큼의 서버 측 지연 효과를 얻을 수 있음. (시간을 맞출 수 있음.)
	- **참고**: 단일패킷 공격에서 하나의 네트워크 패킷에 최대 한도까지 HTTP 패킷을 넣을 경우, 여러 네트워크 패킷에 나뉘어져 요청이 들어감. 

4. Turbo Intruder를 이용한 정밀한 지연 시간 주입
	- 단일패킷 공격을 포기하고 각각 요청을 보내면서 `time.sleep(0.01)` 같은 딜레이를 이용하는 방법
	- 각각의 요청이 TCP 연결을 맺기 때문에 Jitter가 달라지므로, 결과를 예측할 수 없음. 



### 세션 기반 잠금 메커니즘

일부 프레임워크(PHP 등)는 **서버가 동일한 세션 ID로 들어온 요청들은 병렬로 처리하지 않고 순차적으로 처리함.** 
PHP는 세션 잠금이 기본으로 작동하고 다른 프레임워크(Spring, Python, Node.js)에서는 기본적으로는 세션 잠금을 강제하지는 않지만 개발자가 설정할 수 있음. 

서버 입장에서 한 사용자(동일한 세션 쿠키)가 동시에 두 개의 요청을 보내면, 세션 데이터(예: 장바구니, 유저 상태 등)를 동시에 수정하려다 데이터가 꼬일 수 있기 때문에, **요청 1이 들어오면 해당 세션을 잠그고(Lock), 요청 1의 처리가 끝날 때까지 요청 2를 대기시킴.**

단일패킷 공격을 할때는 항상 세션 잠금에 대해서 생각해야함. 


### 부분 생성 경쟁 조건

많은 애플리케이션들은 **여러 단계에 걸쳐 객체를 생성**하는데, 이 과정에서 해당 객체가 악용될 수 있는 임시 상태가 만들어질 수 있습니다.

예를 들어, 새로운 사용자를 등록할 때, 애플리케이션은 DB에 해당 사용자를 생성하고, 사용자를 식별하기 위한 API 키를 생성해서 DB에 저장함. 찰나의 순간에 사용자는 DB에는 존재하지만, **API 키는 아직 초기화되지 않은 상태(`null`과 같은 값)** 가 생김. 이때 `null`을 일치시켜서 공격할 수 있음. 

PHP: `param[]`은 `param = []`로 처리됨.
- `/confirm?token[]` => `token = []`: `strcmp(null, []) == 0`인 경우에 `strcmp(null, [])`가 에러가 나서 `null`이므로 최종적으로 `true`가 나와서 뚫을 수 있음.
- `/confirm?token[]=` => `token = [""]`
- `confirm?token=` => `token = ""`: `null == ""`인 경우에 `true`이므로 뚫을 수 있음.
JSON: `{"token": null}`, `{"token": []}` 


### 타임스탬프 기반 토큰 예측

암호학적으로 안전한 난수를 사용하는 대신 **타임스탬프(시간)를 기반으로 보안 토큰을 생성하는 경우**에 취약점이 발생함. 현대의 웹사이트에서는 난수를 만들어주는 도구가 있어 더 편리하지만, 레거시 시스템에서는 랜덤값을 만들때 종종 현재시간을 이용하는 경우가 있었음.

예시: 비밀번호 재설정 토큰을 타임스탬프로 발급하는 경우, 단일패킷 공격을 이용해서 다른 사용자의 비밀번호 변경 토큰의 값을 발급받아 공격할 수 있음. 

**해커가 타임스탬프로 만들어진 것인지 추측하는 단계**
1. 토큰의 형태 분석: 토큰이 32, 40, 64자리의 고정된 길이를 가진 16진수 문자열(0~9, a~f)로 이루어져 있다면, 어떤 데이터를 해시한 값이라고 추측할 수 있음. (물론 그냥 난수일 수도 있음.)
2. 변화 요인 찾기: 같은 사용자(wiener)가 재설정을 요청해도 매번 다른 해시값이 나옴. 해시 함수 안에 매번 변하는 동적인 값이 포함되어 있다고 추측할 수 있음. (물론 그냥 난수일 수도 있음.)
3. 세션 잠금을 우회하여 두 요청을 병렬로 요청했을때, 똑같은 토큰값을 받은 경우에는 타임스탬프로 토큰을 만들 가능성이 굉장히 높음. 

*참고: 세션 잠금을 생각해서 각 요청이 독립적인 세션과 상태를 유지하도록 구성해야함. *
