## 정보 노출 취약점

정보 노출이란, 웹사이트가 의도치 않게 사용자들에게 민감한 정보를 공개하는 것을 말함.

- 사용자명이나 금융 정보와 같은 다른 사용자에 관한 데이터
- 민감한 상업적/비즈니스 관련 데이터
- 웹사이트 및 그 인프라에 관한 기술적 세부 사항

만감한 사용자 정보나 비즈니스 데이터가 유출되는 건 위험성이 명백함. 
기술적 정보가 유출되는 것은 그다지 위험하지 않아 보이지만, 다른 취약점들을 발견하는데 도움이 될 수 있음.
*민감한 데이터는 여러 곳에서 유출될 수 있으므로, 특정 취약점에만 과도하게 집중하지 않고 웹사이트가 던져주는 모든 조각(응답 데이터, 에러, 소스코드)에서 민감한 데이터를 발견하는 능력을 키워야함.*


### 정보 노출의 원인

1. 웹 크롤러를 위한 파일: `/robots.txt`, `sitemap.xml`에는 일반적으로 크롤러가 건너뛰어야할 특정 경로(민감한 데이터를 관리하거나 관리자 권한을 가진 경로)가 명시되어 있음. 접근하면 안되는 경로들을 알 수 있음.
	- `도메인주소/robots.txt`으로 접속
	- `/robots.txt`: 검색엔진 크롤러(로봇)에게 웹사이트 방문 규칙을 알려주는 텍스트 파일
	- `/sitemap.xml`: 구글, 네이버 같은 검색엔진 크롤러(웹 로봇)가 웹사이트 내 모든 페이지 정보를 효율적으로 수집하고 색인할 수 있도록 돕는 **웹사이트의 목차** 파일

2. 디렉토리 리스팅
	- `example.com/admin/`처럼 디렉토리 이름까지만 치고 들어가면, 웹 서버는 보통 약속된 기본 파일인 `index.html`이나 `index.php`를 화면에 보여줌. 
	- 그런데 폴더 안에 `index.html`을 두지 않은 경우 해당 폴더 내의 모든 파일과 폴더의 목록이 보여짐. 
	- 요즘의 프레임워크들은 자동적으로 이런 현상을 방지하지만, 옛날 방식의 **Nginx나 Apache를 리버스 프록시로 둘때** 설정을 깜빡한 경우나 **클라우드 저장소(예: AWS S3)의 권한 설정 실수**로 취약점이 발견됨. 

3. 개발자의 코멘트: HTML 파일에 **개발자가 작성해둔 주석**에서 중요한 정보를 얻을 수도 있음. 보통 프로덕션 환경에서는 배포 전에 제거됨. Burp나 브라우저의 개발자 도구를 사용해서 쉽게 확인할 수 있음. 

4. 오류 메시지: 지나치게 상세한 오류 메시지들을 통해 정보를 얻을 수 있음. 
	- 특정 파라미터에 어떤 형태의 입력 또는 데이터가 필요한지 
	- 템플릿 엔진, 데이터베이스 유형, 서버의 종류 및 버전 번호 
	- 오픈소스 프레임워크 종류

5. 디버깅 데이터: 디버깅을 위해, 애플리케이션의 동작에 대한 다양한 정보를 포함한 오류 메시지와 로그가 운영 환경에서 노출된다면 공격자에게 매우 유용한 정보가 됨. 
	- **사용자 입력을 통해 수정할 수 있는 세션 변수의 값들**
		- 예: 디버그 창에 `[Current Session: {"username":"test", "role_id": 0, "is_admin": false}]` 라고 뜬 것을 발견하면 해커는 이걸 보고 권한을 올리려면 `is_admin`이라는 단어를 `true`로 조작해서 서버에 보내면 된다는 것을 알 수 있음
	- **백엔드 구성요소들(DB나 내부 서버 등)을 위한 계정 정보**
	- **서버상의 파일 및 디렉토리 이름들**
	- **클라이언트 전송 데이터를 암호화하는 데 사용되는 키**
	- **디버깅 정보를 기록하는 별도의 파일**
		- 에: 해커가 눈에 보이지 않는 취약점(블라인드 SQL 인젝션 등)을 공격할 때 내가 찌른 공격이 먹히고 있는지 확인할 수 있음.

6. 사용자 프로필 및 계정 페이지: `user` 파라미터를 기준으로 다른 사용자 프로필에 접근할 수도 있음. 대부분의 웹사이트는 이런 부분의 방어 코드를 작성해둠. 하지만 때로는 특정 데이터를 불러오는 로직은 방어 코드가 견고하지 않을 수 있음. 
	- 예: 계정 페이지에서 이메일을 가져오는 API 요청(예: `/api/get-email?user=carlos`)은 `user`와 일치하는지 확인을 하지 않을 수 있음. 이런 경우 다른 사용자의 정보가 노출됨. 

7. 백업 파일을 통한 소스 코드 유출
	- 기본적으로 브라우저에서 확인 할 수 있는 소스 코드는 화면에 보여지는 HTML, CSS, JS 파일뿐임.
	- 리눅스 서버에서 **직접 리눅스 편집기(`vi`나 `nono`)로 코드를 수정하면 `~` 혹은 `.bak`가 붙은 임시 백업 파일을 만드는데** 이것을 지우지 않는 경우, 공격자가 해당 파일을 요청했을때 서버에서 텍스트 파일로 인식하고 보여줌. 
	- 공격자는 `robot.txt`나 다른 정보들에서 얻은 파일명을 이용해서 백업 파일을 찾아야함.

8. 설정 실수: 제3자의 기술(Nginx, Tomcat, AWS 등)을 사용하면 설정이 복잡하고 메뉴얼이 매우 길기 때문에, 뭘 끄고 뭘 켜야 안전한지 완벽히 이해하지 못한 채 일단 기본 설정으로 놔두는 경우가 흔함. 
	- **리버스 프록시가 사용되는데 HTTP TRACE 설정이 켜져 있는 경우**에 공격자가 빈 HTTP TRACE 요청을 보내면 리버스 프록시를 거치면서 내부에서 사용되는 토큰이나 인증 정보를 추가되므로 해당 정보를 응답을 받을 수 있음. 

9. Git 버전 관리 기록: `.git` 폴더가 운영 환경에서 노출되는 경우, `/.git`으로 해당 디렉토리에 접근할 수 있고 전체 `.git` 디렉토리를 다운해서 **커밋된 변경 사항** 등을 확인할 수 있음.
	- 재귀적 다운로드 명령어: `wget -r https://YOUR-LAB-ID.web-security-academy.net/.git/`
