## 접근 제어

웹사이트 보안 시스템
1. 인증: 로그인 창에 아이디와 비밀번호를 입력하여 자신이 'user1'임을 증명하는 과정
2. 세션 관리: HTTP는 매 요청마다 사용자를 잊어버리는(Stateless) 특성이 있음. 그래서 로그인에 성공하면 '세션 쿠키'나 '토큰'을 발급해 주고, 이후 페이지를 이동할 때마다 다시 로그인하지 않아도 누군지 식별할 수 있게 해줌.
3. **접근 제어**: 세션을 통해 당신이 'user1(일반 회원)'인 것은 확인했지만, 관리자 전용 페이지인 `/admin/deleteUser`에 접속하려고 할 때 이를 차단하는 결정 과정

종류 
1. **수직 접근 제어**: 특정 유형의 사용자에게만 중요한 기능에 대한 접근을 제한 
	- 예: 일반 사용자는 관리자 페이지에 접근 불가
2. **수평 접근 제어**: 서로 다른 사용자가 동일한 유형의 리소스에 대해 특정 하위 집합에 대한 접근 권한을 가짐. 
	- 예: 은행 앱에서 자신의 계좌 거래 내역을 조회할 수 있지만, 다른 사용자의 계좌에는 접근 불가
3. **컨텍스트 종속 접근 제어**: 애플리케이션의 상태 또는 사용자의 상호 작용에 따라 기능 및 리소스에 대한 접근 제한 (잘못된 순서로 작업을 수행하는 것을 방지)
	- 예: 쇼핑몰에서 결제를 완료한 후 장바구니 내용을 수정하지 못하도록 제한

### 수직적 권한 상승

만약 사용자가 자신에게 허용되지 않은 기능에 접근할 수 있다면, 이는 수직 권한 상승임. 
예: 관리자가 아닌 사용자가 관리자 페이지에 접근하여 다른 사용자의 계정을 삭제

#### 보호되지 않은 기능

`/admin` 등의 관리자 페이지가 보호되지 않아 그냥 접근이 가능할 수 있음. 
`robots.txt`나 소스 코드 내에서 관리자 페이지에 대한 URL 정보를 찾을 수 있음.

#### 매개변수 기반 접근 제어 방식

1. 쿠키: 쿠키 `Admin=false` 등이 있다면 `true`로 바꾸면 관리자 권한으로 상승 됨.
2. 쿼리 문자열 매개변수: `https://insecure-website.com/login/home.jsp?role=2` 등
3. 숨겨진 필드: POST 요청 본문에 `"roleid":2` 넣어서 보내는 경우 권한이 상승 됨. 

#### 플랫폼의 잘못된 설정으로 인한 접근 제어 기능의 오작동

- 플랫폼의 예시: 웹 서버(Nginx, Apache), 웹 방화벽(WAF), API 게이트웨이, 보안 프레임워크
- 예를 들어 보안으로 웹 서버 설정 파일에 `DENY: POST, /admin/deleteUser, managers`와 같은 설정만 되어있다면 취약점이 될 수 있음.

1. 일부 애플리케이션 프레임워크는 `X-Original-URL` 나 `X-Rewrite-URL` 와 같이, 원본 요청에 포함된 URL을 대체하는 데 사용될 수 있는 다양한 비표준 HTTP 헤더를 지원
2. GET, PUT 등의 다른 HTTP 메서드로 우회 (해당 엔드포인트에서 모든 HTTP를 받는 코드인 경우, 예: 스프링의 `@RequestMapping("/admin-roles")`)
3. URL 일치 오류: 일부 환경이나 설정으로 되어있는 경우에 URL에서 대소문자를 구분하지 않는 경우가 있음. 
	- `/ADMIN/deleteUser`로 보안 필터를 우회해서 `/admin/deleteUser`로 매핑 가능
	- `/admin/deleteUser/`로 보안 필터를 우회해서 `/admin/deleteUser`로 매핑 가능


### 수평적 권한 상승

수평적 권한 상승이란, 사용자가 자신이 소유한 자원이 아닌, 다른 사용자가 소유한 자원에 접근할 수 있게 되는 경우
예: 한 직원이 자신의 기록뿐만 아니라 다른 직원들의 기록에도 접근

#### 요청 파라미터로 사용자 프로필 페이지 접근

- `/my-account?id=carlos` 등으로 다른 사용자 계정으로 로그인할 수 있음.
- 만약 사용자 ID가 이름 대신 예측할 수 없는 전역 고유 식별자(GUID) 등을 사용하는 경우, 다른 사용자 관련 정보가 저장되는 곳 (예: 사용자 게시글, 메시지, 리뷰 등)에서 노출될 수 있음.
- `/my-account?id=carlos`으로 다른 사용자의 정보에 접근할때 로그인 페이지로 리다이렉트 하는 경우, 리다이렉트 정보를 담은 응답 데이터에 해당 사용자의 정보가 포함될 수 있음.


### 불안전한 직접 객체 참조 IDOR

애플리케이션이 사용자가 제공한 입력을 이용해 객체에 직접 접근할 때 발생하는 접근 제어 취약점
사용자가 제어하는 매개변수 값이 자원이나 함수에 직접 접근하는 데 사용되는 경우가 많습니다. 이러한 것이 바로 접근 제어 취약점 중 하나임. 

1. 데이터베이스 객체를 직접 참조하는 IDOR 취약점
	- 예: `https://insecure-website.com/customer_account?customer_number=132355`
2. 정적 파일을 직접 참조하는 IDOR 취약점
	- 예: `https://insecure-website.com/static/12144.txt`


### 다단계 프로세스 접근 제어 취약점

많은 웹사이트들은 중요한 기능들은 여러 단계를 거치게 되는데, 특정 단계들에 대해서는 엄격한 접근 제어가 이루어지지만 다른 단계들에 대해서는 그러한 제어가 이루어지지 않는 경우가 있음. 

1. 특정 사용자에 대한 정보가 포함된 양식을 불러옵니다.
2. 변경 사항을 제출하세요.
3. 변경 사항을 확인하고 승인해 주세요.

예를 들어, 사용자 정보를 업데이트 하는 작업에서 1단계와 2단계를 생략하고 3단계에서 필요한 매개변수들을 직접 전송함으로써 원하는 기능에 접근할 수 있음. 


### 참조자 기반의 접근 제어 

일부 웹사이트들은 HTTP 요청에 포함된 `Referer` 헤더를 기반으로 접근 제어를 수행함. 
예를 들어, 어떤 애플리케이션은 `/admin` 에 위치한 메인 관리 페이지에 대해서는 엄격한 접근 제어를 수행하지만, `/admin/deleteUser` 과 같은 하위 페이지의 경우에는 `Referer` 헤더만을 확인함. 만약 `Referer` 헤더에 메인 `/admin` URL이 포함되어 있으면, 해당 요청은 허용됨.


### 위치 기반 접근 제어

일부 웹사이트는 사용자의 지리적 위치를 기준으로 접근 제어를 수행함. 
웹 프록시나 VPN을 사용하거나, 클라이언트 측의 지리적 위치 정보를 조작함으로써 이런한 접근 제어를 우회할 수 있음.
