## 웹 캐시 기만

웹 캐시 서버와 웹 서버가 URL을 다르게 해석할때 발생하는 취약점을 이용한 공격

**예시**
1. 해커가 특정 사용자에게 `/profile;a.js`로 요청을 보내도록 유도함. 
2. 웹 서버에서는 `;a.js` 부분을 무시하고 `/profile` 경로로 인식해서 처리함. 
3. 웹 캐시 서버에서는 `.js`를 보고 캐싱 대상으로 인식하고 캐시 서버에 저장
4. 그 이후에 해커가 `/profile;a.js`로 요청을 하면 캐시서버에서 사용자의 정보를 손쉽게 얻을 수 있음.


### 웹 캐시

캐시 서버를 설정해둔 경우 (리버스 프록시로 직접 구축 or CDN 사용) 모든 요청은 캐시 서버에 먼저 거치게 되고 캐시 서버에 존재하는 정적 리소스 같은 경우에 바로 제공함으로써 전송 속도를 높임. 
만약 캐시 서버에 존재하지는 않거나 만료된 경우, 원본 서버로 요청을 보내고 캐싱을 하고 데이터를 반환함. 

- 캐시 키: 캐시되는 데이터를 구분하기 위한 키, HTTP 요청의 정보(URL 경로, 쿼리 파라미터, 헤더나 콘텐츠 유형 등)를 기반으로 생성됨. 
- 캐시 규칙: 어떤 데이터를 캐시할지 정하는 규칙, 보통 동적 리소스는 캐시하지 않음. 
	1. **정적 파일 확장자 규칙**: `.css`, `.js`처럼 파일 확장자를 설정
	2. **정적 디렉토리 규칙**: `/static`, `/assets`처럼 정적 리소스만을 포함하는 특정 디렉토리를 대상 설정
	3. **파일명 규칙**: `robots.txt`, `favicon.ico`처럼 파일 이름으로 설정


### 웹 캐시 기만 공격 구성

일반적으로, 기본적인 웹 캐시 기만 공격을 구현하는 데에는 다음과 같은 단계들이 필요

1. 민감한 데이터를 반환하는 엔드포인트 찾기
	- GET, HEAD, OPTIONS 방식의 엔드포인트를 주목하기
	- 일반적으로 POST 같이 원본 서버의 상태를 변경하는 요청들은 캐시되지 않음. 
2. **캐시 서버와 원본 서버가 URL 경로를 해석하는 방식에 차이가 있는지 확인**
	- **URL 경로 매핑**: `/users/123/foo.js`이라는 요청이 왔을 때, 캐시 서버는 `foo.js`을 파일이나 폴더 이름으로 생각할 수 있지만, 백엔드 원본 서버는 `foo.js`를 경로 매개변수로 인식할 수 있음.
	- **구분 기호 처리**: 특수 기호(`;`, `?`, `#`, `%00` 등)를 만났을 때 서버가 어디까지를 진짜 URL로 읽고, 어디서부터 자를지 결정하는 방식에 차이
	- **경로 정상화**: 상위 폴더로 이동하는 `../` 기호나, 현재 폴더를 뜻하는 `./` 기호가 URL에 섞여 있을 때, 서버가 이를 깔끔한 경로로 정리(정상화)하는 방식의 차이. 예: `/static/../profile`
		- 캐시 서버: 맨 앞이 `/static`으로 시작하니까 캐시함. 
		- 원본 서버: `../` 기호를 계산해서 `/profile`로 인식함. 
3. 동적으로 생성된 민감한 데이터 응답을 캐시에 저장하도록 속이는 악성 URL 생성
	- 피해자가 해당 URL에 접속하도록 유도함. 
	- 동일한 요청을 해커가 보내면 캐시된 응답을 가져올 수 있음. 
	- 브라우저로 요청할 경우, 세션 때문에 리다이렉션을 보낼 확률이 높으므로 Burp 같은 도구를 사용


#### 응답 헤더를 통해 해당 리소스가 캐시된 것인지 구분하는 방법

`X-Cache` 헤더는 응답이 캐시에서 제공된 것인지에 대한 정보를 제공함. 
- `X-Cache: hit`: 해당 응답은 캐시에서 제공됨.
- `X-Cache: miss`: 캐시에는 해당 요청과 관련된 정보가 저장되어 있지 않았기 때문에, 원본 서버에서 데이터를 가져옴. 대부분의 경우 이후에는 해당 응답 데이터가 캐시에 저장됨. 
- `X-Cache: dynamic`: 원본 서버가 콘텐츠를 동적으로 생성함. 캐시 X
- `X-Cache: refresh`: 캐시된 콘텐츠가 오래되어 업데이트하거나 다시 검증함. 

`Cache-Control` 헤더는 원본 서버에서 캐시 서버에 얼마 동안 캐싱하라고 하는 부탁임. 
- 예: `Cache-Control: max-age=3600`, 캐시 서버에 3600초 동안 보관하라는 부탁임. 
- 캐시가 될 가능성이 있지만 캐시 서버에서 무시하고 저장을 안 할 수도 있으므로 확인이 필요함. 


### 정적 파일 확장자 캐시 규칙 악용

캐시 규칙은 대개 `.css` 이나 `.js` 과 같은 일반적인 파일 확장자를 기준으로 정적 리소스를 식별함. 이는 대부분의 CDN에서 기본적으로 적용되는 방식임.

#### URL 경로 매핑 불일치

URL 경로 매핑은 URL 경로를 서버상의 파일, 스크립트, 명령어 실행과 같은 리소스들과 연결하는 과정임. 다양한 프레임워크들은 각기 다른 매핑 방식을 사용함. 

- 전통적인 URL 매핑: 파일 시스템에 위치한 특정 리소스로 가는 직접적인 경로를 나타냄. 
	- 예: `http://example.com/path/in/filesystem/resource.html`는 `http://example.com` 서버의 `/path/in/filesystem/` 디렉토리의 `resource.html` 파일을 가리킴. 
- RESTful URL 매핑: 물리적인 파일 구조와 직접적으로 일치하지 않고 파일 경로를 API의 논리적인 구성 요소로 변환
	- 예: `http://example.com/path/resource/param1/param2`에서 `param1` 과 `param2` 은 서버가 요청을 처리하는 데 사용하는 **경로 매개변수**임. 


**캐시 서버와 원본 서버가 URL 경로를 리소스에 매핑하는 방식에 차이**가 있으면, 웹 캐시 관련 취약점이 발생할 수 있음.

에: `http://example.com/user/123/profile/wcd.css`
- **원본 서버 - RESTful URL 매핑**: `/user/123/profile` 엔드포인트에 대한 요청으로 해석하고, `wcd.css` 는 중요하지 않은 매개변수로 간주하여 무시한 채, 사용자 `123` 의 프로필 정보를 반환
- **캐시 서버 - 전통적인 URL 매핑**: `/user/123` 디렉토리 내의 `/profile` 폴더에 위치한 `wcd.css` 이라는 파일에 대한 요청으로 간주함. 만약 `.css`인 요청들에 대한 응답이 캐싱되도록 설정이 되어있다면 해당 프로필을 CSS 파일인 것처럼 캐시 저장하고 제공함. 


##### 악용

1. 원본 서버의 특정 엔드포인트에서의 URL 매핑 방식 테스트
	- `/api/orders/123` 요청을 `/api/orders/123/foo`으로 수정해도 주문 정보가 그대로 반환된다면 `foo`를 경로 매개변수로 처리되고 무시된다는 뜻임. 
2. 캐시 서버의 URL 매핑 방식 테스트 + 캐싱 규칙 파악
	- `/api/orders/123/foo` 요청을 `/api/orders/123/foo.js` 으로 변경했을때 응답이 캐시된 상태라면 전통적인 URL 매핑을 사용하고 `.js` 확장자는 캐싱되는 규칙이 있다는 뜻임. 
3. 피해자가 `/my-account/foo.js` 같은 경로에 접속해서 피해자의 정보를 캐싱하도록 유도
	- 해커가 서버를 따로 파서 `/my-account/foo.js` 같은 경로로 리다이렉트 되도록 설정함.
		- `<script>document.location="https://target.com/my-account/foo.js"</script>`
	- 혹은 해커가 자신의 서버(블로그, 커뮤니티 글 등) HTML 코드 안에 아래 같은 코드를 숨겨서 사이트에 들어오기만 해도 해당 경로로 GET 요청이 가도록 함. 
		- `<img src="https://target.com/my-account/foo.js" width="0" height="0">` 


#### 구분 기호 처리 불일치

구분 기호는 URL 내의 여러 요소들 사이의 경계를 나타냄. 다양한 프레임워크나 기술에 따라 구분 기호의 사용 방식에 차이가 있을 수 있음.

**캐시 서버와 원본 서버가 구분 기호로 문자나 문자열을 사용하는 방식에 차이**가 있으면, 웹 캐시 관련 취약점이 발생할 수 있음.


##### 예시

`/profile;foo.css` 같은 경로가 있을때 
- Spring 프레임워크: **`;` 를 사용하여 매트릭스 변수라고 불리는 파라미터들을 지정하므로 구분 기호로 해석**함. 즉, `/profile` 이후는 무시함. 
- 다른 대부분의 프레임워크: `;`를 구분 기호로 처리하지 않음. 만약 `.css`를 캐싱하도록 설정되어 있다면 다른 사용자의 프로필 정보를 캐싱해서 가져오는 공격을 할 수 있음. 

Ruby on Rails 프레임워크
- `/profile` 엔드포인트가 기본 HTML 포맷터에 의해 처리되도록 작성되어 있는 경우
- `/profile.css`: CSS는 Ruby on Rails가 알고 있는 확장자지만, HTML 포맷이 아닌 경우 에러가 발생함. 
- `/profile.ico`: `.ico`은 기본 확장자로 등록되어 있지 않음. 이런 경우에 **`.ico`를 무시하고 `/profile`로 처리**함. 

`/profile%00foo.js` 같은 요청이 있을때 
- **OpenLiteSpeed** 서버 (Apache, Nginx, Tomcat 등과 같은 웹 서버 소프트웨어): 인코딩된 빈 문자 `%00`를 구분 기호로 사용, `/profile`로 처리됨.
- 대부분의 다른 프레임워크: URL에 `%00`가 포함되면 오류 반환
- **Akamai나 Fastly** (Cloudflare, AWS CloudFront와 같은 세계 최상위권 CDN(콘텐츠 전송 네트워크) 기업): `%00` 및 그 뒤에 오는 모든 내용을 경로로 해석


##### 악용

1. 대상 엔드포인트 리다이렉션 여부 파악
	- 예:`/settings/users/list` 대신 `/settings/users/listaaa` 등을 넣어봤을때 원래의 응답과 동일하다면 리다이렉션이 되고 있음 의미함. 다른 엔드포인트를 찾아야함. 
2. 원본 서버의 URL 구분 기호 테스트: `/settings/users/list;aaa` 처럼 `;` 문자를 추가해봄.
	- 만약 기본 응답과 동일하다면, `;` 문자가 구분 기호로 사용되고 있고 원본 서버가 해당 경로를 `/list`로 해석함.
	- 만약 해당 경로가 기본 응답과 다르다면, `;` 문자가 구분 기호로 사용되지 않고 원본 서버가 `/list;aaa`로 해석함. 
3. 캐시 서버의 URL 구분 기호 테스트: 
	- 일반적으로 캐싱이 되는 확장자 목록을 기반으로 구분 기호를 추가해서 요청. 예: `/list;aaa.js`
	- 아래와 같은 경우에 공격이 가능
		- 캐시 서버: 구분 기호를 처리하지 않아서 `/list;aaa.js`로 해석해서 캐싱을 함. 
		- 원본 서버: 구분 기호를 처리해서 `/list`로 해석하고 해당 엔드포인트의 결과를 반환함. 
4. 피해자가 `/list;aaa.js` 같은 경로에 접속해서 피해자의 정보를 캐싱하도록 유도
	- 해커가 서버를 따로 파서 `/list;aaa.js` 같은 경로로 리다이렉트 되도록 설정함.
		- `<script>document.location="https://target.com/list;aaa.js"</script>`
	- 혹은 해커가 자신의 서버(블로그, 커뮤니티 글 등) HTML 코드 안에 아래 같은 코드를 숨겨서 사이트에 들어오기만 해도 해당 경로로 GET 요청이 가도록 함. 
		- `<img src="https://target.com/list;aaa.js" width="0" height="0">` 
	- **주의: 피해자의 브라우저에서 구분 기호를 자동으로 URL 인코딩하고 그걸 서버에서 디코딩 하지 않아 구분 기호로 인식이 되지 않을 수도 있음을 고려해야힘.** 

구분기호 리스트: https://portswigger.net/web-security/web-cache-deception/wcd-lab-delimiter-list



#### 구분 기호 디코딩 불일치

일부 파서들은 URL을 처리하기 전에 먼저 디코딩을 함. 만약 구분 기호로 사용되는 문자가 디코딩된다면, URL 경로가 잘림. 
**캐시 서버와 원본 서버가 디코딩을 하는 방식에 차이**가 있으면 웹 캐시 기만 취약점이 발생할 수 있음. 


##### 예시

URL 인코딩된 `#` 기호를 사용하는 `/profile%23wcd.css` 경우
- 원본 서버: `%23` 을 `#` 로 디코딩함. 구분 기호로 `#` 를 사용하므로, 경로를 `/profile` 으로 해석하여 프로필 정보를 반환
- 캐시 서버: `#` 문자를 구분 기호로 사용하지만, `%23` 는 디코딩하지 않음. 해당 경로를 `/profile%23wcd.css` 로 해석하고 `.css` 캐싱 규칙이 있으면 해당 응답을 캐싱함. 

일부 캐시 서버는 먼저 인코딩된 URL에 따라 캐시 규칙을 적용한 다음, URL을 디코딩하여 원본 서버로 전송함. 
- 캐시 서버: 인코딩된 경로 `/myaccount%3fwcd.css` 에 따라 캐시 규칙을 적용. `.css` 확장자에 해당하는 캐시 규칙이 있으므로, 서버는 해당 응답을 캐시하기로 결정. 그 후, 서버는 `%3f` 를 `?` 으로 디코딩한 뒤, 재작성된 요청을 원본 서버로 전송함. 
- 원본 서버: `/myaccount?wcd.css` 라는 요청을 받음. 원본 서버는 `?` 이라는 문자를 구분 기호로 사용하므로, 해당 경로를 `/myaccount` 로 해석함. 


##### 악용

- 캐시 서버에서는 정적 파일 확장자가 인식되고 원본 서버에서는 디코딩으로 인해 해당 확장자를 인식하지 못하는 URL을 찾아야함. 
	- 예: `/profile%23wcd.css`
- 인코딩된 비표시 문자도 활용해볼 수 있음. 원본 서버의 백엔드 언어(C, C++, 구버전 PHP 등)가 해당 문자들을 만났을때 뒷부분을 강제로 잘라버리는 고질적인 특징이 있음. 
	- `%00`: 아무것도 없음을 의미
	- `%0A`: 엔터키, 줄바꿈
	- `%09`: 탭 키
- **주의: 피해자의 브라우저에서 구분 기호를 자동으로 URL 인코딩하고 그걸 서버에서 디코딩 하지 않아 구분 기호로 인식이 되지 않을 수도 있음을 고려해야힘.** 



### 정적 디렉토리 캐시 규칙 악용

웹 서버에서 정적 리소스를 특정 디렉토리에 저장하는 것이 일반적인 방법임. 
캐시 규칙들은 `/static` , `/assets` , `/scripts` , `/images` 와 같은 특정 URL 경로 접두사와 일치시켜 해당 디렉토리를 대상으로 함. 

**캐시 서버와 원본 서버가 URL을 정규화하는 방식에 차이**가 있으면, 웹 캐시 기만 취약점이 발생할 수 있음. 

**예시**
만약 `/static` 경로에 대해서 캐싱을 하는 규칙이 있는 경우에 `/static/..%2fprofile` 경로에 대한 처리 
- 원본 서버: 적절한 디코딩과 정규화를 하는 서버는 `/profile`로 변환한 뒤, 프로필에 대한 정보를 반환함. 
- 캐시 서버: 디코딩을 하지 못하는 캐시 서버는 해당 경로를 `/static/..%2fprofile`로 해석하고 캐싱하게 됨. 

이런 경우에 해커가 피해자의 프로필 정보에 대해서 캐싱을 하도록 유도하고 접근할 수 있음. 

**참고**
- `../`는 인코딩 되어야함. 아니면 피해자의 브라우저에서 자체적으로 경로를 처리할 수 잇음
- `/static/..%2fprofile`처럼 두번째 `/`만 인코딩하는 것이 좋음. 
	- 깐깐한 캐시 서버는 `/static/`를 정적 디렉토리로 인식하지 못할 수 있음. 
- 하지만 `/static/..%2fprofile`이 안 먹힌다면, 다양한 시도를 해봐야함. 
	- 전체 인코딩: `%2fstatic%2f..%2fprofile`
	- 점(.) 인코딩: `/static/%2e%2e/profile`


#### 원본 서버의 정규화 처리 여부 파악

캐시 서버가 테스트 요청을 가로채지 못하도록 POST 요청 사용하는 것이 좋음. 
예: `/profile` 을 `/aaa/..%2fprofile` 로 수정
- 기존 응답과 동일한 경우: 원본 서버에서 `/profile`로 처리된 것임. 
- 기존 응답과 다른 경우: 해당 경로를 `/aaa/..%2fprofile`로 처리한 것임. 

#### 캐시 서버의 정규화 처리 여부 파악

캐시되는 정적 디렉토리 요청을 찾아낸 후 
`/aaa/..%2fassets/js/stockCheck.js` 요청을 보냄. 
- 캐시가 안되는 경우: 해당 경로가 `/aaa/..%2fassets/js/stockCheck.js`로 처리되고 있고 `/assets`에 대해서 정적 디렉토리 캐싱 규칙이 적용되고 있음을 알 수 있음. 
- 캐시가 되는 경우: 디코딩 및 정규화가 되어 `/assets/js/stockCheck.js`로 처리되고 있음. 

`/assets/..%2fjs/stockCheck.js` 요청을 보냄. 
- 캐시가 안되는 경우: 캐시 서버에서 디코딩 및 정규화가 되어 `/js/stockCheck.js`로 처리되고 있고 `/assets`에 대해서 정적 디렉토리 캐싱 규칙이 적용되고 있음을 알 수 있음. 
- 캐시가 되는 경우: `/assets/..%2fjs/stockCheck.js`로 처리되고 있음.

물론 정적 디렉토리를 기반으로 캐싱을 하는 것이 아니라 다른 캐싱 규칙이 적용되고 있을 수도 있음. 


#### 원본 서버의 정규화 기능 악용

원본 서버는 `.`이나 `/`에 대해서 디코딩을 처리하지만 캐시 서버는 디코딩하지 않는 경우

`/assets/..%2fprofile`
- 캐시 서버: 해당 경로를 `/assets/..%2fprofile`로 해석
- 원본 서버: 해당 경로를 `/profile`로 해석
원본 서버는 동적 프로필 정보를 반환하며 이 정보가 캐시에 저장됨. 


#### 캐시 서버의 정규화 기능 악용

캐시 서버는 `.`이나 `/`에 대해서 디코딩을 처리하지만 원본 서버는 디코딩하지 않는 경우

`/profile%2f%2e%2e%2fstatic`
- 캐시 서버: `/static`으로 해석
- 원본 서버: `/profile%2f%2e%2e%2fstatic`으로 해석
원본 서버에서의 응답이 오류 메시지일 가능성이 높기 때문에 구분 기호를 추가해줘야함. 

`/profile;%2f%2e%2e%2fstatic`
- 캐시 서버: **구분 기호를 사용하지 않아** `/static`으로 해석
- 원본 서버: 구분 기호를 사용해 `/profile`로 해석
원본 서버는 동적 프로필 정보를 반환하며 이 정보가 캐시에 저장됨. 



### 파일명 캐시 규칙 악용

`robots.txt` , `index.html` , `favicon.ico`와 같이 특정 파일명을 기준으로 캐시 규칙을 설정해둔 경우

`/profile%2f%2e%2e%2findex.html` 같은 요청을 보냄. 
- 응답이 캐시된 경우: 캐시 서버가 `%2f%2e%2e%2`를 디코딩 처리를 해서 `/index.html`로 해석함. 

정적 디렉토리 캐시 규칙의 악용 파트처럼 `/profile;%2f%2e%2e%2findex.html?aaa` 같은 요청을 보내서 원본 서버는 `/profile`로 해석해 응답을 하고 캐시 서버는 `/index.html?aaa`로 해석해 응답을 캐싱하도록 하면 악용이 가능
