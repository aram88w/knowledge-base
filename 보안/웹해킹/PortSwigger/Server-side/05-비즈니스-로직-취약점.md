## 비즈니스 로직 취약점

**비즈니스 로직**의 주요 목적 중 하나는 애플리케이션이나 기능을 설계할 때 정의된 규칙과 제약 조건을 시행하는 것. 
넓게 말하면, 비즈니스 규칙은 특정 시나리오가 발생했을 때 애플리케이션이 어떻게 반응해야 하는지를 규정. 
여기에는 사용자가 비즈니스에 부정적인 영향을 미치거나 단순히 타당하지 않은 행동을 하지 못하도록 방지하는 것이 포함

논리적 결함으로 인해 공격자는 이러한 규칙을 우회할 수 있음. 
- 의도된 구매 절차를 거치지 않고 거래를 완료할 수 있음. 
- 사용자 입력 데이터에 대한 유효성 검사가 제대로 이루어지지 않거나 아예 없는 경우, 사용자는 거래에 중요한 값을 임의로 변경하거나 의미 없는 값을 입력할 수 있음.

### 클라이언트 검증 의존

사용자들이 오직 제공된 웹 인터페이스(클라이언트)를 통해서만 수행할 것이라고 가정하면 안됨. 적절한 무결성 검사나 서버 측 검증을 해야함. 
공격자들은 브라우저에서 데이터가 전송된 후 서버 측 로직에 도달하기 전에 데이터를 조작할 수 있음. 


**예시**
1. 비밀번호 변경 POST 요청에서 username을 원하는 아이디로 조작
2. 이중 용도로 사용되는 엔드포인트인 경우 파라미터 제거 시 취약점 접근 가능 
``` php
// 서버 코드 예시
// [ /api/update_user 엔드포인트 (동일한 스크립트) ]

// 1. 이메일 파라미터가 있으면 이메일 업데이트 함수 실행
if (isset($_POST['email'])) {
    updateEmail($_POST['email']);
}

// 2. 새 비밀번호 파라미터가 있으면 비밀번호 변경 로직 실행
if (isset($_POST['new_password'])) {
    
    // 2-a. '현재 비밀번호' 파라미터가 같이 넘어왔는지 확인
    if (isset($_POST['current_password'])) {
        // 일반 유저 정상 플로우: 현재 비밀번호를 검증하고 새 비밀번호로 변경
        verifyPassword($_POST['current_password']); 
        changePassword($_POST['new_password']);
    } 
    // 2-b. '현재 비밀번호' 파라미터가 아예 없는 경우
    else {
        // 관리자용 플로우 또는 개발자의 실수 (검증 없이 바로 변경)
        forceChangePassword($_POST['new_password']); 
    }
}
```
- '현재 비밀번호' 파라미터를 없앤 경우에 관리자 계정에 접근이 가능함. (근데 이렇게 작성하는 서버 코드가 말이 되나?)
- 모든 관련된 코드 경로가 제대로 실행되도록, 한 번에 하나의 매개변수만 제거해야 함.
- 파라미터의 이름과 값을 모두 삭제, 일반적으로 서버는 이 두 경우를 서로 다르게 처리



### 비전형적인 입력값 

사용자가 일반적이지 않은 입력값을 넣을 수 있도록 허용이 되어있다면 심각한 문제를 초래할 수 있음. 
예: 계좌이체에서 음수를 송금하면 오히려 돈을 받는 상황, 쇼핑몰 제품의 개수를 음수로 넣을 수 있는 상황

**체크사항**
- 데이터에 대해 어떤 제한 사항들이 있나요?
- 그 한계에 도달하면 어떤 일이 일어나나요?
- 입력 데이터에 대해 어떠한 변환이나 정규화 작업이 수행되고 있나요?

**예시**
- 음수 입력
- 양수의 최대값을 넘어가면 음수로 바뀜: int(4바이트) 기준으로 -2,147,483,648 ~ +2,147,483,647
- 최대 길이(예: 255)를 넘어가는 경우 뒷부분이 짤려서 저장됨
	- 회원가입할 때 이메일을 `testAAAA...@dontwannacry.com.web-security-academy.net` 이런식으로 넣으면 DB에는 `@dontwannacry.com`으로 저장되지만, 메일은 내 이메일로 받을 수 있음. (이렇게 허술한 웹 서비스가 있는지는 모르겠음.)


### 예정된 순서 무시 

공격자들은 웹의 워크플로우 순서를 따르지 않을 수 있음. 

**강제 브라우징**: 웹사이트가 의도한 순서를 무시하고, 억지로 다른 단계의 요청(Request)을 보내보라는 뜻
- 건너뛰기 (Skip): 1단계 ➔ **(2단계 건너뜀)** ➔ 바로 3단계 URL로 요청 보내기 
	- 건너뛸때 Burp Suite의 Intercept Drop 사용 가능
- 반복하기 (Repeat): 1단계 ➔ 2단계 ➔ **2단계 또 보내기** ➔ 3단계
- 거꾸로 가기 (Reverse): 1단계 ➔ 2단계 ➔ 3단계 ➔ **다시 1단계로 요청 보내기**

이렇게 하다보면 개발자가 전혀 예상하지 못한 논리적인 오류(예상된 변수들의 값이 null이거나 초기화되지 않은 상태)가 발생함. **이때의 에러메시지가 엄청난 힌트**임. 


**예시**
- 로그인 후 2차 인증을 하지 않고 홈화면에 들어가면 로그인이 되는 경우
- 'POST 주문' -> 검증 -> 'GET 주문완료 페이지' 단계에서 **'GET 주문완료 페이지' 내에서 실제 주문 로직을 실행하는 웹사이트**(RESTful API의 기본 원칙인 'GET 요청은 데이터의 상태를 변경하면 안됨'을 어긴 잘못된 설계)인 경우에 검증 단계를 건너뛰고 주문을 할 수 있음.
- 로그인 -> role 선택 -> 메인 페이지 단계에서 role 선택 리다이렉트 요청 자체를 Drop 하면 role 선택 화면 자체를 GET 하지 못하기 때문에 role 선택 단계인 session을 받지 못하게 되고, 기본 role(여기서 기본 role을 관리자권한을 잘못 설정함.)로 메인페이지에 갈 수 있음.


### 도메인 특유 결함

대부분의 경우, 해당 비즈니스 분야나 웹사이트의 목적에 특유한 논리적 오류들을 마주하게 됨. 
이러한 취약점들을 파악하려면, 공격자가 어떤 목적을 가질 수 있는지 신중하게 고려해야 하며, 제공된 기능들을 활용하여 그 목적을 달성할 수 있는 다양한 방법들을 찾아보아야 함. 
특정 상황에서 무엇이 유리한지 이해하기 위해서는 **해당 분야에 대한 전문적인 지식**이 필요할 수 있음. 
	예: SNS 팔로워를 강제로 늘릴 수 있는 취약점을 발견했는데 이 중요성을 모르는 공격자라면 그냥 넘어갈 수 있음. 


**예시**
- 쿠폰을 번갈아가면서 먹이기
- 기프트카드를 쿠폰으로 구매해서 무한으로 크레딧 충전


### 암호화 오라클

해당 서버에서 사용하는 **암호문이 사용자에게 제공될 경우**, 공격자가 임의의 데이터를 암호화해 동일한 알고리즘을 사용하는 요구하는 곳에 공격을 할 수 있음. 

**예시**
이메일을 잘못 입력하는 경우, 잘못입력된 평문을 암호화해서 쿠키로 내려주고 해당 쿠키를 사용해서 화면에 보여주는 경우(복호화)에 공격자는 평문과 암호화된 쿠키, 해당 쿠키의 복호화를 알 수 있으므로, 관리자 계정의 로그인 유지 세션값을 유추해서 접근할 수 있음. 


https://portswigger.net/web-security/logic-flaws/examples/lab-logic-flaws-authentication-bypass-via-encryption-oracle
이 문제 풀때 암호화할때 16글자씩 묶어서 하므로 더미글자를 넣어서 맞췄어야했음. 그런데 더미글자를 넣지 않고 뒤에 32개를 짤랏을때 왜 화면에 복호화된 평문이 안나왔는지 모르겠음. 


### 이메일 주소 파서 불일치

인터넷 표준 규칙(RFC)에서 이러한 형태의 이메일 주소도 유효한 이메일로 인정함.
- `"john..doe"@example.com`: 아이디 부분에 따옴표와 연속된 마침표 허용
- `user(comment)@example.com` 주소 중간에 괄호로 주석 삽입 허용
- `"admin@company.com"@hacker.com` 아이디 부분 자체에 또 다른 이메일 형태 삽입 허용 (`""` 안의 내용은 무조건 하나의 텍스트로 취급함.)

만약 어떤 웹사이트에서 가입할때 입력한 이메일의 도메인(`@` 뒷부분)을 추출하는 파서로 사용자의 소속을 파악하는 경우에 문제가 발생할 수 있음. (단순하게 회사 도메인이 들어있는지만 확인하는 경우)

예: `"admin@company.com"@hacker.com`
- **보안 검증 시스템 (A):** `@company.com`가 들어있으면 campany.com 소속 직원으로 잘못 판단함.
- **실제 메일 발송 서버 (B):** 엄격한 국제 표준 규칙에 따라 분석하여 `""` 안의 내용은 텍스트로 취급하므로 `@hacker.com`으로 메일을 보냄.
