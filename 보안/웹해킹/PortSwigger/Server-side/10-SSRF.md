## SSRF

서버 측 요청 위조 SSRF(Server-Side Request Forgery)란 공격자가 웹 서버를 조종하여 **서버가 스스로 내부망이나 의도치 않은 외부 시스템에 대신 HTTP 요청을 보내도록 만드는 취약점**
클라이언트(해커)가 직접 요청하는 것이 아닌 **서버 측**에서 요청이 발생한다는 점이 특징

**예시**
- 이미지 업로드 (URL로 가져오기): 프로필 사진을 URL로 입력하는 경우, 해커가 이미지 URL로 입력하는 대신 `http://localhost/admin`을 넣음
- 웹훅 연동: 이벤트가 발생하면 알림을 보낼 슬랙/디스코드 URL을 입력하는 경우
- PDF 변환 서비스: 웹페이지 URL을 입력하면 PDF로 만들어주는 경우
- 링크 미리보기 기능: 노션이나 디스코드처럼 링크를 치면 썸네일을 가져오는 경우
- 방문자 추적을 위해 `Referer` 헤더를 기반으로 외부 링크를 추적하는 경우


### 서버 자체에 대한 공격

루프백 네트워크 인터페이스를 통해 해당 애플리케이션의 서버로 HTTP 요청을 보내도록 유도함. 
`localhost`, `127.0.0.1`: 서버 자기 자신을 뜻하는 IP 주소 

**예시**
``` http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D6%26storeId%3D1
```
재고 확인을 할때 이런 요청이 날아가는 상황에서, 공격자가 `http://localhost/admin`를 넣어서 보내면 관리자 권한이 없더라도 해당 페이지를 가져와줌. 

`/admin`에 대한 요청이 **로컬 머신(서버)에서 발신되면 요청이 신뢰할 수 있는 위치에서 발신된 것으로 간주**되기 때문에 애플리케이션은 관리 기능에 대한 접근 권한을 부여하게 됨. 


### 다른 백엔드 시스템 공격

애플리케이션 서버가 사용자가 직접 접근할 수 없는 내부 백엔드 시스템들과 상호작용하는 경우, 이러한 시스템들은 대부분 라우팅이 불가능한 내부 IP(프라이빗 IP) 주소를 가지고 있음. 

**내부 IP**: 외부 IP의 네트워크 안에서 자기들끼리만 사용하는 IP, 다음 3가지는 내부 네트워크에서만 사용함. 
- `192.168.x.x`: 주로 가정용 공유기나 소규모 사무실
- `172.16.x.x ~ 172.31.x.x`: 주로 도커나 클라우드 내부망
- `10.x.x.x`: 주로 대기업 사내망이나 AWS VPC

백엔드 시스템들은 일반적으로 외부 사용자가 접근 불가능한 네트워크 구조에 의해 보호되기 때문에 보안 수준이 상대적으로 낮은 편이고 취약한 내부 서버에 대해 패치를 하지 않았을 수 있음.

**예시**
``` http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://192.168.0.68/admin
```


### 블랙리스트 우회 

일부 애플리케이션들은 `127.0.0.1` 나 `localhost` 과 같은 호스트명이 포함된 입력 내용이나, `/admin` 와 같은 민감한 URL을 차단하는 블랙리스트를 사용함.

1. **`127.0.0.1` 을 다른 형태의 IP 주소로 우회하여 표기**
	- `2130706433`: 10진수 표기
	- `017700000001`: 8진수 표기
	- `127.1`: 리눅스 등 일부 운영체제에서는 중간의 0을 생략해도 `127.0.0.1`로 알아들음. 

2. **고유한 도메인 사용**: 해커가 목적지(A 레코드)를 `127.0.0.1`로 설정해둔 고유한 도메인(예: `my-domain.com`)을 만들고 해당 도메인을 사용해서 SSRF 공격을 하면 백엔드 서버에서 도메인 주소로 요청을 보낼때 블랙리스트를 피하게 되고 DNS 서버에서 `127.0.0.1` 응답을 받게 됨. 
	- `http://localtest.me`: 세계적으로 사용하는 `127.0.0.1`을 가리키게 세팅된 도메인

3. **URL 인코딩 및 대소문자 변환**
	- 대소문자 변환: 서버의 파일 시스템이 대소문자를 구별하지 않는다는 점을 노리기 
		- 예: `admin`이 차단 되어있는 경우, `aDmIn` 사용
	- URL 인코딩: 알파벳을 웹 통신용 특수 기호 형태로 바꾸는 것. 
		- 예: 알파벳 'a'는 URL 인코딩으로 `%61`입니다.

4. **리다이렉션 활용**: 보안 장치가 **사용자가 처음 입력한 URL만** 검사하고, 그 URL이 다른 곳으로 리다이렉션 하는 것까지는 끝까지 조사하지 않는 허점을 이용
	- 해커가 자신의 서버를 하나 만들고 요청이 오면 `http://127.0.0.1/admin`으로 리다이렉션 하도록 설정하면 백엔드 서버 내부에서 `http://127.0.0.1/admin`으로 리다이렉트 됨.
	- `http` 대신 `https`로 리다이렉트를 하면 보안 필터를 우회하는 경우가 많음.



### 화이트리스트 우회

일부 애플리케이션들은 특정 값들만 받아들이는 화이트리스트를 사용함. 
**URL 파싱 불일치점**: 보안 필터가 URL을 읽는 방식과 백엔드 서버가 URL을 읽는 방식이 미묘하게 다를 때 발생하는 빈틈을 노려야함. 

HTTP 라이브러리들이 URL 표준 규칙을 기반으로 기능하도록 작성되어있고 그걸 사용하는 구조.
그러나 **허술한 HTTP 라이브러리인 경우에 `#` 뒤의 `/admin` 같은 경로를 무시하지 않고 유지**하는 등의 이상하게 작동하는 경우가 있음. 
또한 HTTP 라이브러리들에서 미세하게 차이가 나는 부분들이 있고 이걸 **파서 불일치**라고 함. 
- 백슬래시 `\` 해석 차이: 어떤 라이브러리는 `\`를 경로 구분자 `/`로 알아서 고쳐서 해석하지만, 어떤 라이브러리는 도메인 이름의 일부로 해석
- 유니코드(특수문자) 변환 차이: 특정 언어는 라틴어 특수문자를 일반 알파벳으로 강제로 바꿔서 해석하는 버그가 있음. 

1. `@` 기호를 이용
	- 원리: 웹 브라우저나 서버는 URL에 `@`가 있으면, `@` 앞부분을 아이디, 비밀번호로 취급하고 **`@` 뒷 부분을 접속할 목적지(호스트명)로 인식하는 표준 규격**이 있음. 
	- 우회: 보안 필터에서 URL이 `expected-host`로 시작하는지 검사할 때 사용
	- 예: `https://expected-host:fakepassword@evil-host`
		- 보안 필터: `expected-host`니까 통과시킴.
		- 실제 서버: 앞부분(`expected-host:fakepassword`)은 로그인 아이디랑 비밀번호로 간주하고, 뒷부분(`evil-host`)을 목적지로 간주해서 접속함.
	- **주의**
		- `http://a.com/admin@expected-host` 같은 주소처럼 `@` 앞에 `/admin` 같은 경로가 사용된 경우에 `@`는 무시되고 `/admin@expected-host` 경로로 요청이 됨.
		- `http://a.com@expected-host/admin`에서 목적지는 `expected-host`, 경로는 `/admin`이 유지됨.

2. `#` 기호 이용
	- 원리: URL에서 `#` 기호는 웹페이지 안에서의 특정 위치(북마크 역할)를 나타냄. **서버가 통신을 할 때 `#` 뒤에 있는 글자들은 무시하고 접속을 시도함.**
	- 우회: 보안 필터에서 URL 어디든 `expected-host`가 포함되어 있는지를 검사할 때 사용
	- 예: `https://evil-host#expected-host`

3. DNS 명명 체계(하위 도메인) 활용
	- 원리: 도메인(`evil-host.com`)을 하나 사면, 그 앞에는 **맘대로 하위 도메인을 만들어둘 수 있음.** 
	- 우회: 보안 필터에서 URL이 `expected-host`로 시작하는지 검사할 때 사용
	- 예: `https://expected-host.evil-host`
		- 해커가 `evil-host` 도메인 앞에 `expected-host`라는 하위 도메인 설정

4. URL 인코딩 및 이중 인코딩 활용
	- 원리 및 우회: **보안 필터와 백엔드 서버에서 URL 파싱(디코딩) 코드가 다른 경우**에 사용
	- 예: 보안 필터는 디코딩을 한번만 하지만 서버에서는 재귀적인 디코딩을 하는 경우, 해커가 `#`을 두 번 인코딩하여 `%2523`을 보내면 보안필터는 `%23`으로 보고 통과 시키고 서버에서는 `#`으로 디코딩되어 사용됨. 

5. 기법들의 조합: 위의 방법들이 단독으로는 막힐 수 있기 때문에 섞어서 사용함. 
	- 예: `https://evil-host%2523@expected-host`
		1. 보안 필터의 해석: `https://evil-host%23@expected-host`
			- `%2523`을 한 번만 해독해서 `%23`으로 봄. 
			- `@` 기호를 보고 앞에 `evil-host%23`은 아이디/비밀번호로 보고 `expected-host`를 목적지로 봄.
		2. 백엔드 서버의 해석: `https://evil-host#@expected-host`
			- 재귀적으로 디코딩되어 `#`으로 봄. `#` 뒤에 있는 `@expected-host`는 무시됨.

#### 참고

`@`, `#` 같은 규칙들은 **URL 표준 규칙**인거지 HTTP 규칙은 아님. 
즉, HTTP 프로토콜(실제 날아가는 패킷)에 `@`, `#`을 사용해서는 안됨.

1. 올바른 SSRF 공격
``` http
POST /check-stock HTTP/1.1
Host: vulnerable-site.com
Content-Type: application/x-www-form-urlencoded

stockApi=http://google.com@127.0.0.1/admin
```

2. 잘못된 SSRF 공격
``` http
GET / HTTP/1.1
Host: google.com@127.0.0.1
```
- HTTP 프로토콜 구조상 Host 헤더에는 @를 이용한 라우팅 규칙 자체가 없음. 


### 리다이렉션을 통한 우회

만약 `/product/nextProduct?currentProductId=1&path=/product?productId=2`처럼 리다이렉션 주소를 받는 페이지가 있고 이 주소에 대해서 보안 검사가 철저히 이루어지지 않는 경우

``` http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://weliketoshop.net/product/nextProduct?currentProductId=6&path=http://192.168.0.68/admin

```

이러한 요청으로 보안 필터를 우회하고 (`weliketoshop.net` 사이트 내의 요청이니 통과할 가능성이 높음.) 리다이렉션으로 공격이 가능함. 



### 블라인드 SSRF 

해커가 URL을 백엔드 서버에 제공해서 HTTP 요청을 보내도록 유도할 수 있지만, **백엔드에서 온 응답이 애플리케이션의 프론트엔드에 전달되지 않는 경우.** 해커는 결과를 프론트엔드에서 확인할 수 없음. 

블라인드 SSRF에서 취약점을 공격하는 가장 좋은 방법은 **아웃오브밴드(OAST) 기법**을 사용하는 것임. 
Burp Collaborator나 Interactsh를 활용하여 고유한 도메인 이름을 생성하고, 이를 SSRF 공격에 활용하면 백엔드 서버와 해당 도메인과의 상호작용 여부를 모니터링할 수 있음. 

1. **인증이 없는 사내 관리자 페이지 공격** (가장 흔함): 내부망(예: `192.168.0.50`)에서 비밀번호 없이 클릭만으로 작동하는 관리자 시스템이 많음. 해커가 화면을 볼 필요 없이 그냥 URL만 쏘면 됨.
	- 예: `http://192.168.0.50/admin/delete_all_users` 유저 삭제

2. 다른 낡은 취약점들 (Log4j 등): 내부망에는 패치되지 않은 옛날 소프트웨어들이 많음. URL에 `${}`를 넣어서 명령어를 실행할 수 있는 Log4j처럼 **특정 URL로 악성코드르 실행**시킬 수 있음.


#### 참고

SSRF 취약점을 OAST 기법으로 공격할때 도메인에 대한 **DNS 조회는 이루어지지만, 실제 HTTP 요청은 네트워크 단(내부망의 방화벽, 보안 그룹, 아웃바운드 필터링 장비 등)에서 차단될 수 있음.** 

회사나 서비스의 백엔드 서버는 보통 외부 인터넷과 단절된 내부망에 숨겨져 있고 관리자들은 이 서버에서 데이터가 밖으로 새어 나가는 것을 막기 위해서 규칙을 설정해둠. 
- **HTTP 차단 (데이터 유출 방지)**: 백엔드 서버에서 뜬금없이 외부 인터넷으로 웹 접속(HTTP, 포트 80/442)을 시도하는 것은 차단시킴. 
- **DNS 허용 (필수 인프라)**: 하지만 서버도 작동하려면 외부의 합법적인 API나 업데이트 서버의 IP 주소를 알아야함. IP 주소를 알려면 도메인의 주소를 확인하는 DNS 조회(UDP 포트 53)는 반드시 열어두어야 함. 


#### CGI를 사용하는 웹서버

WAS가 없던 시절에는 복잡한 계산 등을 하는 프로그램(Python, C, Bash 등)을 웹서버에서 직접 실행시키는 구조였음. 
**CGI**는 웹 서버에서 외부 프로그램을 실행시킬 때, 서로 데이터를 주고 받기 위한 통신 규칙임. 
특정 엔드포인트에서 웹서버가 CGI 규칙을 통해서 외부 프로그램을 실행시키도록 설정되어있다면 사용자가 보낸 **HTTP 헤더 정보를 환경변수 형태로 바꿔서 프로그램에 전달**하게 됨. 
프로그램이 실행되기 전에, **웹 서버가 아까 만들어둔 환경변수를 먼저 열어봄.** (실행 환경을 세팅하기 위함.)

이때, 이러한 조건이 맞는다면 Shellshock 취약점(예: `() { :; }; /bin/bash -c "ping hacker.com"`)이 발생함. 
1. 해당 엔드포인트에 대해서 웹 서버가 외부 프로그램을 CGI 규칙으로 실행하는 경우
	- 예: `/cgi-bin/env`, `/cgi-bin/status`, `/cgi-bin/test.cgi`, `/cgi-bin/hello.sh`
2. 외부 프로그램이 취약한 구버전의 Bash 쉘 스크립트(내부에서 Bash를 실행하는 프로그램)인 경우


### HTTP 클라이언트 공격

지금까지의 SSRF는 백엔드 서버를 대리인으로 삼아 서버 내부의 공격을 한 것임.
이 공격은 애플리케이션이 해커가 제어하는 서버로 요청을 보내도록 하고 그 서버에서 악성 응답을 줌으로써 해당 연결을 수행한 HTTP 클라이언트에 하는 공격임. 
- 예: 해커 서버가 **수만 글자짜리 기형적인 응답 헤더**를 준 경우, 웹 서버 내부의 `curl` 같은 HTTP 클라이언트 프로그램은 이 긴 헤더를 메모리(버퍼)에 넣다가 메모리가 터져 버퍼 오버플로우 문제가 발생함. 
- 예: 프로필 사진을 해커가 운영하는 서버(`http://해커서버.com/pic.jpg` 등)에서 가져가라고 유도하고, 해커 서버는 **사진인 척하는 악성 스크립트 파일**을 응답으로 내려줌. 웹 서버가 프로필 사진을 여는 순간 해킹당함.
