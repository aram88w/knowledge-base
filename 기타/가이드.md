## 웹사이트 디자인 순서

>[!info] 디자인 적용 순서 
> 1. ==디자인 가이드== 정의: 마음에 드는 웹사이트를 캡처하든 검증된 디자인 키트(`shadcn` 등)를 사용하든 `Stitch` 사용하든 해서 웹디자인에 사용할 컬러 3개, 폰트 사이즈 3단계(제목, 본문, 소제목), 테두리 등의 값들을 미리 지정함.
> 2. ==레이아웃 구현==: Vue에서 전체적인 화면 구조를 디자인 가이드에 맞춰서 작성. 필요하면 가짜 데이터를 채워넣음.
> 3. 기능 주입: 클릭 이벤트, 백엔드 API, 실제 데이터 등 실제 기능을 넣음.
>    - 복잡한 기능을 사용해야하는데 기능이 검증이 필요한 경우에는 프로토타입을 따로 만들어서 검증 후에 옮기는 방식을 써도 됨

1. 색상
	- **브랜드 컬러 정하기:** `Primary` (포인트 컬러), 앱의 정체성을 나타내고 가장 중요한 버튼 등에 쓰이는 색상
	- **공통 배경 정하기:** `Background` (가장 밑바닥), `Surface` (배경 위 카드/패널)
	- **글자 단계 정하기**: `Text-Primary` (진한 색), `Text-Secondary` (부연 설명), `Text-Disabled` (비활성화)
	- **상태 색상 정하기:** `Success`, `Error`, `warning`
2. 타이포그래피 
	- 폰트 패밀리: 제목용 폰트와 본문용 폰트
	- 폰트 스케일: 사용할 글자 크기를 단계별로 정해둠. (예: 제목, 본문, 소제목)
3. 여백 및 크기
	- 요소들 사이의 간격과 크기 규칙: tailwind의 4px 단위의 `p-4`, `m-8` 등을 이용
4. 테두리 곡률
5. 그림자와 입체감
	- "클릭할 수 있는 버튼은 평소에 `shadow-sm`을 주고, 호버(Hover)하면 `shadow-md`로 띄운다."
	- "화면 중앙의 메인 컨트롤러 패널은 `shadow-xl`을 주어 배경과 분리시킨다."

## AI 없이 작성 못하는 코드는 AI를 사용하면 안 되나?

- (X) 구시대의 기준: "AI 없이 **작성(Write)**하지 못하는 코드는 쓰지 마라."**
- (O) AI 시대의 기준: "AI가 짠 코드를 **리뷰(Review)하고 통제(Control)**하지 못한다면 쓰지 마라."

코드의 아키텍처를 이해하고 코드를 평가할 수 있는 리뷰어의 시각이 있다면 AI를 편하게 다룰 수 있음. 
생각해보면 스프링처럼 직접 코드를 작성해봐야 코드의 리뷰 및 통제가 가능해지고 AI를 정확하게 사용할 수 있었음. 
그러나 지금처럼 AI가 계속 발전하는 와중에 코드를 하나하나 손수 작성하는 것은 획기적인 AI의 생산성을 이용하지 못하는 것임. 


***AI 시대에 코드 작성 방식***
AI한테 코드를 작성 시키기 전에 **한글 주석**으로 로직을 직접 작성해보기. 
'이 컴포넌트가 어떤 순서로 동작해야 하는가'에 대한 한글 주석(설계도)만큼은 꼭 먼저 작성하는 습관을 들이시길 강력히 권장

1. 데이터 흐름을 생각하기
	Tone.js를 어떻게 쓰는지 전혀 몰라도, 메트로놈이라는 '서비스'가 Controller(React)에게 제공해야 할 **입출력(Input/Output) 명세서**는 상식선에서 정의할 수 있습니다.
	- **Input (React → Engine):** "재생해라", "멈춰라", "BPM 120으로 바꿔라"
	- **Output (Engine → React):** "지금 박자가 울렸으니 화면에 불 켜라"

2. AI에게 **코드**가 아닌 **개념과 패턴**을 먼저 묻기
	처음보는 라이브러리 등을 사용해야할때나 처음 보는 패턴으로 작성해야할 경우에 바로 떠올라서 주석으로 작성하는 것은 불가능함. 그렇다면 **한글 주석으로 로직을 작성하기 전에** 해당 **개념과 패턴**에 대한 질문으로 학습함. 
	
	- "Tone.js를 처음 써보는데, 메트로놈을 만들려고 해. 코드는 짜지 말고 개념만 알려줘. 특히 오디오 엔진이 박자를 칠 때마다 React UI(화면)에 불빛을 깜빡이게 하려면 어떤 구조(패턴)로 데이터를 주고받아야 해?"

3. 학습한 개념으로 **한글 주석(흐름)** 작성하기
	내가 직접 주석을 작성함으로써 아키텍처, 패턴 구현 능력이 상승하고 코드 주도권이 AI가 아닌 나한테 생김. 
	한글 주석으로 작성 후에 AI와 의논 후에 주석에 맞춰 코드를 구현해달라고 하면 됨.

## 다국어 적용 시점

다국어는 **'인프라 구축'** 은 무조건 처음에, **'실제 번역 적용'** 은 개발 방식에 따라 유연하게 적용
**프로젝트 초기 (필수):** 라우팅 설정(예: `next-intl` 미들웨어 셋팅), 기본 언어 감지, 번역 함수(`t()`)를 사용할 수 있는 환경 셋팅은 **프로젝트 극초기**에 해두어야 함. 중간에 도입하면 기존에 하드코딩된 텍스트를 다 찾아서 바꿔야함. 


**개발 중에는 '기본 언어'만 유지 (추천)**
1. 개발하는 동안에는 기본 언어(예: `ko.json` 또는 `en.json`) 딱 하나에만 새로운 키와 문구를 추가
2. 다른 언어 JSON 파일은 건드리지 않습니다. (`next-intl` 같은 라이브러리는 해당 언어에 키가 없으면 알아서 기본 언어로 폴백(Fallback)되어 에러 없이 노출되도록 설정 가능)
3. **기능 개발이 완전히 끝나고 배포하기 직전**에 비어있는 다른 언어의 번역을 한 번에 채워 넣음.
