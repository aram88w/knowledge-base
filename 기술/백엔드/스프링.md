### 엔티티 표준 모델

- 권장 방식: `@Builder`를 적용한 전체 생성자 + 정적 생성 메서드(create, of, from) + JPA용 기본 생성자(`protected`)

``` java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED) // JPA를 위한 기본 생성자
public class Post {
    @Id @GeneratedValue ...
    private Long id;
    private String title;

    @Builder // 외부 노출 최소화
    private Post(String title) {
        this.title = title;
    }

    // 의도가 명확한 정적 생성 메서드
    public static Post createPost(String title) {
	    // 비즈니스 로직이나 검증을 여기서 처리 가능
        return Post.builder()
                .title(title)
                .build();
    }
}
```


### DTO 표준 모델

1. Request DTO (클라이언트 → 서버)
	- 조합: `record` + `@Builder`
	- 이유: 요청 데이터는 값이 변할 일이 없으므로 `record`가 최적입니다. 필드가 많을 경우 테스트 코드 등에서 객체를 편하게 만들기 위해 빌더를 붙입니다.

2. Response DTO (서버 → 클라이언트)
	- 조합: `record` + 정적 생성 메서드(`from`)
	- 이유: 엔티티를 DTO로 변환할 때 `PostResponse.from(post)`처럼 한 줄로 끝낼 수 있어 서비스 로직이 매우 깔끔해집니다.
	- `@Builder`는 필요한 경우 사용

``` java
@Builder
public record PostResponse(
    Long id,
    String title
) {
    // 정적 생성 메서드 (변환용)
    public static PostResponse from(Post post) {
        return PostResponse.builder()
                .id(post.getId())
                .title(post.getTitle())
                .build();
    }
}
```

### 로그 공통화

1. MDC에 값 저장
	- MDC에 값을 넣으면, 로그 패턴에서 `%X{키이름}` 형식으로 그 값을 꺼내 쓸 수 있음.
	- MDC는 `ThreadLocal`을 사용하므로 무조건 `clear()`, `remove()`로 비워줘야함. 

``` java
/**
* 모든 요청에 requestId를 부여하고 응답 헤더에 포함시키는 필터
*/
@Component
public class RequestIdFilter extends OncePerRequestFilter {
	@Override
	protected void doFilterInternal(
		HttpServletRequest request, 
		HttpServletResponse response,
		FilterChain chain) throws IOException, ServletException 
	{
		String requestId = UUID.randomUUID().toString().substring(0, 8); // 짧게 8자리만 사용
	
		MDC.put(LogKeys.REQUEST_ID, requestId);	
		request.setAttribute(LogKeys.REQUEST_ID, requestId);
		response.setHeader("X-Request-ID", requestId);
		
		try {
			chain.doFilter(request, response);
		} finally {
			MDC.clear(); // 스레드 누수 방지
		}
}

```

 * Reactor(Mono/Flux) 환경에서 MDC 전파를 위한 설정

@Configuration
public class ReactorMdcConfig {

    @PostConstruct
    public void setupMdcPropagation() {
        // 방법 1. 기존의 전체 MDC 맵 전파 설정 (유지)
        ContextRegistry.getInstance().registerThreadLocalAccessor(
                "MDC",
                MDC::getCopyOfContextMap, // 현재 스레드 MDC 전체를 Reactor 저장소(Context)로 복사
                MDC::setContextMap, // 새로운 스레드에서 복사본을 다시 MDC에 저장
                MDC::clear
        );

        // 방법 2. [핵심 추가] Reactor Context의 "videoId"와 "jobId"를 MDC로 매핑하도록 등록
        // contextWrite(Context.of(LogKeys.VIDEO_ID, xxx)); 같이 수동으로 Context에 추가한 값을 이 키들을 찾아 MDC에 넣어줍니다.
        ContextRegistry.getInstance().registerThreadLocalAccessor(new VideoIdAccessor());
        ContextRegistry.getInstance().registerThreadLocalAccessor(new JobIdAccessor());

		// 스레드가 전환될 때마다 1,2번을 자동 적용함. 
        Hooks.enableAutomaticContextPropagation();
    }

	// videoId 전용 전파기
	class VideoIdAccessor implements io.micrometer.context.ThreadLocalAccessor<String> {
	    @Override public Object key() { return LogKeys.VIDEO_ID; }
	    @Override public String getValue() { return MDC.get(LogKeys.VIDEO_ID); }
	    @Override public void setValue(String value) { MDC.put(LogKeys.VIDEO_ID, value); }
	    @Override public void reset() { MDC.remove(LogKeys.VIDEO_ID); }
	}
}

### Mono / Flux 비동기-논블로킹

 데이터 흐름의 파이프라인을 설계
- Mono: 결과가 딱 하나이거나 없는 경우 (단건 조회, API 호출, 단순 성공 여부)
- Flux: 병렬 처리 (데이터가 1건씩 생기는대로 클라이언트에 반환, 데이터 스트리밍)

##### Mono
- Project Reactor에서 제공하는 0 또는 1개의 결과 데이터를 방출(Emit)하는 비동기 스트림(Publisher)
- 파이프라인: 여러 연산자를 체이닝하여 데이터 가공 흐름을 설계할 수 있음. 
- *주의: @Transactional은 ThreadLocal 기반으로 동작하므로 스레드가 바뀌면 종료됨. Mono를 사용하면 Netty 스레드, boundedElastic 스레드 등으로의 전환이 잦으므로 주의해서 사용해야함.*
- 보통 DB에 접근하는 객체를 따로 분리하여 @Transactional을 해당 객체에 붙여 DB에 접근할때마다 새로운 트랜잭션이 생기도록 하고 boundedElastic 스레드에서 호출하여 사용함.

``` build.gradle
implementation 'org.springframework.boot:spring-boot-starter-webflux'
```

``` java
/**
 * 스프링 MVC 환경에서 Mono 사용
 */
@PostMapping("/scan")
public Mono<ResponseEntity<ApiResponse<ScanResponse>>> scanScene(@Valid @RequestBody ScanRequest scanRequest) {
    log.info("사전 조사 요청 시작: {}", scanRequest);
    setRequestAttribute(LogKeys.VIDEO_ID, scanRequest.videoId());
    return captureService.scanScene(scanRequest)
            .map(result -> ResponseEntity.ok(ApiResponse.ok(result)))
            .contextWrite(Context.of(LogKeys.VIDEO_ID, scanRequest.videoId()));
    }
```
- 컨트롤러에서 톰캣 스레드는 Mono 설계도를 만든 후 바로 반환됨.
- 설계도를 보고 Netty 스레드, boundedElastic 스레드가 처리함

``` java
public Mono<ScanResponse> scanScene(ScanRequest dto) {
        return Mono.fromCallable(() -> {
                    // ✅ JPA는 여기
                })
                .subscribeOn(Schedulers.boundedElastic()) // 블로킹 I/O 작업은 boundedElastic 사용
                .flatMap(pythonWorkerClient::fetchSceneScores)// ✅ WebClient는 Netty
                .doOnNext(response -> log.info("사전 조사 결과 응답 성공"))
                .onErrorMap(error -> {
                    // 에러처리
			    })
			    .doFinally(...) // 초기화 로직
			    .contextWrite(Context.of(key, value));
```


- `Mono.fromCallable(() -> data)`: 일반 동기 로직을 Mono로 감쌀 때 사용 (예외를 던질 수 있는 로직에 사용)
- `Mono.fromSupplier(() -> data)`: 일반 동기 로직을 Mono로 감쌀 때 사용
- `.subscribeOn(Schedulers.boundedElastic())`: 해당 로직이 실행될 스레드 풀을 지정함.
- `Schedulers.boundedElastic()`: 블로킹 I/O 작업(DB 조회, 파일 저장 등)을 위한 전용 스레드 풀
	- JPA 같은 블로킹 작업을 리액티브 기본 스레드(Netty 스레드)에서 실행하면 먹통이 될 수 있어서 boundedElastic를 사용
- `.flatMap()`: 비동기 작업 결과를 가지고 또 다른 비동기 작업을 할때 사용
	- 또 다른 Mono를 반환하면 이들을 흐름을 평평하게('flat') 펴주기 위해 사용
- `.then()`: 앞의 비동기 작업이 완료 되면 실행. 앞의 작업의 결과를 버려짐.
	- 앞의 작업 결과값은 필요하지 않고 순차적인 실행이 필요한 경우 사용
- `.doOnNext()`: 데이터가 성공적으로 통과하면 실행
- `.doFinally()`: 성공하든 실패하든 무조건 실행 (초기화 작업에 많이 사용)
- `.onErrorMap()`: 발생한 에러를 다른 타입의 에러로 변환 (예외 객체를 반환)
- `.onErrorResume()`: 에러가 발생했을 때 다른 흐름으로 대체 (새로운 Mono를 반환)
- `.contextWrite()`: Reactor 저장소(Context)에 데이터 저장
- `.timeout()`: 타임아웃 설정


### @Async 비동기 처리

##### @Async

- 설정: main 클래스에 `@EnableAsync` 명시
- 사용: `@Async`
- 주의점: 단순히 `@Async`만 쓰면 스프링은 기본적으로 `SimpleAsyncTaskExecutor`를 사용합니다. 이 녀석은 요청이 올 때마다 **스레드를 무한정 새로 만드는** 위험한 녀석입니다. 실제 운영 환경에서는 반드시 **커스텀 ThreadPoolTaskExecutor**를 설정해서 사용해야 합니다. 
- 사용할 때는 `@Async("myExecutor")` 처럼 빈 이름을 명시해주면 됩니다.

``` java
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean(name = "myExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5); // 기본 스레드 수 (항시)
        executor.setMaxPoolSize(10); // 최대 스레드 수 (QueueCapacity가 꽉 찬 경우 스레드 추가)
        executor.setQueueCapacity(100); // 작업이 머무는 대기 공간 크기
        executor.setThreadNamePrefix("AsyncThread-"); // 로그에 찍힐 스레드 이름의 앞부분
        executor.initialize();
        return executor;
    }
}
```

##### Mono와 @Async 차이

1. `@Async`: "이 작업은 오래 걸리니까 **다른 스레드**에서 따로 돌려줘." (단순 배경 작업)
	- 단순한 배경 작업: "로그를 저장해라", "메일을 보내라" 같이 결과값이 중요하지 않거나, 메인 로직과 분리된 작업
2. `Mono`: "이 작업은 여러 단계의 비동기 흐름이 엮여 있는 **파이프라인**이야." (정교한 흐름 제어)
	- I/O가 많은 작업: 외부 API 호출, Redis 조회, DB 작업 등 **기다림(Wait)**이 발생하는 작업이 여러 개 섞여 있을 때.
	- 정교한 흐름 제어: "A 작업이 성공하면 B를 하고, 실패하면 C를 해라" 같은 **복잡한 조건부 비동기 로직**이 필요할 때.
	- 고성능/고효율: 적은 수의 스레드로 엄청나게 많은 동시 요청을 처리해야 할 때.

                .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE) 
                .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE) // 공통 헤더

2. API 호출
``` java
private final WebClient webClient;

public Mono<ScanResponse> fetchSceneScores(ScanJobMessage scanJobMessage) {
    return webClient.post() // 1. HTTP 메서드 결정 (get, post, put, delete 등)
            .uri("/scout/scan") // 2. 엔드포인트 경로 (baseUrl 뒤에 붙음)
            .contentType(MediaType.APPLICATION_JSON) // 3. 요청 컨텐츠 타입
            .accept(MediaType.APPLICATION_JSON) // 4. 응답 받을 타입
            .header("X-Request-ID", MDC.get(LogKeys.REQUEST_ID)) // 5. 개별 헤더 세팅
            .bodyValue(scanJobMessage) // 6. 요청 바디 데이터
            .retrieve() // 7. 응답 결과 추출 (실제 실행 루틴 진입)
            .onStatus( // 8. HTTP 상태 코드별 에러 처리
		        // 1. 첫 번째 인자: 상태 코드가 '에러'인지 판별하는 조건 (Predicate)
				statusCode -> statusCode.isError(), 
			    // 2. 두 번째 인자: 에러일 경우 응답(response)을 받아 처리하는 함수 (Function)
			    response -> {
				    return response.bodyToMono(JsonNode.class) // 에러 바디를 JSON으로 읽기
				            .flatMap(json -> {
				                String msg = json.get("message").asText(); 
					            // 마지막엔 반드시 Mono.error()로 예외를 던져야 함!
				                return Mono.error(new RuntimeException("서버 에러 발생: " + msg));
				            });
			})
            .bodyToMono(ScanResponse.class) // 9. 응답 바디를 특정 객체(Mono)로 변환
            .doOnNext(...)
            .flatMap(...)
            .timeout(Duration.ofSeconds(60));
    }
```

- **`post() / get() / put()`**: HTTP 메소드 정의
- **`uri()`**: 호출할 경로 지정
- **`header(key, value)`**: 헤더 추가
- **`bodyValue(Object)`**: 요청 바디에 객체를 담음 (자동 JSON 직렬화)
- **`retrieve()`**: 응답을 가져옴. 응답 본문(Body)에 바로 접근할 때 사용
- **`onStatus(predicate, function)`**: 특정 상태 코드가 올 때 예외를 발생시키거나 커스텀 로직을 실행
	- Mono.error()를 던져야하기 때문에 보통 4xx, 5xx인 경우에 예외 처리 로직에서 사용
- **`bodyToMono()`**: 응답 본문을 Mono<>로 변환
- **`bodyToFlux`**: 응답 본문을 Flux<>로 변환
